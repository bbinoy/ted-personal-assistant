# Safety model

The agent can read your mail and act on your behalf, so most of the design is about limiting what it can do and making everything it does visible and reversible.

| Layer | What it does |
|---|---|
| Owner allowlist | Only your own *Note to Self* (or, with the assistant's own account, your one-to-one chat), from the admin, is ever acted on: the sender must resolve to the registry record with role admin, by Signal account id, else by your number (`guards.ts`, `src/tenants/tenants.ts`; the id is learned once from your first message and logged; seeded from `SIGNAL_OWNER_NUMBER`). Your linked device also receives all your other Signal traffic; it is dropped and logged with a masked number. (tested) |
| Admin role and capabilities | The admin role changes ONLY through the local CLI (`npm run tenants -- set-admin <id>`, also the way back in after a lock-out). No tool, chat path, hook or agent-relayed message can change it (a test scans `src/` for any import of `setAdmin`), and a message relayed by another agent never grants anything. A friend's capabilities are not stored and nobody can grant or revoke them: she has every capability except the owner's own (`OWNER_ONLY`: `profile`, `card`, `admin`, `drive`, which need the instance's own login), so the admin role, the saved profile, the card and the owner's Drive connectors can never be hers; what she cannot use is what is not set up, what `.env` switches off and what her own `tenant.json` turns off. To stop a friend the admin suspends or removes her. **The admin's powers are the instance's:** invites, list, suspend / resume / remove a tenant (suspend and remove ask on the admin's phone), pause, `/card off`, doctor / cost / error reports and system notices, oversight of groups, and the instance's own logs and audit. They give no access to a tenant's notes, history or session (see Tenant isolation); a test lists the admin tools and checks it. |
| Tool policy | allow / ask / deny in `src/policy/policy.ts`, tested against real tool names. Every tool the model might get is declared in one manifest (`src/policy/toolmanifest.ts`, the rows of the tool modules in `src/modules`) by what it is, not by who may use it: a read or the assistant's own plumbing runs, everything else goes through the approval judge below and then, if it says ask, to your phone; the same for every mail provider and every place. `classify` is one fold for every run (the owner's, a group's, a friend's; attended or not, `src/core/runkind.ts`): the tool exists here (the run's tool set, derived from its conversation's capability set for the owner too, and the row's `attended` and `who`), the never-allowed set, local files, then the manifest (a free tool allows, anything else asks), lowered by every module's floor (a floor can only restrict), then the notes path for the file tools. There is no separate rule for a group: its browse entry tool is judged like yours, with the member's words as provenance. Unknown tools *ask*: they are never free and never judged, whatever their name says (a read verb in the name only marks the text it returns as untrusted). Every read of a data kind (mail, calendar events, Notion pages, Drive and Docs files, web pages) is untrusted text: after one, the judge is told the run's arguments may be steered; only public weather data is exempt. The heartbeat run reads untrusted mail with nobody watching, so the judge is told so as soon as it has read mail, and a call that a mail asked for asks you. **The never-allowed set** (trading, trash, permanent delete, spam, blocking a sender) is hard code for everyone (owner, group, friend) and every mail or file provider, by ONE mechanism (`src/policy/neverallowed.ts`, `src/policy/toolmanifest.ts` `neverAllowedTool`, `src/policy/policy.ts`): a manifest row whose action is `trash`, `delete`, `spam`, `block` or `trade` (Mailbird trash, delete, discard draft, spam, block; Gmail trash, untrash, spam, delete draft and label; Calendar delete; Drive trash; the Claude Docs delete), the trading connector as a whole (a module marked `never`, any tool under its prefix), a name fallback for a tool no module lists (the words trash, delete, purge, erase, destroy, spam, junk or block at word boundaries), and the call's arguments (a TRASH or SPAM label however spelled, `spam: true`, `in_trash` or `archived` on any tool, Notion `allow_deleting_content: true` (it deletes child pages), an `action` of delete, trash, purge and the like). Hidden tools, the judge floor and the no-fix rule read the same predicate. **Five destructive actions are not in that set but allowed, with care** (action `delete-confirm`, `DELETE_CONFIRM` in `src/policy/neverallowed.ts`): deleting a draft (Mailbird `discard_draft`, Gmail `delete_draft`), deleting a calendar event (the connector's `delete_event` and a friend's `manage_event` with action delete), moving a Notion page to the bin (`notion-update-page` with `in_trash` or `archived` true, the owner's and a friend's; declared by the module's floor `confirmDelete`, for those tools and those arguments only, so the same flag on any other tool stays denied) and moving a Drive file to the bin (`trash_file`, the owner's Drive). They are never free and never fixed ("yes, but change it" cannot retarget them), and they go to the judge, whose default for a delete is ask: the judge is told by code, in a line `Created by the assistant in this conversation: yes, no or unknown` (the call's id against the ids in the assistant's own create results of this conversation within 24 hours, `src/approvals/created.ts`, in memory, per conversation), and may pass a delete only for something the assistant just made and no longer needs, or that your own message asked to remove. Anything of yours, older, shared, unasked or asked for by a mail or page asks you, on the phone of the conversation that made the call (her chat for a friend), with a title that says what goes ("Delete draft", "Delete calendar event", "Move Notion page to the bin", "Move Drive file to the bin") and the ids and the subject, summary or title the call carries. A calendar delete that names guests (it would email a cancellation) is never judged. Everything else that deletes stays denied (conversations in Mailbird, Gmail trash, untrash, spam and `delete_label`, Claude Docs `delete`, trading, an unlisted tool whose name says so). Moving Mailbird mail (`move_conversation`, whose destination may be Trash or Junk) always asks and is never judged. Unsubscribing is an ordinary action: floor, judge, then your phone. What a group or a tenant may use at all is its capability set (`src/policy/capabilities.ts`), the same table for tools and skills: a tool or skill outside it does not exist for her and an unknown tool is denied. No tool input may reference a local file, for any source including groups and tenants: any string value that starts with `file:`, and an absolute or `~` path in an attachments field, are denied, so an injected email cannot get `~/.ssh` or `.env` attached to a draft. An approval of a mail shows the attachments by name or address (`src/policy/mailview.ts`, `src/approvals/format.ts`), not only that there are some. |
| Approvals | Approvals are conversational (docs/ARCHITECTURE.md, "Approvals"), and only a chat turn asks (unattended runs never do, next row). A chat question waits 15, a stranger's registration a day; the question states the real wait, and a timeout or any doubt means *no*. Several approvals can be open at once. Edit-and-approve is limited to calendar create/update, never to recipients or attendees. **What stays in code:** only a message after the question or a reaction on it resolves an approval; a 👍 / 👎 and an exact plain yes / no for the single open approval (or for the one a reply quotes) are matched by code; an edit goes only through the calendar allow-list (never recipients), so what runs is what was asked about or an allowed edit of it; any failure approves nothing, is audited, and is returned to the agent as the tool result (it may ask again at most twice for the same call). **An edit is never an answer:** editing a message ("no" into "yes", or the reverse) cannot approve or decline anything, because the approval check is skipped for every edit and picture caption and an edit of a message that was taken as an answer is dropped (`edit()` in `conversation.ts`, tested); an approval is answered only by a new message, a reaction on the question, or a quoted reply. **What is the model's:** which approval a reply answers (one, several: "yes to both", or none), whether it is yes, no, an allowed edit or something else ("yes but not Bob", "later", a hedge, a question and sarcasm are not approval: the approval stays open and the owner gets a short reply), and the wording of the question. The same small model (and warm process) as the approval judge below does the reading, told which job it has in the first line of the prompt; an answer that names another job is discarded. There is no length limit and no word list: a wrong `approve` from the model on a reply is an approval, so this is only as safe as the judge (measured: 0 false approvals in 3 of 4 passes over 72 replies, one stale-quote case in the fourth, see ARCHITECTURE; that is evidence on a small corpus, not a bound). A background approval (today only a stranger's registration; unattended runs ask nothing) is answered only by a reply that quotes it or a reaction on it: a bare yes / no never reaches it (code, tested), and its question says so (registration's own text), and the reading model is shown it as such but cannot answer it from a message that quotes nothing of it. When one lapses unanswered nothing is posted in the chat (a chat question, a registration alike: a registration is asked again at the next start): one line goes into that conversation's journal and an `approval-expired` audit row; the model is told an expired question was *not answered in time* (nothing was done, mention it later), not that it was declined, and a late yes quoting a question that timed out is answered with "timed out, ask again" and runs nothing. A voice message may answer (the judge is told it is an automatic transcript and asks again when a risky action is ambiguous). **One approver per conversation:** a question is asked in the chat that triggered the action, never elsewhere: the owner's chat for her own turns and her unattended runs (the heartbeat run and its expert), a group in the group (ANY member may answer, by message, quote or reaction), a tenant in her own chat (`src/approvals/approvers.ts`, one place, keyed by the conversation). Every question carries its conversation and an answer must come from the same one, so the admin never approves for a tenant (nor a tenant for the admin, nor one group for another); a quoted reply to another conversation's question, a text that merely contains a yes, and a message relayed by an agent answer nothing. A tenant who has been removed cannot be asked at all: nothing is sent, and the owner's chat is never the fallback. A card payment is asked in the owner's foreground chat only (typed yes, unchanged); a group, a tenant and an unattended run never pay. **A payment resolves only through a direct path:** it is the sole open approval of its conversation, or the reply quotes it. The answer model's choice of target never resolves it: with a payment and another question open and no quote, a bare YES that the model aims at the payment approves nothing and the owner is asked which one is meant (tested); "yes to both" never applies to it either. Open approvals are keyed by conversation and message timestamp, so the same timestamp in two conversations is two questions. The audit records who answered; which tools a group has is unchanged (today none asks). **There is no approval inbox** (deleted 26 Oct): unattended runs ask nobody (next row), so nothing is parked, batched, numbered or expired, and `/approvals` is gone. **Question wording:** one model call writes it and code requires every address, URL, title, subject, time, date, amount and Cc / Bcc word (opaque ids of events, mails, pages and files are not required: the question names the thing, not its id) from the arguments to appear verbatim, and no address or link that is in neither the arguments nor the code-rendered details; otherwise nothing is sent. The question must also show the call faithfully: the writer is told to name every recipient and attachment and to quote the text that will go in full and verbatim, and the approval judge (task `check`, same model) reads the code-rendered details next to the finished question and refuses one that hides or rewords any of it (a reply carrying a code described as "a thank-you"); a refused question is not sent, the failure is audited (`question-failed`) and returned to the run as the tool result so it asks again; a judge failure or timeout also sends nothing. A card payment keeps its own fixed, code-checked text and is not reviewed. This leaves the model free to *describe* the action wrongly ("add" for "replace", a body's claim repeated as fact) and to be steered by attacker text in an email body; a hostile argument described truthfully is still the owner's decision. Everything is logged: `approval-asked` with the full arguments and the question, `question-failed`, `answer-*` with who answered and the verdict, `approval-outcome` with whether the executed arguments equal the asked ones; `npm run report` shows "Approvals: question vs arguments". |
| Unattended runs never ask | Since 22 Oct (the owner: "act when it's sure and stay silent if it's not"). A run that answers no live message of a person (a heartbeat look of the owner, a group or a friend; its expert and the routines it delegates, the brief, the evening wrap, the weekly review; the browse worker of such a run) puts **no question to anyone**: a call that would lead to one (the judge's `ask`, a floor that forces ask: a never-judged action, an unknown tool, a send to an unaccounted recipient, a guard step, no provenance, `AUTO_APPROVE=off`; a decline that still stands; a judge `fix` that may not be applied) is declined back to the run with the fixed text "Not done: not certain enough to act without asking, and background work never asks. Leave it; do not mention it unless it truly matters, then say it in your message as information, not as a question." and audited `background-skip` with the tool and a reason class only (`skip`: judge, fix, redeclined, never-judged, guard-step, untrusted-recipient, inferred-note-read, no-provenance, judge-off). No approval question or waiting message is ever created by such a run; its approver is `NEVER_ASKS` (`approvers.ts`). A judge `fix` that may be applied stays what it is (the call is refused with the judge's hint and nothing runs; the corrected call is judged again). What stays: the never-allowed set is denied for everyone, a payment is refused outright (`deny-payment-unattended`), secrets never go through a chat or a model, and a group's or a friend's look follows the same rule in its own conversation. Code: `permissions.ts` `UNATTENDED_SKIP`, from one fact of the run, `RunKind.attended` (false for every look of the owner, a group or a friend and for everything a look starts, the browse worker included; true for every message turn). A chat turn asks exactly as before. |
| Tasks (own list) | Each conversation's task list is its own data in its own `assistant.db`, so the task tools (`add_task`, `update_task`, `complete_task`, `drop_task`, `snooze_task`, `list_tasks`) are own-data writes that ask no approval in the owner's chat, a friend's own chat or a group (any member). For a list that was brought over from Notion once, a Notion edit of the old task table is told to the judge by a code line and corrected to the task tools (fix), never a second list. **Nothing is deleted:** `dropped` is the end state, the tables refuse a DELETE (and any change to the history) with database triggers, no code path deletes (a test greps `src/`), and every change is an append-only `task_events` row with before and after; forgetting a friend or group deletes the folder and the list with it. **Reminders only message, never act:** code decides WHEN (`src/tasks/remind.ts`, `src/heartbeat/remindtick.ts`, no model): a reminder whose time came is claimed (at most once: the mark and the item's change are one transaction), which makes the conversation's look due at once; the look's prompt carries it as a fact and the look says it in its own words, with no more power than any look (a reminder grants nothing). Only when the look said something (posted, or sent while it worked; a held post counts unless the item is urgent) is it marked told and journaled ("Reminded about ..."): a send that failed is never journaled as done. The one fixed line ("⏰ Call Sam (due today)") is only the fallback when no model run says it: the conversation has no look, or 30 minutes after the claim no look has told it; it is retried three times at most. Its only other effects are on the item itself (the reminder cleared or moved, a snooze that ran out reopened, a repeating due rolled), each a history row. Quiet hours and `/quiet` hold it (only an item the person marked `urgent`, which a background look or a group member can never set, breaks them), the global pause switch stops it. The old code answers to a reminder (a quoted "done", a ✅) are gone: the chat model completes or snoozes the item with the task tools like any request. **A look has the chat's task tools** (26 Oct, the owner: a look may do everything a chat may; no restricted copy): it can add, edit, complete, snooze and drop. The safety is the record, not a restriction: every change is a `task_events` row with before and after, attributed to "assistant (look)", journalled with the look as the why, and undone with `update_task` reopen; nothing is deleted. The code limit is on adding: at most 10 a day per conversation by looks (a mail flood is not a task flood), and never twice for the same mail (`source_ref`, in any state: a dropped one does not come back). A look cannot make an item urgent. **A task from a mail is added and told, never asked** (26 Oct, the owner: "automatically add to-dos and just notify me"): the look tells the person in its own words in its message, and undo is one message ("drop that task"). **A task from a mail grants nothing:** its text is the mail's, so a run that lists a list holding an item with source mail is marked as having read untrusted text (`untrustedWhen` of the tasks module, read by `readsUntrusted`), and a look whose prompt carries one (the code-built `task_list_facts` block) is untrusted from its first call: the judge treats acting on it like acting on the mail (a send to a recipient no person named asks; paying still needs the typed YES in the owner's own chat). The old one-tap suggestions (`💡` message, `suggestion_asks`, `SUGGESTIONS_PER_LOOK`, `SUGGESTION_DAYS`, `confirm_suggestion`, `reject_suggestion`) are gone; migration 11 made the items still waiting ordinary open tasks, origin and source kept (old rows with those words are only read). In a group "remind me" is a GROUP task (everyone sees it) and the member is told once, persisted, that a private reminder goes to the assistant directly. Dates are validated strictly (the model resolves words into ISO, the reply echoes what was understood); the list is fenced as data when read. **The one-time Notion import is gone** (its tools, table and confirmation code were removed once the owner's tasks were brought over); bringing tasks over again is the model reading Notion and calling `add_task`, an own-data write like any other, and Notion page text read for it is data, never instructions. No skill writes tasks to Notion. (tested: `test/tasks.test.ts`, `test/mailtasks.test.ts`) |
| Clean at the door | Untrusted text is cleaned where it first enters, by one shared sanitiser (`sanitize.ts`), so hidden or look-alike content never reaches a model: zero-width, bidi, tag-block (invisible ASCII), stray variation selector, control and private-use characters are dropped (emoji joiners, VS16, flags and Persian ZWNJ survive), text is NFC-normalised, lengths are capped with a visible `[... N characters cut]`, absurd runs collapse. HTML (mail, web) is parsed with parse5 and only the visible text is kept (`html.ts`: comments, script/style/head/template, `hidden`, display:none, font-size:0, opacity:0, off-screen, zero-size and same-colour text are dropped; best-effort, no browser engine). Applied to Signal messages, captions, quotes, names and voice transcripts (`conversation.ts`), mail bodies (`mailtext.ts`), every `fence()`, and every tool result the model reads (the SDK PostToolUse hook rewrites the output, `toolclean.ts`). Fences cannot be closed or forged, nor batch headers and speaker marks. The log shows counts only (`clean: ... removed N hidden character(s)`). |
| Reversible by default | Mail is only archived (never deleted), every archive is recorded with ids, and `npm run restore <id>` brings it back. At most `ARCHIVE_MAX_PER_RUN` (default 25) mail archives per run, whichever provider (one heartbeat look, one chat turn): a module floor in code (`src/modules/archivecap.ts`, asked from `permissions.ts`) counts each conversation, thread or message, a batch counts each one, and refuses the rest with "archive cap reached for this look; the rest waits for the next one" (audit row `deny-run-cap`). There is no keyword blocklist: the classifier decides by intent (what is left to do), and the morning brief lists every archived mail since the last brief, numbered and grouped by sender with its id (`journal` with `kind` `archive`), so you can scan for a mistake and say "restore 3". An unattended run archives only what the judge is sure about (anything else stays in the inbox, no question). Putting mail back in the inbox is free in your own chat (no judge: it only undoes an archive); trash, spam and delete stay never-allowed. |
| Routines (evening wrap, weekly review, and the routine notes people ask for) | The two skills are read-only by their skills' rules and by the same floor as the brief: the expert that runs one has the heartbeat run's tools, so every call passes the floor and the judge exactly as the brief's do, and what the judge would ask about is not done (unattended runs never ask); the skills tell it to change nothing and add no task. Code, not the model, decides when one is due and records that it ran (`routine_runs`), so a routine cannot run twice in an occurrence or be retried more than twice. A routine note (`routine-*.md` with a `when:` line) is a standing instruction of the person whose conversation it is: its look does it with that conversation's own tools, floor and judge, exactly as it would act on the same words in a chat message, and never asks anyone; only the person's own chat turn can write one (an unattended run cannot, and the dream never touches the category), so a mail or web page cannot schedule anything. The only extra permission is the brief's mail: with `BRIEF_EMAIL=on` the Gmail send to `MAIL_SELF_ADDRESS` is free for an unattended run (the address must be the only recipient, no cc, bcc, attachment, draft or thread; `gmailrules.ts`); Mailbird's self-briefing tool can only reach the owner. The scheduled skills are the owner's only: they are private, so a friend's or a group's run is never offered or told one. Tested (`test/routines.test.ts`). |
| Memory | Every run of a conversation, a chat turn or a look, keeps its notes the same way: the SDK's own file tools (`Read`, `Write`, `Edit`), confined by policy to that conversation's notes folder (the owner's: `conversations/owner/notes/`; a group's or a friend's: its own), plus `forget_note`. A change by a chat turn is mentioned in the assistant's own reply and logged (the result of the note write tells the model to mention it, so even a reply that is only a reaction comes with words); a change by a look is logged and in the journal, not announced. **A note written by an unattended run that read mail is no longer marked** (the earlier `origin: inferred` stamp, the "inferred" label in the index, the read-only tools of a look and the judge floor for a wake-up that had read an inferred note are gone; this was the owner's decision): a note planted by a hostile mail is neither prevented nor marked, only findable in the audit trail, the journal and the notes, and it shows in "Changes are visible daily" only when the dream touches it. What keeps this safe is unchanged: notes shape tone, priorities and sorting but never permissions (policy and suspicious-text isolation are code), and the code floor and the approval judge still judge every action of a run that has read mail or a page, whatever its notes say. `MEMORY.md` is code's: regenerated from the notes' front matter after every change (one line per note, expired notes left out, capped by `MEMORY_MAX_NOTES`), so a model cannot hide a note from the index or plant text in it; a write over `MAX_NOTE_CHARS` or a new note beyond `MEMORY_MAX_NOTES` is refused by the same policy. Changes are audited by outcome, never by content. **Changes are visible daily** (`src/memory/learned.ts`): what the nightly dream applied is recorded in code where it happens and told once, the same for the owner and a friend: as a fact in the conversation's next run (`learnedFact`, counted as told only when that run spoke; the owner's brief expert gets it with the look's context and says it in its own words), with the way back in ordinary chat ("forget <note>", "undo the dream" for the night's tidy-up; no reply is parsed by code). Groups are off. **Learning from a 👎 or a correction** (no code path of its own; the helper-model proposal and its code check are gone, this was the owner's decision): a reaction or quoted reply to the assistant's own message is addressed to it in every conversation (a group answers it without the participation gate; one on another member's message is chatter), and the run applies the general learn rule of its persona and saves the rule as a note itself. Such a note is written by the model with **no code check** (no check of category, size or of addresses, links and numbers copied from the reacted message), like any other note a run writes. The reacted message may quote mail, so it is fenced as data in the turn's prompt, and the plain limits on notes still apply (`MAX_NOTE_CHARS`, `MEMORY_MAX_NOTES`, the notes folder). **Notes are never judged, but every action is**: a note cannot widen what the assistant may do, and the code floor and the approval judge still judge every action whatever the notes say. There is no daily cap and no thumbs-up counter any more. |
| Reply drafts | A reply the assistant drafted (in chat or in a heartbeat look; Mailbird or Gmail alike) is a draft in the mail client and is never sent unprompted. Sending it is a chat send: the judge decides from your message and the exact draft, and when it does not clearly say go ahead you are asked, with the draft read back from the mail client at that moment (recipients, Cc, Bcc, subject, new text, attachments), not the model's description. If the draft cannot be read back, nothing is sent. |
| Look versus chat | An unattended look never starts while a turn of its conversation is settling, queued or running, and a written message that arrives while it runs calls it off (unless it waits on an approval, whose answer that message may be; a bare reaction never does), but not if that would starve it: after 2 preempted looks in a row, or when the last full look is older than 2x the look interval (30 minutes at least), it runs to completion (`preemptible`, `src/heartbeat/look.ts`); a look that was told of news and did nothing but read does not post its closing message, so it cannot contradict what chat just did on the same mail. At most `MAX_CONCURRENT_RUNS` (3) background model processes run at once (looks, dreams, quiet compaction); chat turns never wait for a place (`src/core/rungate.ts`, `src/conversation/conversation.ts` lease). |
| Gmail | With `MAIL_PROVIDER=gmail` the connector comes through your Claude login; the same layers apply (manifest, approvals with the real recipients, the sanitiser on every result). Added in code (`gmailrules.ts`, `src/policy/policy.ts`): trash, spam, delete, untrash, attachment content, label deletion and the raw MIME format are denied; any label tool that names `TRASH` or `SPAM` (add or remove) is denied whatever the tool; an archive is only "remove INBOX from a thread"; attachment content is stripped from results before the model reads them. A send, reply or forward always shows its real recipients: a reply that names none is shown with the people of the original message read back from Gmail, a send of a draft with the draft read back, and a call that cannot be read back is not sent. The only mail the assistant may send without asking is the brief to `MAIL_SELF_ADDRESS` (`BRIEF_EMAIL=on`, an unattended run only): the address must be the only recipient, with no cc, bcc, attachment, draft or thread. The heartbeat reads Gmail through a small relay run that may make only the planned calls with exactly the planned arguments; its tool results are captured by code, not taken from the model. |
| Chat only | With `MAIL_PROVIDER=none` there is no mail client in the agent at all: nothing connects to Mailbird, the Mailbird server is added to the hidden connectors so none of its tools is sent to the model, and the mail skills are not offered. This only removes capability; `src/policy/policy.ts` and every approval rule are unchanged, so a mail tool that somehow appeared would still be classified exactly as before. |
| Approval judge | One switch, `AUTO_APPROVE`: `auto` (the default) or `off` (ask about everything that is not a plain read; for debugging). Every tool goes through the same path in every place (chat, group, tenant, heartbeat run and its expert, browse): **code floor, then the approval judge (`src/approvals/autojudge.ts`, `src/approvals/approvaljudge.ts`), then the question on your phone**. The manifest (`src/policy/toolmanifest.ts`) says only what a tool is and where it exists; it holds no per-tool or per-source yes/no. Reads and the assistant's own plumbing (its notes, memory, skills, `send`, `draw`, `voice`, the browser's reads) run without the judge; everything else is judged. The judge is bold: it says `auto` whenever the action follows from your request, your standing task or an obvious routine follow-up and is reversible or of small blast radius, and `ask` only for real ambiguity, money, irreversible loss, exposing something to a third party, or something the content itself asked for. It can only loosen, and only inside the floor. **The floor, in code, whatever the judge says:** the never-allowed set (trading, trash, permanent delete, spam, blocking a sender: one mechanism, `src/policy/neverallowed.ts`, see Tool policy; a draft, a calendar event, a Notion page or a Drive file to the bin is not in it: allowed, judged with care, default ask); a payment is never judged and is approved only by a typed YES in your own foreground chat; payment and login fields are never judged; secrets never reach a chat or the model; a group's or tenant's tools are its capability set and its approvals are asked in its own conversation (an agent-relayed message cannot grant anything); a web page is judged only for a plain https address on a named public host (no IP address, local name, port, login, fragment or long query, since an address can carry data out); the browse guard's address and field checks; calendar writes that name guests (any field that names people, read by its words, case-insensitively: `attendees`, `attendeeEmails`, `addedAttendees`, `addedAttendeeEmails`, `guests`, recipients, `to`, `cc`, `bcc`, e-mail fields; removing people does not count; `src/policy/guests.ts`, which also feeds the judge's "Notifies:" line and the fields a chat reply may never edit), a send nobody can be named for (the draft is read back from the mail client first), a send in a run that has read untrusted mail or pages to any recipient that neither your own message nor the thread being answered names (`recipientsOutside`; a standing task or wake-up names nobody), a wake-up in a run that has read (`read_note`) an `origin: inferred` note (the run records what it read; `JudgeSetup.inferredNoteRead`), whose task the judge then does not take as the person's word, sharing a file and stopping or removing a tenant are never judged and always ask; | Heartbeat run (every conversation's proactive path) | One Haiku run per look (`HEARTBEAT_MODEL`) for the owner, each group and each friend with `wake`, started by code when the model-chosen next look is due and there is something to look at (a mail, calendar or notion capability that is set up, or a note), after `mayRun` (pause, usage-limit cooldown, daily budget; a friend's key and own budget). It is the same agent as the conversation's chat (the same system prompt, tools from the same capability set, the owner's connectors included; the only tools that differ are the rows marked `attended`) in a fresh session every time, and every call goes through the unchanged path: the code floor (never-allowed set, sends, recipients, guests, money and sharing ask), the approval judge, and where that would ask, a skip (unattended runs never ask), with `standing` provenance (the fixed, code-written instruction; no mail or chat text in it) and the untrusted flag once it has read mail or a page. Payment stays a typed YES in the card holder's own foreground chat (a heartbeat run never pays); secrets never go through the chat or the model. A per-run budget (`limits` in the preset, 2 USD and 40 turns, the same for the owner, every group and every friend) apply. Code keeps: the next look clamped to 10..120 minutes (also at night), pause and the spend limit, **quiet hours and a daily cap on unprompted posts** (`src/heartbeat/notices.ts`: inside the conversation's quiet window (`QUIET_HOURS`, else the preset's, in its own time zone) and past `MAX_UNPROMPTED_PER_DAY` (6) a post is held in a small state file, not sent, and goes out as ONE combined message when the window ends or the next day; the run's answer carries an `urgent` flag for what is truly time-critical, which is exempt from both; what the run sends with the `send` tool while it works is not held, but counts toward the cap). Archiving is judged and audited with the mail's id like any call and is reversible (`npm run restore`); there is no special archive floor. Its record, the `looks` table of `instance.db`, holds counts only. A look never starts while a chat turn of the same conversation is settling, queued or running; it is delayed to the next tick, not dropped. |
| Experts (every run's subagents) | Any run, a chat turn or a look, of the owner, a group or a friend, may hand heavy work to an SDK subagent (Sonnet `expert`, Opus `expert-opus`). A PreToolUse hook (the Agent call never reaches `canUseTool`) allows only `expert`, `expert-opus` and `expert-<skill>`, at most 2 per run, no nesting, and denies loading a `delegate:` skill to the run itself. An expert has exactly the run's tools (a skill's variant only the tools its own frontmatter declares) and each of its calls goes through the same floor and approval judge (in a chat turn the same question to the person, in an unattended run the same skip instead of a question) with the run's provenance and untrusted flag; the run's brief to it is shown to the judge as derived data, never as the owner's words. Audit rows carry `agent_type`. The run's per-run budget covers the experts. |
| `send` in a heartbeat run | The run (and its expert) has the normal `send` tool, the same as a chat turn: text, voice, picture or reaction into the conversation the look belongs to and nowhere else (no recipient argument), delivered by the same function as a reply, sanitised, as a notice. It is free (nothing to judge or ask: it reaches nobody the conversation does not already include) and grants nothing; the look's row counts what was sent, and the final answer is told not to repeat it. |
| Meeting prep | Shortly before a meeting with other people (`PREP_MINUTES`, default 15; 0 = off) code claims the meeting and makes the conversation's look due; the look prepares and says it. **Code decides when, the model writes:** any run that reads the calendar (a look or a chat turn) records the upcoming meetings with `note_upcoming_meetings` (own data in the conversation's own `assistant.db`, free, validated in code: a time without its UTC offset, a past, far-off or id-less event is refused), and the tick claims a row in the database BEFORE the look is made due, so a meeting is prepared at most once per event id and start time (a moved event gets one new prep); declined, all-day, private and alone-on-it meetings are skipped by code. **Prep is an ordinary look, not a read-only run:** it has the conversation's normal tools under the normal floor, judge and phone (unattended: what the judge is not sure about is not done, nobody is asked), the normal budget and run gate; there is no separate read-only guard, spend cap or call filter. What it may do beyond reading is exactly what any look may do. **Timing in code:** no prep is claimed between 23:00 and 06:00 (her zone) nor under `/quiet`, it stays open until the night or `/quiet` ends in time (else dropped once too late), it is dropped when less than 3 minutes remain, and it is marked sent only when the look posted or sent (a held or failed post gives it back once). The meeting's title and people are fenced data in the look's prompt; the audit log holds the look's counts and cost only. A friend has it only with her own Google calendar; groups never. |
| `seen_mail` | The heartbeat run's memory of which inbox mail it has worked through: a provider-agnostic tool over the conversation's own bounded id log (2000 ids). It touches only that file, so it needs no judge and no question. Ids it reports as new are committed only when the look ends well. |
| Fixed messages | Approval questions (the exact arguments shown), the draft shown for sending, error, login and usage-limit notices (they must work when the model does not), the voice failure note and "Applied your change" stay code on purpose. |
| Quiet vs pause, and held posts | **`/quiet` is not `/pause`.** `/pause` stops unattended work (looks, wake-ups, the brief). `/quiet 2h`, `/quiet until 18:00`, `/quiet` (until `/unquiet`) only keeps the conversation from being *spoken to* unprompted: its heartbeat posts are HELD exactly as in quiet hours (urgent ones still go through), while chat, the approvals you asked for in chat and the heartbeat's own work carry on. The owner and a friend (in her own chat, for her own conversation) can set it; a group cannot; `/status` shows it. The switch is one row per conversation (the `quiet` table of its `assistant.db`, next to `held_posts`; an unreadable time means NOT quiet, so a bad value never swallows a post). **What was held is handed to the next look, never sent as written** (`src/heartbeat/notices.ts`): when quiet ends (the window or `/quiet`) and the day's cap has room, the conversation's look is due at once and its prompt gets everything held as facts (when each was written, that it was not delivered; nothing older than 36 hours), exactly once; the look says again only what is still true, in today's words. Without a look the held posts are dropped with a journal line. Urgent posts never wait for it. |
| Spend guard | A daily ceiling pauses *background* work (every conversation's heartbeat run); chat stays available. Every run is charged in the spend ledger to its conversation, and the only daily ceilings are the two payers' (`src/core/budget.ts`, `payer.ts`): `DAILY_BUDGET_USD` for the owner's login, which the owner's chat, her background work and every group run on, and `INSTANCE_KEY_DAILY_USD` (10) for the instance key, all friends together (refusal reason `instance-budget`). No conversation has a day of its own. At the login's limit the owner's background work (looks, brief, dreams) and every group's looks stop, a group's addressed chat turn is not answered (checked in `group.ts`, one line a day in the group) and the owner's own chat still answers; at the key's limit every friend's turn and look is refused (`mayRun`) with one fixed line a day, and the owner's login is untouched. One noisy group can therefore use the owner's day and pause her background work until midnight, as the owner chose. Neither is silent (`src/core/capnotice.ts`, each at most once a local day, kept in the `notices` table of `instance.db`, a group under its folder name and never its id): a friend refused for the key's ceiling gets one short fixed line in her chat, an addressed message in a group at the login's limit one in that group (both from the one `refusal` table, `src/tenants/errors.ts`), and the owner a fact for her next run (the limit, no friend's name or words). The heartbeat run also has its own per-run budget and the clamp on how often it looks (10 minutes at the soonest); `npm run heartbeat-report` shows the dollars per day and per kind. **It is never silent:** when the day's budget is reached the owner gets ONE message that day ("Daily budget of $X reached, background work paused until midnight. To lift it today, raise DAILY_BUDGET_USD in .env and restart."), and a group whose addressed message was dropped for it is told once that day in one short line (no terminal, no setting names). Looks that fail are system status and send NO message: a group's or a friend's go to the log and `npm run doctor` only (counts per kind from the looks table, never a name or a word); the owner's own become a code-built FACT in her next look's prompt once they have failed at least 3 times in a row over 2 hours of time the Mac was AWAKE (the monotonic clock: sleep does not count, and a look stopped by a sleep or cut by its ceiling across one is no failure), with the cause and the ONE step to take (`FIXES` in `src/tenants/errors.ts`, which every owner-facing failure notice in chat ends with too; no secret, token or minted link); the look decides whether it is worth one line. There is no "back to normal" message. The budget and the shared-key notices respect quiet hours (held, then delivered with the rest) and the cap does not apply to them. |
| Robust state | State files and notes are written atomically (temp file, fsync, rename, folder fsync) and updated synchronously: no torn files after a crash or power cut, no lost updates between concurrent parts. A file that does not parse is kept (`<name>.corrupt-<time>`), not overwritten by defaults, and an unreadable tenant registry blocks saving instead of erasing every tenant, and pauses the friends while the owner is still served. The dream never overwrites a note that changed while it ran. A failed send is retried and a message lost to a restart is answered at start (within 30 minutes), unless the run had already acted (audit log), in which case only a short note is sent so no side effect runs twice. Settings are validated at startup, so a typo stops the agent instead of misconfiguring it. |
| Conversation databases | Each conversation's small state (session pointer, tasks, held posts, seen mail, `/quiet`, voice-note snippets, a friend's bookkeeping) is one owner-only SQLite file in ITS folder, `assistant.db` (`src/core/convdb.ts`). A store has a connection to its own conversation only, so a lookup cannot read another conversation's rows; the owner's file tools cannot read it (it is in the closed part of `conversations/`, like every file there but the owner's notes, history and the three logs). **A damaged file is not silently emptied:** it is set aside (`assistant.db.corrupt-<time>`, never deleted), chat in that conversation goes on with a fresh session, its background work (looks, the dream, approved archives) is refused until a person looks, you are told once a day, and `npm run doctor` fails with the file. Only the running agent does this (a CLI or the intake page gets an error and leaves the file alone). The mail the agent had already handled is copied into the fresh file and the first look after a reset skips the whole inbox instead of triaging it again; nothing else is replayed from a damaged file (`npm run convdb -- list | accept <convId>`). Forgetting a friend or a group closes its connection, deletes the folder with the database. |
| Retention | A daily job (`src/core/retention.ts`, `src/heartbeat/retentionrules.ts`; 03:30 on your clock, never while your chat is in a turn, no model; `npm run retention -- --dry-run` lists what each rule would remove, `--now` runs them; `RETENTION=off` disables the schedule) removes only what has outlived its window: **rotated** `audit.jsonl.<n>` generations lose lines older than `AUDIT_RETENTION_DAYS` (90; the current `audit.jsonl` is never touched); signal-cli attachments older than `SIGNAL_ATTACHMENT_DAYS` (30; default on only on macOS, 0 turns it off), except a voice note or audio file still in its 7-day look-back in any conversation's `assistant.db` or a file named in a pending approval; only plain files in the `attachments` folder, never signal-cli's keys or config; notes with an `expires:` date in the past (the status notes too) are moved into that conversation's `notes-backup/expired/` and out of `MEMORY.md`, and deleted 30 after their expiry; dream snapshots beyond the newest 7 per conversation (the expired folder is not a snapshot, so undo is unaffected); OpenBao's audit, server and keeper logs are cut at 20; 2 generations kept and raft snapshots beyond the newest 7 go; `instance/shore/` keeps the newest 50; `picture-`, `voiceclip-`, `speech-`, `voice-` and `ted-google-` temporary folders older than 24 are swept. **Never removed by it:** the current audit file, the kill switches (`instance/paused`, `card.disabled`), the payments ledger, the friends list, live notes, histories. `npm run doctor` shows the last run and what it freed. (tested with temp folders and a fake clock) |
| Observability | **One event stream, three records** (`src/core/events.ts`): what the assistant does is told once and written by the sinks, so the records cannot disagree. `logs/audit.jsonl` (the admin's: `npm run report`, `search_logs file=audit`) records every tool decision (ids, never email content; a friend's rows carry no words at all: every field that holds words becomes its length). The **journal** is one line per action (never a read) in the log of the conversation it happened in, with what (the mail by subject and sender), why (code-derived: your message and its time, the approval number you answered, the judge's verdict, a standing instruction; the model's own reason only from a structured field, marked as its own) and how to undo it. Auto-approvals are silent on the phone but are in the journal with the judge's reason and in the audit log. Who reads what: the owner's chat reads the owner's journal (the `journal` tool, `/today`, the daily brief) and the audit log (`search_logs`); a friend's chat reads only her own journal, which holds her words (her audit rows do not), and a group only its own; nobody reads another conversation's. The journal tool is closed to the conversation it runs in (its notes folder decides, never a parameter), fenced as data when read, and kept verbatim at least 90 through log compaction. The `looks` table of `instance.db` is the third record (counts per look, no words). `logs/agent.log` is redacted (numbers, tokens; every console level, not only log and error) and rotated; the audit log has credentials masked too. Child processes that read files or network data other people control (ffmpeg, whisper, Kokoro, signal-cli) start without any key, token or secret variable. `npm run report` lists what was archived (ids to restore) and the judge's decisions, `npm run heartbeat-report` what the heartbeat run did (counts), and `npm run doctor` warns if the heartbeat has stopped ticking. **Bounded growth:** the heartbeat `looks` table is pruned by age (400 days, the retention job); `logs/signal-daemon.log` is rotated (renamed) when over 5 MB only when the app starts a new daemon (a reused daemon keeps writing the same file) and, while any daemon runs (it holds the file open for days), copied aside and cut to nothing hourly (copy-truncate: a line written in the moment between is lost, it is a log); the intake page's `logs/intake-launchd-stderr.log` is trimmed at start like the agent's, and the intake process uses the same redacting logger (`scripts/intake.ts` imports `src/core/log.ts` first). the `payments` table of `instance.db` is a financial record: never rotated and never deleted by default (see "Ledgers and retention" below). The once-per-interval notices (the shared-key problem, a group's error notice) are remembered in the `notices` table of `instance.db`, so a restart does not repeat them. |
| Read access (your chat's file tools) | An **allow-list**, not a deny-list (`src/policy/policy.ts` `readableData`): your chat's `Read` may open only `conversations/owner/notes/` (your notes, `MEMORY.md`), `conversations/owner/messages.jsonl` and `logs/audit.jsonl`, `agent.log`, `signal-daemon.log`. Everything else under the data folder is unreadable (the rest of `conversations/owner/` too: your session, snapshots, search index), so a store added later is private from the day it is written (the old deny-list missed friends' voice-note snippets and cloned reference audio, the friends list with every friend's name and account id, the database `instance.db` (intake marks, notices, spend), `notes-backup/`, the search indexes and every group's folder). A short deny-list (every other conversation's folder, `instance/`, `state/`) stays on top as a second lock. Symlinks are resolved first. `search_logs` has its own fixed folder and is unaffected. Groups and friends still reach only their own notes folder. Writes are never allowed outside the notes. |
| Kill switches | `/pause` (or `/pause 2h`, `/pause until 18:00`) pauses every unattended run (heartbeat looks, wake-ups, the daily brief, browse, group gate looks); your own chat still answers. It is one `paused` row in `instance/instance.db` holding an "until" value (empty, or an ISO time; `src/core/pause.ts`, `src/core/until.ts`), and it **fails safe**: a value nobody can read, or a database that cannot be opened, counts as paused. `/resume` lifts it now (`npm run doctor` warns while it is on). An old `instance/paused` file is read once at start, converted to the row and deleted. `/quiet` uses the same "until" value, one conversation at a time, and fails the other way (an unreadable value is not quiet: a missed post is worse than a dropped switch). `WAKEUPS=off` stops everything that runs by itself; `AUTO_APPROVE=off` makes every non-read tool ask. From your own chat, handled in code before any model sees it and only as the exact message: `/pause 2h`, `/pause until 18:00`, `/pause` (until `/resume`), `/resume`, `/status` (paused, budget today, last look, open approvals, connectors down) and `/stop` or `stop!`, which aborts the conversation's running turn at once (`stopRuns` in `src/run/ceiling.ts`; a friend can stop her own turn and nothing else). Pause and status are the owner's only; a group has none of them. |
| Edits and deletes | Signal lets people edit a message and delete it for everyone. Both are untrusted input like any message (sanitised, fenced as data in the prompt), and both are accepted only from the original's author: the sender is compared with the author recorded in the log (or on the message still waiting); an edit of an unknown message in a group, of a message that is not a person's own (Ted's own, say) or from anybody else is ignored. A message deleted before it was answered is dropped from the queue and never acted on; a deleted message is hidden from the group's context, the gate's tail and the dream, and what was deleted is never evidence for a memory note (an edited one counts once, as edited). Nothing is announced about either, in a group least of all. The logs stay append-only: an edit and a deletion marker are lines of their own, and `search_logs` leaves a deleted message out of its ranked results and shows an edited one with its newest text (the word-for-word `file` search of a background log is unchanged). |
| Message log | `conversations/owner/messages.jsonl` (owner-only; every conversation's own history is `messages.jsonl` in its folder) holds the conversation in the assistant's chat, with Signal timestamps: what the assistant sent, what you sent (voice notes as transcripts) and your reactions. It lets a reaction be matched to its message, lets the assistant search the past, and is what the nightly dream learns from. It is size-bounded (1 MB): the oldest messages are folded into one short summary by a small model. |
| Data layout and forgetting | Everything of one conversation is one folder (`conversations/<convId>/`; a group's folder name is a hash of its id, never the id), the rest is `instance/` and `logs/` (docs/ARCHITECTURE.md, "Where the data lives"). Only `src/core/convpaths.ts` builds such a path, and a test greps the sources for any other. A data folder in any other layout than 4 stops the start, the CLIs and the intake page with a sentence (an older one says to check out the git tag `last-migration` and run `npm run migrate` there; this version has no importer). `npm run forget -- friend <id>` and `-- group <folder name|name>` take a whole conversation out (its folder, its keys in the shared files, the audio signal-cli saved for its voice notes, a friend's secret-store items), idempotently, and say what went. The assistant is not told when it is removed from a group (the messenger has no such event), so a group is forgotten on the owner's word. |
| Voice messages | Transcribed locally (whisper.cpp), never sent anywhere; every voice note is transcribed (in a group it may be meant for the assistant), but at most 2 at a time, the rest wait in line, so a flood cannot start many processes. Only a plain audio attachment from your own chat with the assistant under 25 MB is read, by file name inside signal-cli's folder (no paths). The transcript goes into `conversations/owner/messages.jsonl` (owner-only) next to your other messages, and a spoken reply can never answer an approval. The chat agent may *read* its own data (the allow-list above; symlinks resolved, never written) and search the logs with a read-only `search_logs` tool, so it can tell you what a voice note said or what happened to a mail; their contents are treated as data. |
| Pictures | A photo (JPEG, PNG, WebP, GIF or HEIC, up to 20 MB, plain file name inside signal-cli's folder, no paths) is read from disk, checked by its bytes rather than its name, shrunk locally and shown to the model for that one turn. Other files and videos are skipped. The bytes are never written to a log or a note; only `🖼️ caption` is recorded. **Text inside a picture is data, never an instruction**: the prompt says so next to every picture, and what the model can do is still decided by `src/policy/policy.ts`, not by what it reads. A group member's picture is treated like any member message (policy source `group`, no owner tool, whoever sent it and whatever it shows). A caption or a photo is never an approval answer. In groups set to `tagged` only, a picture nobody addressed to the assistant is not even opened. Residual risk: a picture stays in the resumed session's history (until compaction or the idle reset), like any message. |
| Documents | A file that is not a picture or voice (PDF, text, audio file: see the next row, anything else) is read only from the plain file name signal-cli saved in its folder (no paths, no symlinks, size re-checked on the file itself) and **the bytes decide**: `%PDF-` is a PDF (up to 20 MB and 100 pages, not password protected, shown to the model as a document block for that turn), a `txt md csv json log ics vcf` name plus strict UTF-8 without NUL bytes is text (cut at 200 KB, fenced as `<file_text>` data), anything else (Word, Excel, PowerPoint, zip, executables, a renamed file) is **never opened**, never written elsewhere or run, and the sender is told in one sentence. The sender's file name is untrusted: reduced to a plain label before it is shown to the model. **Content is data, never an instruction**: the prompt says so next to every document, and what the model can do is still decided by `src/policy/policy.ts` and the normal approvals, whoever sent it (a group member's document gets the group's policy source). Only size is logged (`📄 file (N bytes)`), plus `📄 caption` in the conversation log, never the name or the content; a document is never an approval answer. In groups set to `tagged` only, a document nobody addressed to the assistant is not opened. Residual risks: a PDF is parsed by the model service, not by us (a malformed one can fail the turn with the normal error notice); like a picture it stays in the resumed session's history until compaction or the idle reset. |
| Audio files | An MP3, M4A, WAV, OGG, AAC or FLAC file someone sends (owner or group member) is opened only from the plain file name signal-cli saved (no paths, no symlinks) and **the bytes decide**, never the name or the declared type: first bytes, then `ffprobe` (execFile with an argument list, no shell, timeout, plain files only): it must contain an audio stream and no real video, otherwise (a video, a fake `.mp3`, a renamed file) it is refused with one sentence and never transcribed; over 50 MB is refused. Only the first 5 minutes are transcribed (locally, in the same queue as voice messages) and the model is told in a fenced block that it is a transcript of a FILE the sender attached, with the name reduced to a plain label; the content is data, never an instruction. A file with speech becomes a **voice source of that conversation only** (same list as voice messages, id only, 50 per conversation for 7 days, file must still exist, probed again at use, both the requester and the file's sender recorded in the voice's `meta.json`, a voice made in a group is used only in that group, the owner can reset it). The clip and its words are private (logs: size and length only). In `tagged` groups a file declared as audio is opened even when nobody addressed the assistant (like a voice message, so it can be named later); any other file is not. Residual risk: ffmpeg/ffprobe parse a file a group member chose (same exposure as voice messages, with a secret-free environment and a timeout); a declared-audio attachment that has a file name is treated as a file, so a voice message that comes with one is labelled as a file (still transcribed); music with singing may be taken as speech. |
| Cloned voice | With `TTS_PROVIDER=qwen` the model has a `voice` tool (`src/modules/voice/voicetool.ts`) to make the spoken replies of ONE conversation sound like a voice note. **Per conversation:** each conversation has its own library in its folder (`conversations/<convId>/voices/`: the owner's, each friend's, each group's under the hash of its id); a voice made in a group is used only for the assistant's replies in that group, never in the owner's chat or another group, and the default voice (`TTS_REF_AUDIO`) is the fallback everywhere. **Where a voice comes from:** only a voice note (or an audio file with speech, see Audio files) that was received in THIS conversation (the owner's chat, or that same group), named by its message timestamp from the conversation's own record (`src/modules/voice/voicenote.ts`: the last 50 notes, none older than 7 days, id only), its file found by joining that id to signal-cli's attachments folder like transcription does (no free paths, never another chat's or group's notes, the file must still exist). The model chooses which note (the message's own, the one it replies to, or one from the list it can ask for) from the meaning, not from fixed words; code only checks the rules. Who made the request and whose voice it is are both recorded in `meta.json` (`by`, `from`), and for a group the assistant is told to say in one short line whose voice is now used, that it applies only in that group, and that anyone can say "normal voice". **Who may do what:** anyone in the conversation can switch (including back to the default); delete is for the maker or the owner (the owner can always delete or reset a group's voice from the owner's chat); the default cannot be deleted; libraries are capped (10 for the owner, 5 per group). No approval: it is a local, reversible change and undo is switching. Never offered to unattended runs (manifest `only: chat, group`) or without Qwen. **The clip is private data:** converted locally (ffmpeg, whisper), refused when too short, mostly silence, steady noise or without words, cut to the best 15 seconds, stored in the conversation's folder (not in git), read only by the local speech server over loopback with its per-start key (a voice is named by a fixed-shape relative path inside the conversations folder, verified there), never sent anywhere, logged by name, length and size only. Cloning a voice without its owner's consent is the person's responsibility; the assistant says so once, briefly, for the owner's first voice. Residual risk: in a group any member can have the assistant speak in their own voice (or a voice note they quote) in that group; the spoken line names whose voice it is. |
| Spoken replies | By default generated locally (Qwen, or Kokoro when that is not set up), never sent anywhere. Only in the assistant's own chat or a group it answers in, only when the model chooses to (the option is offered with every message when speech is set up; notes can switch it off), only for short answers; anything else, and any failure, is sent as text. Approval prompts are always text, and a voice message can never answer one. What was said is logged as text in the conversation's `messages.jsonl`. **Optional remote speech** (`TTS_PROVIDER=elevenlabs` or `http`, off by default, [REMOTE-TTS.md](REMOTE-TTS.md)) changes the first sentence: the words of each spoken reply, and only those, are sent over HTTPS to a third party or to your own server, so anything Ted says aloud is known to that service. It never receives mail, notes, history or approval questions (those are text). Keys and tokens are read from `.env` only, sent in a header, never logged (errors blank them out) and never committed (`npm run check:secrets`); redirects are not followed; an `http://` address is accepted only for localhost; a missing key stops the agent at start-up. Failures (timeout, HTTP error, quota) are sent as text; the provider is switched to Kokoro only if you set `TTS_FALLBACK=kokoro`. You must have the rights and consent for any cloned voice you use; the reference recording stays on the remote side and no cloned or celebrity voice ships with this repo. |
| Participation gate | A small gate model (Haiku, no tools; notes and log fenced as data) decides whether the assistant should speak on an untagged group message. Its output is untrusted JSON: anything but a literal `act: true` does nothing, and the delay and the next look are clamped in code. What a conversation does on its own when nobody wrote is not the gate's: it is the heartbeat run above. Groups are woken only when the assistant runs on its own Signal account (never on Note to Self, where it would post as you). |
| Group chats | Only in groups you are a member of (checked against the group's member list; if it cannot be checked, no answers, nothing logged and no voice message is even transcribed), a small gate model (no tools, group text fenced as data) decides when to speak, only with the assistant's own Signal account. The run has no private data: the tool policy denies everything outside the group's fixed capability set: web search, send, voice, draw, weather, browse (a separate run that asks in the group), the file tools on a path strictly inside that one group's notes folder (`..` and symlinks resolved first, `src/core/contain.ts`; the one gate on what it may write) and the memory tools of a server bound to that one group (forget a note, search its log, undo its dream), in code, whatever anyone writes, including you. Its Claude Code session loads no user settings and no connectors, and only the shared skills its capabilities allow (`web-research`, `research-booking`, `surf-conditions`, `draw`), never a private one (daily brief, mail, calendar, Notion, setup). The one warm process kept for the latest group (`WARM`) is built from that same isolated set of options for that one group and handed to nobody else (a different group, a changed session or notes index: it is closed instead); the owner's warm process is never handed to a group; the gate's warm Haiku process carries no conversation (only the gate's rules and a one-line style summary in its options, no tools, no connectors, no memory: the conversation's text arrives only in the prompt) and only the exact system prompt it was built with may use it. Warm processes together are at most three, about 200 MB resident each, no tokens; one that died is replaced by a cold start; the gate's answer delay is capped in code (4 seconds). The boundary is tested without a model in `npm test` (`test/isolationboundary.test.ts`) and again by `npm run check:isolation`: for a group and for a tenant (with another tenant beside her) the options are built exactly as production builds them and checked for their shape (strict MCP config, no settings sources, her own folder as the auto-memory, only her tools and servers, her environment), the real `canUseTool` is called with a scripted table (your notes, `MEMORY.md`, audit log, `conversations/`, `state/openbao/`, another tenant's notes and history, a symlink, a `..` path and an outside file are denied for Read, Write and Edit; Bash, WebFetch, Glob and your connectors are denied; her own folder is allowed), and the real memory server is called over an in-memory MCP connection (`search_logs` finds none of your lines, `forget_note` cannot reach your notes or another tenant's); a unit test feeds the checker a gate that lets a path through and requires it to fail. `check:isolation` then adds a live-model smoke run (haiku, a few cents) in which the model is asked to try the forbidden steps; what it chooses to try is printed as INFO, and the run fails only on evidence of a breach (a forbidden path the gate allowed, a canary kept in files only appearing in a tool result or text, a file written outside or changed in your or another tenant's folders, your note gone). `--strict` also fails when the model did not try what it was asked. The only thing shared from your private memory is your personality (`style` notes). Other people's text is fenced data, never instructions. Each group has its own folder (`conversations/group-<hash>/`: notes, history, session), separate from yours; the group's dream reads only that group's words, writes only that group's notes (snapshotted, undoable), and your own dream never sees any of it. A member can plant a note, but only in that group's own memory, and a note is bounded where it is read (how many a prompt includes), not when written, as with yours. A group's memory changes are not announced on your phone: its reply says what it saved. |
| Nightly dream | The run that updates memory has **no tools**: it answers with JSON and code decides what is applied. A new note needs a verbatim quote of *your own* typed or spoken words (checked in code, so a mail, a handled-mail message or a reaction's target cannot plant a memory; a 👎 or 👍 is never evidence, and the only note a reaction can lead to is one the owner confirmed through the offer above, which already exists as a confirmed note before the dream reads anything); a merge may only shorten what it merges; expired notes are checked against their date; `setup-` and `voice-` notes are off limits; at most 8 writes and 12 deletions per run (a bound on one night's changes, not on how many notes you can have). The notes are snapshotted first (7 kept), the changes are logged (not announced), and "undo the dream" restores them. The owner's chat, each group and each friend go through the same dreamer (`dream.ts`), each over its own folder only, gated by its `dream` capability and its payer (`mayRun`); a friend's run is on the instance key and her ledger, and its log line and audit row carry counts, never a note's words. |

Known limits: `signal-cli` stores its keys unencrypted on disk (keep FileVault on); its local socket is unauthenticated (it listens on `127.0.0.1` only); anything running as your user can reach it. Prompt injection cannot be solved, only contained: the design above limits what a hostile email can make the agent do, it does not make it impossible to try.

## Ledgers and retention (instance.db)

- **The spend ledger and the payment ledger are in `instance/instance.db`** (SQLite, WAL, owner-only 0600, closed to the model's file tools like all of `instance/`). They are *ledgers*: a damaged database file stops the start with a clear message and is left exactly as it is; it is never moved aside and started empty (that would reset the day's budgets and forget which payments happened). Restore it from a backup (docs/SETUP.md "Backup").
- **Payments are never pruned** by default. Every status change of every card payment is a row, committed durably (fsync) before the page is told to go on. Only an explicit `PAYMENTS_KEEP_YEARS` (>= 2; 0 = keep for ever) lets the retention job drop *settled* payments older than that; an open or unconfirmed payment is never dropped.
- **Spend rows** older than 400 days and heartbeat looks older than 400 days are pruned by the retention job (`npm run retention -- --dry-run` shows what would go). Forgetting a group or a friend unnames her spend rows but keeps them, so the owner's and the key's day do not shrink.
- **A damaged ledger fails closed, not open.** The start runs a full integrity check of `instance.db`; if it fails the agent runs degraded: chat works, background work, browse and card payments are refused, the owner is told, the file is untouched. See docs/ARCHITECTURE.md "instance.db".
- **Forgetting a friend** unnames her spend rows (the totals stay).
- **The card switch stays a file** (`instance/card.disabled`): it must work when the database cannot be opened. The pause is a row of `instance.db` and fails safe: if the database cannot be opened, background work counts as paused.
