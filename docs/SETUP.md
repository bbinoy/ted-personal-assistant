# Setup

## Status and limits

This is a personal project that runs daily for its author. It works, its safety-critical logic is unit-tested, and it is opinionated. It is **macOS only**, built for **one user**, and it works only while your Mac is awake. Read the code before trusting it with your inbox, and check Anthropic's current terms for using your plan this way.

## Requirements

- **macOS** (launchd supervises the agent; Mailbird is the mail client). Linux would work for everything except those two.
- **Node 24+** (TypeScript runs directly, there is no build step).
- **[Claude Code](https://docs.claude.com/en/docs/claude-code/overview)** installed and logged in (`claude auth login`). The agent uses your stored login so it can reach your claude.ai connectors (Notion, Google Calendar, Gmail…). *Check Anthropic's current terms for using your plan for personal automation like this.* An API key or `claude setup-token` also work but cannot use those connectors (see `HARNESS_AUTH` in `.env.example`).
- **[signal-cli](https://github.com/AsamK/signal-cli)** (`brew install signal-cli`). Either linked to your own Signal account as a secondary device (Note to Self, the default), or, better, registered as the assistant's own account ([SIGNAL-ACCOUNT.md](SIGNAL-ACCOUNT.md)).
- **A mail client with an MCP server**, unless you run chat only (below). This repo uses [Mailbird](https://www.getmailbird.com/); see [Why a local mail client](ADAPTING.md#why-the-default-is-a-local-client). Gmail only: use the Gmail connector instead ([Gmail](#gmail-no-local-mail-client) below).
- Optional: Notion and Google Calendar connected under *claude.ai → Settings → Connectors*, for the task and calendar parts of the brief.

## Install

```bash
git clone https://github.com/bbinoy/ted-personal-assistant && cd ted-personal-assistant
npm install

# 1. Link Signal (scan the QR code in Signal → Settings → Linked devices)
signal-cli link -n "ted-personal-assistant"            # prints a sgnl:// link; turn it into a QR code, e.g.
                                      #   brew install qrencode && qrencode -t ANSIUTF8 '<link>'

# 2. Configure
cp .env.example .env && chmod 600 .env
$EDITOR .env                          # at least SIGNAL_OWNER_NUMBER; set OWNER_NAME / ASSISTANT_NAME

# 3. Mail: make sure `claude mcp list` shows your mailbird server as connected
#    (the agent reads its connection details from the same entry in ~/.claude.json)

# 4. Check everything, then run it for real
npm run doctor
npm run install:launchd               # installs a launchd job; the agent starts now and at login
```

On its first start (an empty data folder) the assistant introduces itself in your chat, in its own words; say "set up" to walk through connecting your calendars and how you write. It archives routine mail from the first look, as your notes say; every archive is listed in `/today` and the brief, and asking Ted brings one back.

Send yourself a message on Signal. Every heartbeat look reviews the whole inbox, read and unread (its last decision per mail is handed to every run, so a mail not listed there is new), so the first look already tidies a big inbox, a batch at a time. The first daily brief is started by the heartbeat run around 07:30 (its rules are in `assistants/ted/persona/heartbeat.md`).

### Choosing a messenger

Signal is the messenger that works, and the default (`MESSENGER=signal`, or leave it unset). No other platform is built (design notes for Telegram, Slack and WhatsApp are in docs/ADAPTING.md). Only the chosen package is ever loaded; a platform other than Signal is installed with `npm install -w packages/<name>`. `npm run doctor` names the active messenger first, then the checks of that platform.

### Chat only (no mail)

Mail is optional. For the Signal chat, memory, wake-ups, the heartbeat run and a daily brief without an inbox, you need only **Claude Code** (logged in) and **signal-cli**: skip the Mailbird step above and put this in `.env`:

```
MAIL_PROVIDER=none
```

What changes: no mail client is started or contacted anywhere; the heartbeat tick only keeps its liveness line; the daily brief has no email step, so the brief the model writes is the deliverable and is sent in chat; the model is not offered the mail skills or the Mailbird tools and is told there is no mail; `npm run doctor` shows `mail: off` as OK and does not look for Mailbird; setup does not ask about your writing style or sent mail; `npm run restore` refuses to run. The default is `MAIL_PROVIDER=mailbird`, which behaves as described everywhere else in these docs.

### Gmail (no local mail client)

If your mail is in Gmail you can skip Mailbird: the assistant uses the Gmail connector of your Claude account, the same way it uses Notion and Google Calendar. Connect Gmail in your Claude account (Settings, Connectors), make sure `HARNESS_AUTH=login`, and set in `.env`:

```
MAIL_PROVIDER=gmail
MAIL_SELF_ADDRESS=you@example.com
```

`MAIL_SELF_ADDRESS` is your own address. It is the only address the daily brief may ever be emailed to (a hard check in code, not a request to the model).

What works:

- **The heartbeat run on Gmail.** It lists the inbox with the Gmail connector like any other tool and keeps its own memory of what it decided about each thread (`mail_decisions`). The few calls code makes without an agent loop (reading a draft back for an approval, `npm run restore`) go through a small relay run.
- **Archiving is always live.** An archive is removing the INBOX label (reversible). `npm run restore <threadId>` puts an archived thread back in the inbox.
- **Drafts and sends.** Drafts (new or in-thread) are made freely. `send_message`, `reply` and `forward` always go through the approval flow, shown with the real recipients (including cc, bcc and attachments); a send of a draft is shown from the draft as read back from Gmail. The approval judge (`AUTO_APPROVE`) may skip the question for a send you asked for in so many words, or one that a standing task of yours explicitly covers; a send decided on the strength of a mail always asks.
- **Never allowed**, whoever asks: trash, spam, delete, the labels `TRASH` and `SPAM` on any label tool, reading attachment content, deleting or renaming labels.
- **Routines** are everything Ted does at set times, planned by code (once per occurrence, retried once if it died, caught up on waking within 4 hours, else skipped and the next message says so). Three are built in, each a skill with a `schedule:` line in its `SKILL.md`: the **daily brief** (every day at 07:30), the **evening wrap** (what got done today, tomorrow, what still waits on you; weekdays 18:30, chat only) and the **weekly review** (wins, what slipped, next week, who to follow up; Fridays 16:30, chat). The wrap and the review only read and message you; switch either off by removing its `schedule:` line in `plugin/skills/<name>/SKILL.md` (a schedule is data; a routine note is off without its `when:` line). To change a time, switch the skill off and ask Ted in chat for your own ("every weekday at 19:00 give me the evening wrap"). Anyone Ted chats with (you, a friend, a group) can ask for their own: "every morning at 8 send Anna a pep talk" is saved as a note `routine-<name>.md` with a `when:` line, and Ted tells you how he read the schedule and when it runs first. `/status` lists every scheduled item with its next and last run.
- **The brief** is a skill the assistant's heartbeat run hands to its expert (at 07:30). With Gmail it goes to chat as the short summary; `BRIEF_EMAIL=on` also emails the full brief to `MAIL_SELF_ADDRESS` (and only there).
- **Reply drafts on Gmail**: a reply the assistant drafts is a Gmail draft; it tells you in chat, and sending it is a chat send you approve, with the draft read back through the connector.

`npm run doctor` checks that `MAIL_SELF_ADDRESS` is set and that the Gmail connector was available in the last run (start the agent once first). The connector's results were written against its published tool descriptions and tested on recorded-shape fake output; watch the first days in `npm run report` and `logs/audit.jsonl`.

### Skills and first-time setup

The skills the agent works with ship in the repo, in `plugin/skills/`, and are loaded straight from there: there is nothing to install or copy. They hold no personal details. What they need to know about you (which calendars to check, where your Notion task list and meeting pages are, how you write) lives in your memory notes, and the agent sets those up with you in the chat.

**Recommended: give the assistant its own Signal account**, so you chat with a contact that has a name and a picture, and see "typing…", instead of with yourself in Note to Self. It takes about ten minutes: [SIGNAL-ACCOUNT.md](SIGNAL-ACCOUNT.md). Everything works in Note to Self without it, and you can switch at any time (set or remove `SIGNAL_ACCOUNT`).

After the agent is running, send it **"set up"** on Signal. It walks you through one item at a time, and you can skip any:

| Item | What it does | Saved as |
|---|---|---|
| Calendars | lists your Google calendars, you pick which count, plus your time zone | `setup-calendars.md` |
| Meeting notes | searches Notion for your meetings database the same way, or creates a page for prep notes | `setup-meetings.md` |
| How you write (mail only) | with your permission, reads up to 15 of your sent mails and describes your style for you to correct | `voice-writing.md` |
| Optional | booking link, topics for the brief's radar | `setup-booking-link.md`, `brief-radar-topics.md` |

**Moving your tasks off Notion (once).** Tasks live in the assistant now (`list_tasks`, `add_task`, `/tasks`); nothing needs setting up. If you keep a task table in Notion, send **"import my tasks"** in your own chat (the owner's chat only). Ted reads the table with your Notion connector (using your `setup-tasks` note if it has one, else it asks which page), maps each row (title, kind, due date, person, open or done, its Notion link) and shows a preview written by code: counts by status and kind, the first 15 rows, what was left out (finished rows older than 30 days by default; say "keep the history" to include them) and any rows it rejected with the reason. **Nothing is imported until you say yes** ("import them" or a thumbs-up on the preview). Then all rows come in at once as your own items, each with a history entry and one journal line ("Imported 42 tasks from Notion"). Running it again only brings rows that are new in the table (each row is matched by its Notion link), so it is safe to repeat. After the import Ted never writes tasks to Notion again; archive the old table when you like. Friends and groups do not have the import (their Notion is not read this way).

**Notion and Google Calendar come through connectors in your Claude account** (Settings, then Connectors). If one is not connected, its tools do not exist, and the agent says so plainly ("Notion isn't connected") instead of asking you to type in what the connector would have told it, and skips that part: tasks and meeting prep without Notion, the calendar review without Google Calendar. Mail triage, chat and writing-style setup need neither. Connect it, message the agent again, and it carries on. `npm run doctor` shows the status of each connector as of the last run.

Until something is set up, the parts of the agent that need it skip it and say so (in chat, it offers to set it up; in the daily brief, a one-line "🛠 Setup" note at the end). `npm run doctor` shows what is missing. To change something later, say "set up my calendar" (or tasks, meetings, writing) again, or edit the note in `conversations/owner/notes/`.

The skills are `daily-brief` (the brief's structure), `mail` (triage and drafting rules for every provider, with `mailbird` or `gmail` holding the tool names and quirks of the one you use, and the Mailbird connection fix), `calendar`, `tasks`, `meeting-prep` and `setup`. To change how a domain is handled, edit the file in `plugin/skills/`. Your own skills in `~/.claude/skills/` are not offered to the agent.

**Keep the agent's view of tools in step with the skills.** To save cost and time the model only sees four Notion tools (search, fetch, create-pages, update-page), and the Gmail, Claude Docs and trading connectors are hidden (Google Drive and Google Docs are visible: add `mcp__claude_ai_Google_Drive,mcp__claude_ai_Google_Docs` to `HIDDEN_CONNECTORS` to hide them again). If a skill you write needs another tool, add it to `NOTION_TOOLS` (or `DRIVE_TOOLS` / `DOCS_TOOLS`) or remove the connector from `HIDDEN_CONNECTORS` in `.env`; otherwise that skill silently fails.

## Browser (forms and bookings)

On by default (`BROWSE=on`). `npm install` fetches the pinned `@playwright/mcp` but does not download the browser (about 100 MB) unless `BROWSE_INSTALL=1` (or `BROWSE=on`) is set in the environment of the install; it only prints a hint. `npm run setup:browse` downloads a headless Chromium into `instance/browse/browsers`, not anywhere global; delete that folder to remove it. Until you have run it (or if the download failed, e.g. offline) the browse tool answers "not set up" and `npm run doctor` says what is missing. The browser presents itself as the plain desktop Chrome of the same version (not "HeadlessChrome"), with the language `en-GB` and this machine's time zone; nothing else is disguised, and sites that block automated browsers (SNCF Connect, Rail Europe, bahn.de, Trainline's search) stay blocked. `BROWSE_BROWSER_PATH` points it at a Chromium or Chrome you already have. `BROWSE=off` removes the tool from every run. A real-world check that costs a few cents: `npm run browse:smoke` (example.com, the httpbin pizza form up to but not including its submit button; `-- submit` shows the approval text a commit step produces, declined; `-- big` a large page). See [SAFETY](SAFETY.md) for what it can and cannot do.

## The secret store (OpenBao)

Your saved details, the card and, later, tokens and API keys live in **OpenBao** (an open-source Vault fork) on this Mac, not in a file next to the code. It is a local service: it listens on `127.0.0.1` only, with TLS that Ted pins, keeps its data in `state/openbao/` (0700, not in git) and writes an audit log whose values are hashed. Ted reaches it with its own token (policy: only `tenants/owner/*`), which is kept in the macOS Keychain. See [SAFETY](SAFETY.md) for the whole picture.

**Install and first setup (once).** In a terminal on this Mac, not through the chat:

```
npm run openbao -- setup
```

This downloads the pinned OpenBao release (2.7.1, Apple silicon, from github.com, SHA-256 checked; `npm run openbao -- install` does only that step), makes the certificate and the config, starts the server and a keeper job as launchd user agents (`com.<you>.ted-openbao`, `...-keeper`; `OPENBAO_LAUNCHD_LABEL` changes the name), initialises it with Shamir 2 of 3, mounts the key-value store, writes the owner policy and token (and the intake page's write-only token, see "The intake page"), and revokes the temporary root token. Then it shows **three recovery shares, once**, and asks you to type the end of share 3 to confirm that you have them. **Record each of the three in a different safe place** (a password manager entry, a paper in a safe), never in this repository, a chat or a note on this Mac; any two unseal OpenBao. The Mac itself keeps shares 1 and 2 in the Keychain (items `ted-openbao-unseal-1` and `-2`) so that it can unseal itself; the screen and its scrollback are cleared afterwards. If you did not manage to record them, stop the jobs (`npm run openbao -- service uninstall`), delete `state/openbao/data` and run setup again: nothing is stored yet.

**After a reboot.** Log in (FileVault needs that anyway). The server starts at login but sealed; the keeper job unseals it from the Keychain within a minute and also renews the tokens. Nothing to do. Check with `npm run openbao -- status` (or `npm run doctor`). If it stays sealed (the Keychain item is gone, or after moving to a new Mac): `npm run openbao -- unseal --recovery` asks for two of your recovery shares at hidden prompts; then `npm run openbao -- setup` again writes the Keychain items and tokens back.

**Backups.** `npm run openbao -- backup` writes a Raft snapshot into `state/openbao/backup/` (mode 0600). It is encrypted by OpenBao, so it is useless without the unseal shares; keep a copy off this Mac (with your normal backup) and keep the recovery shares apart from it. Restoring needs `bao operator raft snapshot restore` and the shares. The audit log (`state/openbao/audit/audit.log`) grows without limit; truncate it now and then while OpenBao is running (`: > state/openbao/audit/audit.log`).

**Settings** (none is a secret, all optional, see `.env.example`): `OPENBAO_ADDR` (default `https://127.0.0.1:8200`), `OPENBAO_MOUNT` (`ted`), `OPENBAO_HOME` (`state/openbao`), `OPENBAO_ROLE` (`ted-owner`), `OPENBAO_KEYCHAIN_PREFIX` (`ted-openbao`). The app token is never an environment variable.

**Good to know.** The Mac's Keychain holds enough shares to unseal, so sealing protects the data directory, backups and a stolen disk, not someone logged in as you. Lost recovery sheet while everything works: run setup on a fresh data directory, or change the shares with OpenBao's `operator rekey`, which needs `disable_unauthed_rekey_endpoints = false` in `state/openbao/config.hcl` for the time it takes (setup rewrites the config). The setup tool's own token (`ted-openbao-operator` in the Keychain) can only ask for a root token and take snapshots; if it is lost, OpenBao's recovery mode (`bao server -recovery`) is the way in. Upgrading OpenBao means changing the pinned version and checksum in `src/secrets/openbaoadmin.ts` (from the release's `checksums.txt`) and running setup.

## Saved details for forms (optional)

The browse worker can fill a form with your name, address, date of birth, passport number or loyalty numbers without ever seeing them. You enter them **in a terminal on this Mac, never in the chat** (the chat is logged and goes to the model):

```
npm run profile -- set email                 # hidden prompt; needs the secret store (previous section)
npm run profile -- set passport --domains sbb.ch,trainline.com
npm run profile -- list                      # keys, kinds and sites; values masked
npm run profile -- domains passport sbb.ch   # change the sites
npm run profile -- delete passport
```

Keys are lowercase words (`first_name`, `email`, `address.street`, `loyalty.sbb`); the kind (name, email, phone, address, nationality, dob, id, other) is guessed from the key or set with `--kind`. Name, e-mail, phone, address and nationality may be typed on any https page; date of birth, ID or passport and everything else are typed only on the sites you list, and nowhere until you do. The data is in the secret store (OpenBao, see the next section; `tenants/owner/profile/<key>`), not in a file next to the code. Card numbers, passwords and bank details are refused here (a payment card has its own command, see the next section). The final submit of a form that used your details always asks you first. See [SAFETY](SAFETY.md).

## Paying with a card (optional)

The browse worker can pay for what you asked it to buy, with **one dedicated debit card**. Use a card that has a low limit and confirms every online payment in its own app (3-D Secure, for example a Wise card); Ted treats it as a standard debit card and its caps are a second layer, not the first. You enter the card **in a terminal on this Mac, never in the chat**:

```
npm run card -- set --currency CHF --label Wise   # hidden prompts: number, expiry, security code, optional name on the card
npm run card -- list                              # the last four digits, caps, whether card payments are on
npm run card -- disable                           # the kill switch (the chat has /card off too)
npm run card -- enable                            # switch on again: only possible here, never from the chat
npm run card -- payments                          # the last payments: merchant, amount, last four, status
npm run card -- clear <id>                        # an unconfirmed payment you checked in the card app
npm run card -- delete
```

The card, including its security code, is stored in the secret store (`tenants/owner/card/primary`), apart from your saved details; nothing shows more than the last four digits. Every payment asks you first on Signal: the question names the shop, where the card is typed, the total with its currency, the last four digits and an id, and **only a typed YES approves it** (a 👍 does not; 👎 or NO declines). The payment is then confirmed in the card's own app, where you should check the amount. Ted's own caps apply too: `CARD_CAP_PURCHASE` (25) per payment and `CARD_CAP_DAY` (50) per day in the card's currency, and 1 payment per task; set a cap to 0 to turn card payments off. Groups and background tasks never get the card. If a shop's payment page cannot be checked (an embedded frame from a site Ted does not know, no clear total), Ted stops and gives you the link to pay yourself. A card run starts the browser with a debugging port on the loopback address. See [SAFETY](SAFETY.md).

## More than one person (optional)

Off by default. With `TENANTS=on` friends can use the same instance, each as a **tenant** with a folder, notes, history and limits of her own, and every tool of the assistant except the ones that are yours alone, running on a **shared instance key** (a separate Anthropic Console workspace key with a spend limit; yours is never used for her). It needs the assistant's **own Signal account** ([SIGNAL-ACCOUNT](SIGNAL-ACCOUNT.md); in Note to Self there is nobody else to talk to). Read "Host admin trust" in [SAFETY](SAFETY.md) first: you can read your friends' files, and you should tell them.

**The one-time steps for friends, in order** (each is explained below or in the next two sections):
1. In the Anthropic Console, a separate workspace with a monthly spend limit and a key in it; `TENANTS=on` and `TENANT_ANTHROPIC_API_KEY=<that key>` in `.env`; the assistant's own Signal account.
2. Only if friends should connect Google or Notion: a public https address for the setup page, from a tunnel (Tailscale Funnel or Cloudflare Tunnel, "The intake page" below), as `INTAKE_BASE_URL=https://<address>` in `.env`; `npm run openbao -- setup` once more (it is a repair: it gives the setup page's token and the app's token the rights for friends' Google and Notion items; nothing stored is lost); `npm run intake` running.
3. Google also needs a Google Cloud project and its OAuth client ("Google for friends"). Notion needs nothing from you but the address above: the assistant registers itself with Notion the first time a friend opens a Connect Notion link ("Notion for friends").
4. Per friend: nothing to prepare and nothing to grant. She writes to the assistant, you say yes in your chat (or write first with `npm run tenants -- invite +15555550114`); she is in. Google and Notion are offered to her as soon as they are set up on the instance (steps 2 and 3). `npm run tenants -- list` and `npm run doctor` show what each friend has and whether she has connected it.

1. In the Anthropic Console create a separate workspace with a monthly spend limit and a key in it. Set `TENANTS=on` and `TENANT_ANTHROPIC_API_KEY=<that key>` in `.env` (not `ANTHROPIC_API_KEY`) and restart. Without the key friends are told the assistant is not set up for them and you get a notice; `npm run doctor` shows whether it is set.
2. Tell your friend to write to the assistant on Signal (the assistant's own account). She gets one fixed line ("I've asked my admin ...") and no model call; what she wrote is held, and you are asked in your own 1:1 chat: "Approve Anna (+49...) as a friend?". Reply yes or no (or react). Yes: she is in and her first message is answered. No: she hears nothing and is not asked about again; `npm run tenants -- pending` lists open and declined requests, `approve <id>` / `decline <id>` do the same from the terminal, `forget <id>` lets a declined person ask again. A request lasts 7 days, at most 10 are open at once, and past that strangers are dropped silently. To write first instead: `npm run tenants -- invite <+number|username>` (or ask in your chat, you are asked first) sends ONE fixed hello to that number or Signal username; when she answers she is a friend with no question.
3. She is now a tenant with every capability except your own (`profile`, `card`, `admin`, `drive`: your saved details, your card, the admin powers and your Drive connectors), as far as they are set up: chat, browse, voice, the loops, weather, draw, and her own Gmail, Calendar and Notion once the instance can offer them. Nothing about her tools is stored and there is no grant or revoke. `npm run tenants -- list` shows everybody with role and the tools each one has now. `npm run tenants -- set-admin owner` restores the admin role if you are ever locked out. The admin role changes only there, never in chat.
4. There is no question about age or country. In her first turn the assistant greets her in its own voice (short, a bit playful), says plainly that it is an AI whose answers may be wrong, that what she tells it and what it notes stays private from other users and from you through it, and the honest limit: whoever runs the Mac could technically read the files.
5. Her runs have the same limits as yours (the preset's `limits`); her spend counts with every friend's on the instance key; past `INSTANCE_KEY_DAILY_USD` (10) a day, and every $5 more, you are warned (nothing is refused), and no conversation has a daily limit of its own. `conversations/friend-<id>/tenant.json` overrides a few things (language, persona, `browse`/`voice` off). Her clock is the Mac's unless you set hers: `npm run tenants -- timezone <id> Europe/Lisbon` (`default` removes it); it decides the time her unprompted looks are told and the day her notes expire on. If a request of hers hits a limit, runs out of credit or is refused, only she is paused (`npm run doctor` shows it).
6. Stop or leave: ask the assistant to suspend her (nothing is answered, data stays) or remove her (her folder is deleted; both ask on your phone). That is the way to stop a friend; there is no per-tool switch. Her own Gmail and Calendar ("Google for friends" below) and her own Notion ("Notion for friends") need her to connect them; your mail and calendar, payments and your saved details are never available to tenants.

## The task page

The agent serves your own task list (never a friend's or a group's) as a read-only web page, rendered by code from the task database; no model is involved. It listens on `127.0.0.1:TASKS_PAGE_PORT` (8788; `0` turns it off) and nowhere else, and starts with the agent. On the Mac, open `http://127.0.0.1:8788/tasks` and pin it. It groups open tasks as overdue, today, this week, later and no date, and refreshes every minute.

For the phone: install Tailscale on the Mac and the phone (same tailnet), then give the page its own tailnet-only https port: `tailscale serve --bg --https=9443 http://127.0.0.1:8788`, and open `https://<machine>.<tailnet>.ts.net:9443/tasks`. Use a port of its own, not a path on 443: if Funnel is on for 443 (as it is when the intake page is public), Funnel covers the whole listener, so a path added there would be public too. `tailscale serve status` must show the 9443 entry **without** "(Funnel on)". **Never use `tailscale funnel` for this page**: that makes it public on the internet. `serve` is reachable only from your own devices.

## The intake page (optional)

Off by default, and only for tenants. A secret never goes through Signal (the chat is logged and goes to the model), so a person who should save a detail (an address, a passport number) or a card does it on a small web page that runs on this Mac: she asks the assistant, it gives her a **single-use link** (valid 15 minutes, and only for that one thing), she opens it in her browser and types the value there. The assistant never sees it, only "stored (12 characters)". The page is a separate process (`npm run intake`, `src/intake/intakeserver.ts`) that listens on `127.0.0.1:INTAKE_PORT` (8787) and nowhere else, writes into the secret store with its **own write-only token** (it can create and update profile and card items and can read, list or delete nothing), and sets no cookies except one on a "Connect Google" / "Connect Notion" page (see "Google for friends": it ties the sign-in to the browser that opened the link). Nothing below installs a tunnel, a domain or a launchd job: those are your steps.

1. **The token.** `npm run openbao -- setup` again (it is a repair; nothing stored is lost) writes the write-only policy `ted-intake` and the token (Keychain item `ted-openbao-intake`; the keeper renews it like the others). `npm run doctor` shows the page's state and checks that the token can write profile, card, google and notion items and nothing else.
2. **The public address.** The page speaks plain http on the loopback address; a tunnel puts https in front of it. Choose one:
   - **Tailscale Funnel** (no domain needed, a stable `<machine>.<tailnet>.ts.net` name): install Tailscale, turn on HTTPS certificates and Funnel for the machine in the admin console, then `tailscale funnel --bg 8787`. `tailscale funnel status` shows the public address.
   - **Cloudflare Tunnel** (needs a domain you own on Cloudflare): `brew install cloudflared`, `cloudflared tunnel login`, `cloudflared tunnel create ted-intake`, `cloudflared tunnel route dns ted-intake intake.example.com`, a `~/.cloudflared/config.yml` with the tunnel id and one ingress rule `hostname: intake.example.com`, `service: http://127.0.0.1:8787` (and the final `service: http_status:404`), then `cloudflared service install` (or `cloudflared tunnel run ted-intake`).
   Only the page's own paths answer; everything else is the same 404. The page sees every request as coming from the tunnel's loopback address and uses the last `X-Forwarded-For` entry the tunnel adds as the visitor (for its rate limits).
3. **The settings.** In `.env`: `INTAKE_BASE_URL=https://<that address>` (https only; an `http://` address is refused for links, except the loopback address with `INTAKE_ALLOW_HTTP_LOOPBACK=on`, which is for tests). Restart the agent. Without `INTAKE_BASE_URL` the tool is not offered and nobody is told anything but "setup link not available yet".
4. **Run the page.** `npm run intake` in a terminal, or as a launchd user agent so that it survives a reboot (it needs your login Keychain, so a user agent, not a daemon). A minimal `~/Library/LaunchAgents/com.<you>.ted-intake.plist`: `ProgramArguments` = `/bin/zsh`, `-c`, `cd <repo> && exec node --conditions=workspace-source --env-file=.env scripts/intake.ts` (put the directory of `node` in `PATH` under `EnvironmentVariables`, as `run.sh` does), `RunAtLoad` and `KeepAlive` true, `Umask` 63, and `StandardOutPath` / `StandardErrorPath` in `logs/`; then `launchctl bootstrap gui/$(id -u) <that file>`. The log has one line per request (method, route kind, status) and never a path, a code or a value.
5. **Friends.** Nothing to switch on: once `INTAKE_BASE_URL` is set, a friend is offered the sign-in purposes (Google, Notion) that are set up. The saved-detail and card forms (`profile`, `card`) are yours alone, like the capabilities of the same name: a friend is not offered them. The page's rules for a friend's card (never a security code) stay as defence in depth.
6. **For yourself.** The intake page never writes your own items (its OpenBao token is denied your folder, because the page faces the internet): set your card with `npm run card -- set` and a saved detail with `npm run profile -- set` in a terminal on this Mac. Your card keeps its security code (see [SAFETY](SAFETY.md)).

## Google for friends (optional)

Off by default. A friend can connect her OWN Gmail and Calendar; her heartbeat run then looks at her mail like yours (docs/ARCHITECTURE.md, "Tenancy: friends and groups"). It needs `TENANTS=on`, the intake page reachable from the internet (the section above) and a Google Cloud project of yours. Nothing is used until you finish all of it; the first live run is yours.

1. **The tunnel and the address.** As in "The intake page": a tunnel in front of `npm run intake`, and `INTAKE_BASE_URL=https://<that address>` in `.env`. Google's redirect needs this public https address; it cannot be a loopback address.
2. **A Google Cloud project.** console.cloud.google.com: create a project, enable the **Gmail API**, the **Google Calendar API**, the **People API** (contacts, for `find_person`) and the **Google Drive API** (read-only file search). Under *Google Auth platform* (OAuth consent screen): user type **External** is fine for friends (an Internal one only works inside your own Workspace); app name, your support address; add the scopes you will use (the defaults of `GOOGLE_OAUTH_SCOPES`: openid, userinfo.email, gmail.modify, gmail.compose, gmail.send, calendar.events, calendar.readonly, contacts.readonly, drive.readonly) or leave Google to ask for them; **Audience: Testing** and add each friend's Google address as a **test user** (up to 100). In Testing status Google expires a refresh token after about 7 days, so a friend has to connect again weekly; publishing the app for production removes that but Gmail's scopes are *restricted* (Google's verification and, for many users, a security assessment). That is Google's rule, not the assistant's; for a handful of friends Testing plus a weekly reconnect (the assistant tells her when the link has stopped working and gives her a new one) is the realistic setup.
3. **The OAuth client.** *Clients* -> *Create client* -> type **Web application**; **tick "Use this client for an AI-powered agent"** (Google asks for it for clients used by agents); *Authorised redirect URIs*: exactly `<INTAKE_BASE_URL>/oauth/google/callback`. Copy the client id and secret into `.env` as `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`.
4. **The server.** The assistant starts `workspace-mcp` (taylorwilsdon/google_workspace_mcp, MIT) for each friend with `uvx`: `brew install uv`. It is pinned by `GOOGLE_MCP_ARGS` (default `--exclude-newer 2026-10-20T00:00:00Z workspace-mcp==2.1.0 --single-user --tools gmail calendar contacts drive`: the version pins the top package and `--exclude-newer`, a `uvx` option, makes uv resolve the dependencies to what existed on the pin date; this reduces the supply-chain risk and does not remove it, the next steps would be a lock file with hashes or running the server under `sandbox-exec`; move the date together with the version, after reading the diff). The server stays running for a friend while her mail is checked (for the heartbeat interval + 5 minutes, at least 20: one resident Python process per friend with Google during the day; set it lower to save memory and pay a restart on every tick). Its token folder is removed when the app stops and any left over by a crash is swept at the next start (`ted-google-*` folders in the temp directory that are older than five minutes, owner-only and real directories). To pin a commit instead set `GOOGLE_MCP_ARGS="--from <the repository's git address>@<commit> workspace-mcp --single-user --tools gmail calendar contacts drive"`. Nothing updates itself; read the diff before you change the pin.
5. **The write and read rights.** `npm run openbao -- setup` again: the intake token may now also create and update `tenants/+/google/*`, and the app's token may read it (and nothing else of a friend's). `npm run doctor` checks the intake token's rights, the server command and each friend's connection.
6. **Nothing to switch on per friend.** Once the client (step 3) and the address (step 1) are set, every friend is offered Google. Optional: `npm run tenants -- timezone <id> Europe/Lisbon` gives her her own clock. Restart the agent. She asks the assistant to connect Google, opens the link, ticks every permission on Google's page ("Google hasn't verified this app" is expected for a Testing app: *Advanced* -> continue) and the page says Google is connected as her address (if that is not her account, she tells you); the assistant tells her. The consent link only works in the browser that opened her link: the page sets a short-lived cookie for that browser and the callback refuses any other, so a consent address forwarded to somebody else finishes nothing. Open the link and press the button in the same browser (with Notion the same).
7. **First days.** Her heartbeat run lists her inbox now and then (about every 30 minutes in her day), tells her what is worth interrupting for, drafts routine replies (she sends them herself, or asks the assistant to in her chat, where she approves) and archives routine mail for real (reversible with `npm run restore`). With `WAKEUPS=off` nothing runs by itself for her. Her own list of mail already looked at is `seen-mail.json` in her folder (`conversations/friend-<id>/`); the audit log has ids and decisions only.
7b. **Contacts and Drive (read-only).** With the defaults above a friend's assistant can look people up in her Google Contacts (`find_person`, the only way her contacts are read: results are fenced, her own account only) and search and read her Drive files (`search_drive_files`, `get_drive_file_content`, `list_drive_items`). Both need the People API and Drive API enabled in the project (step 2) and the scopes `contacts.readonly` and `drive.readonly`; there is no write scope for either and the server's Drive writes and shares are not offered to her run. **A friend who connected before this was added has a grant without those scopes**: `find_person` then says Google Contacts is not available for her (it still answers from her notes) and she gets a new link when she next connects; to switch contacts or Drive off, remove `contacts` or `drive` from `GOOGLE_MCP_ARGS` (`--tools`) or the two scopes from `GOOGLE_OAUTH_SCOPES`.
8. **Take it away.** Suspend her (her tools and her heartbeat look stop at once) or let her remove the app at myaccount.google.com/permissions; clearing `GOOGLE_OAUTH_CLIENT_ID` takes Google away from everybody. Removing her deletes her folder; her refresh token stays in OpenBao until you delete `tenants/<id>/google/oauth` there (it is never used again).

## Notion for friends (optional)

Off by default. A friend can connect her OWN Notion; her Notion tools are Notion's hosted MCP server, reached with her own sign-in, so she chooses in Notion what to share and nothing has to be shared by hand. It needs `TENANTS=on`, the intake page reachable from the internet ("The intake page" above) and nothing else from you: no Notion integration to create and no secret to paste. Nothing is used until a friend has connected; the first live run is yours: check that the registration works, that Notion accepts the redirect address, that a renewal really rotates the refresh token and that the tool names below exist on the hosted server.

1. **The tunnel and the address.** As in "The intake page": a tunnel in front of `npm run intake` and `INTAKE_BASE_URL=https://<that address>` in `.env`. Notion's redirect needs this public https address.
2. **The rights.** `npm run openbao -- setup` again if you have not since this feature: the intake token may now also create and update `tenants/+/notion/*`, and the app's token may read, create and update it (Notion's refresh tokens rotate, so the harness writes the new one back before using it; it can delete nothing). `npm run doctor` checks the intake token's rights.
3. **Nothing to switch on per friend.** Once the address is set, every friend is offered Notion; restart the agent. She asks the assistant to connect her Notion, opens the link, presses Connect Notion, signs in to Notion and chooses what to share; the page says Notion is connected and the assistant tells her. The first Connect Notion link registers the instance with Notion once (dynamic client registration; the client id is kept in `instance/notion-client.json`, which is no secret; if you move to a new tunnel address it registers once more).
4. **What she can do.** Search and read pages she shared; create and change pages and comments (each asks her in her own chat unless the approval judge sees that it follows from her request); moving a page always asks her. Other hosted tools (databases, views, sessions) are not offered.
5. **When it stops working.** Notion can refuse the renewal after a long time unused or when she withdraws the connection (Notion, Settings, Connections). The assistant then tells her in the chat and sends a new link; `npm run tenants -- list` and `npm run doctor` show "needs to be reconnected".
6. **Take it away.** Suspend her (her tools stop at once), or she can remove the connection in Notion. Removing her deletes her folder; her token stays in OpenBao until you delete `tenants/<id>/notion/oauth` there (it is never used again).

## Keep it running

The assistant only works while the Mac is awake: a sleeping Mac stops the heartbeat, cuts off the model call of a look that is running, and scheduled things (the daily brief, a morning message in a group) come late or not at all. `caffeinate` only prevents IDLE sleep; closing the lid on battery power still sleeps the Mac (every 15 minutes or so it wakes for a moment, "DarkWake", without a network). What helps:

- **Plug in power.** `npm run doctor` warns ("laptop can sleep") while the Mac is on battery.
- **A closed lid:** keep the lid open, or use clamshell mode (power plus an external display, keyboard and mouse), or run it on a Mac mini. If you must have a laptop running with the lid closed, switch sleep off yourself: `sudo pmset -a disablesleep 1`, and undo it with `sudo pmset -a disablesleep 0`. It changes a system setting for the whole Mac, keeps it hot and drains the battery, so do it only on power and undo it when you carry the Mac around. The assistant never runs this (or any `sudo`) itself, and `npm run doctor` only reads `pmset`.
- **After a sleep** the heartbeat notices (log line `heartbeat: the Mac slept for N min`), stops the runs whose connections died and starts the looks that are due again after about 20 seconds, a few at a time. The first runs after a wake wait up to 30 s (6 s otherwise) for their connectors, and every wait leaves a log line (`run: connectors ready after ...` or `run: still not connected ...`). A look that hangs is cut after `RUN_MAX_MINUTES_CHAT` (40, like any run) and tried again on the next ticks. `npm run doctor` also warns when several looks failed or timed out in the last 6 hours, and `npm run heartbeat-report` shows the failed and timed-out looks per day.

## Daily use

- **Chat**: message yourself. Replies are formatted with Signal's native styles (bold, italic, strikethrough, monospace).
- **Send a drafted reply**: when the assistant has drafted a reply for you (it tells you in chat), say "send" and approve the question that shows the draft exactly as the mail client holds it, or say what to change.
- **Approve**: reply `yes` / `no`, a sentence, or react 👍 / 👎 on the question.
- `npm run doctor`: health check (tooling, permissions, Signal, Mailbird, login, launchd, skills, heartbeat liveness, spend, recent errors).
- `npm run report [hours]`: what was archived (with the ids `npm run restore` takes), which actions the approval judge let through, how approvals went (local times).
- `npm run heartbeat-report [days]`: what the heartbeat run did: looks, messages by day and at night, dollars, the next looks it chose (counts only).
- `npm run restore <conversationId>`: put an archived conversation back in the inbox.
- `npm test` / `npm run typecheck` / `npm run check:secrets`.
- The data folder (the repo folder, or `HARNESS_DATA_DIR`), all owner-only and git-ignored: `conversations/<id>/` (**one folder per conversation**: `owner`, `friend-<id>`, `group-<hash>`; each holds that conversation's history `messages.jsonl`, its notes, session, pending approvals, search index and cloned voices), `instance/` (what belongs to nobody in particular: the friends list, cost ledgers, heartbeat rows, intake links), `logs/` (`agent.log` in local time, redacted and rotated; `audit.jsonl`, the audit trail; raw crash output, if any, in `launchd-stderr.log`, cut to its last 1 MB at start when it is over 5 MB) and `state/` (only OpenBao and the Qwen voice's Python environment, which are installed software). See [ARCHITECTURE.md](ARCHITECTURE.md#where-the-data-lives).
- **An older data folder** (layout 2 or 3, or `state/`, `memory/`, `tenants/` and the log files by kind) is not moved by this version, which uses layout 4: use an earlier version of the code to move it first. A database file older than the baseline schema (`conversations/<id>/assistant.db` before version 22, `instance/instance.db` before version 4) is refused with a sentence and left untouched. A new, empty data folder just starts. Your `.env` needs no change.
- **Forgetting a conversation**: `npm run forget -- friend <id>` removes a friend and all of her data (the same as `npm run tenants -- remove <id>`); `npm run forget -- group <folder name|name>` removes a group's folder (the names are in `conversations/`, or give the group's name) and its entries in the shared files. Both are safe to run again and say what went. The assistant does not leave a group by itself (leave it in Signal), and it is not told when it is removed from one, so a group is forgotten when you say so. Stop the agent first if the conversation is still active.
- **Memory**: tell it things in chat ("remember that no meetings before 10", "forget the London trip", "what do you remember?"). It saves one markdown note per fact in `conversations/owner/notes/` (the SDK's auto-memory) and tells you on Signal exactly what it saved; say "forget that" to undo. You can also edit or add notes by hand: name the file `<category>-<slug>.md` with a category of `triage`, `people`, `scheduling`, `context`, `brief` or `style` (background jobs only read notes with one of those prefixes), and add `expires: YYYY-MM-DD` to the front matter for a temporary fact. Your writing preferences live here too, e.g. "Never use em dashes"; your daily-brief topics are `brief-` notes.
- **Spoken replies** (optional): the assistant can answer by voice when it fits, in a voice you choose, made locally with [Kokoro](https://github.com/thewh1teagle/kokoro-onnx) (nothing leaves your Mac). Run `scripts/setup-tts.sh` once (about 400 MB; needs Python 3.10+ and ffmpeg), and use the assistant's own Signal account ([SIGNAL-ACCOUNT.md](SIGNAL-ACCOUNT.md)). The model decides per reply whether to speak or write: short conversational answers are spoken, long, detailed or exact ones (times, figures, links) stay text. `VOICE_REPLIES=off` turns it off; `TTS_VOICE` picks the voice. A whole voice reply has one deadline (75 seconds at least): when the voice is not ready in time the same words are sent as text (the log says `voice skipped: took longer than N s, sending text`). A different voice from a hosted service or your own server is possible but sends the spoken words there: see [REMOTE-TTS.md](REMOTE-TTS.md).
- **Nightly dream**: once a day at 04:00 (the preset's `rhythm.dream.hour`, on the first tick after it; `DREAM=off` switches it off), a model with no tools reads what you told the assistant since the last time and proposes changes to its memory notes: new facts about you, people, preferences and projects, merges of duplicates, expired notes dropped. It works silently and logs what it did. See [ARCHITECTURE.md](ARCHITECTURE.md#the-dream). `DREAM=off` disables it; say "undo the dream" to put the notes back.
- **Voice messages** (optional): send a voice note in Note to Self and it is transcribed on your Mac with whisper.cpp (nothing leaves it), handled like typed text (at most 2 are transcribed at once, in your chat and all groups together; more wait in line). The transcript is logged with your other messages in `conversations/owner/messages.jsonl`, and you can ask the assistant what a voice message said (it may read your notes, your history and the three background logs, and search the logs, read-only).
- **Heartbeat run**: every few minutes a free timer checks whose look has come; the owner's look is one run on `HEARTBEAT_MODEL` (default `haiku`): it reads the recent chat, your mail since its last look, the calendar, your tasks and notes, does what is routine within the usual rules (everything that sends, shares or spends still asks on your phone), and messages you only when something deserves it. It chooses its own next look (10 to 120 minutes; about 30 in the day). Quiet hours (22:00-07:00 by default) are its judgement, from the notes and the chat. By default it sends only a handful of messages at night, and only what cannot wait; tell it in chat ("I'm working late, tell me everything tonight") to lift that. `npm run heartbeat-report` shows what it did. It needs the calendar and mail connectors for the parts it reads.
- Tuning: every knob is an env var, listed in `.env.example` (heartbeat interval, quiet hours, spend limit, model). They are validated at startup: a typo stops the agent with a clear message in the log.
- Chat session: it keeps recent history across days (never reset just because time passed) and is compacted when the conversation has grown 100000 tokens beyond its first turn: in the background once it has been quiet for 5 minutes, or right after a reply if it grew 1.5 times past that, the same for your chat and every group, so long conversations stay cheap. Both are optional settings in `.env`.
- Retention: once a day at 03:30 the agent removes what has outlived its window: old lines of rotated audit logs (`AUDIT_RETENTION_DAYS`, 90), signal-cli attachments older than `SIGNAL_ATTACHMENT_DAYS` (30, on a Mac only; voice notes still in their 7-day window are kept), expired notes (moved into `notes-backup/expired/` first), old dream snapshots, big OpenBao logs and old raft snapshots, the shore cache and temporary folders. `npm run retention -- --dry-run` shows what it would remove, `-- --now` runs it. `RETENTION=off` disables it; every window is in `.env.example`. Migration backups are never removed: `npm run doctor` tells you when they are old enough to review.
- Pause: from your chat, `/pause 2h`, `/pause until 18:00`, `/pause` (until you say `/resume`) and `/resume`. It stops all unattended work (looks, wake-ups, the brief, browse) and is kept in `instance/instance.db`; if that cannot be read, Ted stays paused. An old `instance/paused` file is turned into the same switch at the next start and removed. The heartbeat run stops with it. `/status` gives a short summary and `/stop` (or `stop!`) aborts a turn that is running.
- Quiet: `/quiet 2h`, `/quiet until 18:00`, `/quiet` (until `/unquiet`) and `/unquiet` hold what I would post unprompted until quiet ends, while chat and the heartbeat's work go on; unlike `/pause`, nothing stops. A friend can send them in her own chat too. `/status` shows it.
- Quiet hours and caps: unprompted heartbeat messages are held in `QUIET_HOURS` (default from the assistant preset, 22:00-07:00) and handed to my next look when they end (it says again what is still true, in its own words), unless the run marks one urgent; `MAX_UNPROMPTED_PER_DAY` (6) caps them per conversation per day. Spend never pauses anything: when the login's day passes `DAILY_BUDGET_USD` (20), and then every further $5, I tell you once per level per day, in my own words (the same for the friends' shared key past `INSTANCE_KEY_DAILY_USD` and for one friend past the same level); you also hear when background looks keep failing (each notice ends with the one step to fix it).

- Meeting prep: `PREP_MINUTES` (default 15; `0` switches it off) before each meeting that has other people on it (or a video link), your next look is made due and sends one short message with who, what it is about, your last thread and notes with them, what you owe each other from the task list, and the Notion meeting page. It needs the Google Calendar connector (your looks read the calendar and record the meetings; no calendar data, no prep, and `npm run doctor` says so after a day) and the heartbeat running. Whether a meeting is worth a word is the look's call: the meeting facts say who is on it and whether anyone is outside your own e-mail domain; Declined, all-day and private events and meetings with nobody else are skipped; nothing is prepared between 23:00 and 06:00 or under `/quiet` (it waits if the night ends before the meeting, else it is dropped, never held). A friend gets it when she has connected her own Google calendar; groups never.

## Backup

All state is under the data folder (`HARNESS_DATA_DIR`). To back it up, either **stop the agent and the intake page and copy `instance/`** (and `conversations/`), or take a consistent copy of each database while they run with SQLite itself (the instance's, and one `assistant.db` per conversation):

```
sqlite3 instance/instance.db ".backup /path/to/instance-backup.db"
```

Each conversation also has its own `conversations/<convId>/assistant.db` (its session pointer, tasks, held posts, seen mail, `/quiet`, voice-note snippets): `for d in conversations/*/; do sqlite3 "$d/assistant.db" ".backup /path/to/backup/$(basename $d).db"; done` while the agent runs, or copy the folders with the agent stopped. A file copied while the agent runs can miss what is still in its `-wal` file; copy all three files together, or use `.backup`. If the doctor reports a conversation database as damaged, the agent has already set the file aside (`assistant.db.corrupt-<time>`) and started that conversation fresh: restore your backup of it with the agent stopped, then run `npm run convdb -- accept <convId>` (see the doctor line). Without a backup, accepting keeps the fresh start: the mail ids the agent could still read were copied over, and the first look skips what is in the inbox instead of triaging it again. To restore, stop everything and put the file back as `instance/instance.db` (delete any stale `instance.db-wal` and `instance.db-shm` next to it). `npm run doctor` reports the database (WAL, schema version, quick check, row counts).
