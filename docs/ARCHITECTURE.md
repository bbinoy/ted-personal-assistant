**Key design decisions**

- **The heartbeat is not a model, and it sleeps.** Detecting new mail is a plain API call. The model runs only when something changed, and then once per batch, so a quiet inbox costs nothing. At night (22:00 to 07:00 by default) it makes no calls at all and catches up on the first morning tick; urgent overnight mail goes into the daily brief instead of buzzing your phone at 07:00.
- **Permissions are code, not prompts.** Every tool call passes `policy.ts`, which returns *allow* (reads, plus routine writes such as archive and drafts), *ask* (anything outward-facing or unknown, or a send the approval judge did not wave through), or *deny* (delete, trash, spam, block, and the one financial connector the default policy knows by name, which you should extend). A prompt can ask the model to behave; only code can make it.
- **Email is untrusted input.** The classifier sees mail as data, runs with no tools, and returns constrained JSON. Mail containing instruction-like text is classified *alone* (so it cannot influence its neighbours) and can never be auto-archived. Archiving needs the label and the *kind* to agree, and is reversible; the morning brief lists everything that was archived, with the classifier's reason, so a misjudgement is spotted and undone with `npm run restore`.
- **Informational messages are written, not templated.** The new-mail alert and the handler's report are written by a small tool-less Haiku (`src/notice.ts`) from facts code collected (sender, subject, the triage reason; the handler's lines): one mail is one natural sentence, several are grouped as the model sees fit, no header ritual. The facts are fenced as untrusted data; the output is plain text, at most 600 characters, with no number that is not in the facts (draft ids must be copied exactly). Any error, timeout (15 s), empty or failing output sends the old template text instead (`formatAlert`, `formatReport`) and logs one line, so an alert is never lost. About $0.0005 and 3 to 5 seconds per message, only when one is actually sent. Approval questions, error notices and anything with exact data stay code.
- **Observable.** Every decision lands in the audit log, the heartbeat records its last tick (checked by `npm run doctor`), and `npm run triage-check` runs the real classifier on real mail without acting.
- **Three folders, three jobs.** `state/` is bookkeeping the model never reads (seen-message ids, the handler queue, counters, the chat session pointer). `logs/` is the agent log and the audit trail. `memory/` is what the model reads to remember: the last brief and your notes (`memory/notes/`). All owner-only. Reads and writes are small and atomic. Every read-modify-write is synchronous, so two parts of the agent can never lose each other's update, and every write goes to a temp file renamed into place, so a crash never leaves a torn file. The agent has no file tools except in conversations: the owner's chat gets Read, Write and Edit confined by policy to `memory/notes/`, and each group the same inside its own notes folder (`memory/groups/<key>/notes/`); the harness injects everything else into prompts.
- **One authority, the same tools everywhere.** Chat, groups, tenants, the daily brief, the radar, wake-ups, the mail handler and the browse worker use the same tools under the same rules: a code floor, then the approval judge, then the question on the phone. What differs is the context the judge is given (whose message or which standing task led to the call, and whether the run has read raw mail or pages), not the rules. The mail handler, which reads untrusted mail with nobody watching, is judged with that flag set, so a call that a mail asked for asks the owner.

## Memory

Agent memory is usually described in layers. Here is where each one lives:

| Pattern | What it is here |
|---|---|
| **Working memory** | The chat conversation. It resumes between messages, keeps its recent history across days (compaction keeps it small) and is never reset just because time passed (a session the SDK can no longer resume is dropped and the next message starts a fresh one), and is compacted in place with the SDK's own `/compact` once a turn's context passes `CHAT_COMPACT_TOKENS` (150,000 by default; tools and skills alone are about 50k). Compaction normally runs in the background from the heartbeat, once the conversation has been quiet for `COMPACT_QUIET_MINUTES` (5 by default), inside the conversation's own queue (a message that arrives meanwhile waits behind it); only a conversation that grew 1.5 times past the limit is compacted right after its reply. It backs off for an hour if it fails. |
| **Episodic memory** | What happened: `logs/audit.jsonl` (every decision), and the heartbeat digest the daily brief is built from. |
| **Summary memory** | `memory/last-brief.md`: yesterday's brief, so today's builds on it instead of starting over. |
| **Semantic memory** | `memory/notes/`: what you have told it, one markdown note per fact, kept by the SDK's auto-memory with an index (`MEMORY.md`). Plus your own skills and `CLAUDE.md`. |
| **Procedural memory** | The bundled skills (`plugin/skills/`): how each kind of work is done. They hold no personal details; those are `setup` and `voice` notes (semantic memory). |

**Notes** are the SDK's auto-memory. The chat assistant saves one fact per markdown file in `memory/notes/`, with a one-line index (`MEMORY.md`) that the SDK loads into every chat turn. This only works with Claude Code's own system prompt (with a custom prompt the model says "noted" and saves nothing, which we tested), so chat uses that prompt with our persona and rules appended. The category is the start of the file name (`triage-`, `people-`, `scheduling-`, `context-`, `brief-`, `style-`, `setup-`, `voice-`). The background runs do not use the SDK's recall: the harness reads the notes itself and injects the ones a run may see as fenced data, with a standing reminder that notes can never override the safety rules or permit a blocked or approval-gated action. The mail handler gets people, scheduling, context, style, setup and voice; the triage classifier only triage and people; the brief everything. A note with an unrecognised name is shown to chat only, so a mislabelled note fails closed. A note with `expires: YYYY-MM-DD` in its front matter stops being shown after that day. Caps: at most `memoryMaxNotes` notes per run (setting `MEMORY_MAX_NOTES`, default 150) and a fixed limit of 1,200 characters per note. Chat also sees the last brief, as data. What changes between two messages (the last brief, the messages the assistant sent on its own, what is not connected or set up, a friend's mail digest) is not in the chat's system prompt, which changes only with the date, so the warm process and the cached session survive it: it is told at the start of the turn's message, and again only when it changed (`turnContext` in `src/runoptions.ts`, `src/turncontext.ts`).

**Drawing (`draw`, `DRAW=on`, the default)** (`src/drawtool.ts`, `src/svgclean.ts`, `src/svgrender.ts`, `src/shots.ts`, skill `draw`): the model can draw a diagram, chart, flowchart, itinerary or sketch. The in-process MCP tool `draw(svg, caption?)` (manifest row `mcp__draw__draw`, `no` approval, chat and group only; built in `agentrun.ts` wherever `send` is, with the same tell key) takes the SVG as a string (60 kB), has `svgclean.ts` parse and REBUILD it from an allowlist (see docs/SAFETY.md, "Drawings"; pure, no I/O, a short plain message on failure that the model can act on), renders it with `@resvg/resvg-js` (`svgrender.ts`: white background, long side 800 to 1600 px, system fonts with a default family, no script, no network, no files; asynchronous because loading the fonts takes about a second), and keeps the PNG in the conversation's turn folder with `adoptDrawing` under `img1`, `img2`... (the same map, folder, lifetime and `MAX_PICTURE_BYTES` as screenshots; ids are counted per kind). The tool returns the PNG as MCP image content plus the id so the model can look at it and fix its layout once; it has NOT been sent. Delivery is the `send` tool (`picture: "img1"`, optional `caption`), unchanged: `loadShot` accepts `imgN` as well as `shotN`, checks JPEG or PNG magic bytes, and signal-cli takes the content type from the `.png` file. A group's drawing is built by the same code with the group's key and goes only to that group. The skill `draw` (offered with the other skills of the owner's chat, and to a group or tenant whose capabilities include `draw`: see "Capabilities decide the tools and skills of every conversation") says when to draw and how (viewBox, text of at least 14 px, few colours, numbers only from data in the conversation, a sketch and not a photo, emoji may not render). The tool belongs to the capability `draw`, on by default for friends and in groups.
**Weather and spots** (`src/weathertools.ts`, `src/weather.ts`, `src/shore.ts`, `src/kitespots.ts`, skill `surf-conditions`): five read-only tools for the owner's chat (`WEATHER=on`, the default): a forecast (Open-Meteo: wind and gusts in knots, direction, cloud, rain, pressure, daylight hours only, local time, several models side by side if asked), a marine forecast, a place search, a distance, and `get_spot_info`, which gives a launch point's rideable wind directions from a seed list of kite spots (`assets/kitespots.json`) or, for an unlisted point, which directions are onshore, side-on or offshore from OpenStreetMap water outlines (one request per spot, kept in `state/shore/`). The tools report numbers and geometry; whether a day is good, which kite, and whether to message the owner is the model's judgment, guided by the skill. The owner's profile and spots (weight, kites, launch points, hazards) are ordinary memory notes (`context-surf-profile`, `context-spot-<name>`), not code or skill text. The manifest lists the tools as free reads, chat only; they send out nothing but coordinates and a place name.

**Writing** is limited to a chat you started. Policy allows the built-in Read, Write and Edit for chat only on a path inside `memory/notes/` (anything else, `..` and symlinks resolved first, is denied; `isInside` in `src/contain.ts`) and denies them to every other source. There are no write-time limits on notes: no file name pattern, size or count check, no hook. Containment is the only gate; bounds sit where notes are read (`MAX_NOTES_SHOWN`) and in the nightly dream's caps. SDK memory cannot delete, so a small in-process server (`src/memory-tools.ts`) adds `forget_note`, `search_logs` and `undo_dream`, scoped per conversation: the owner's reach the owner's notes and every log, a group's only its own notes, its own log and its own dream. No change waits for approval: every note written, edited or forgotten is mentioned in the assistant's own reply (one message, a few words on what it saved), logged in the audit trail, and, if it answers with only a reaction, announced by a short deterministic notice instead, so a change never goes unmentioned. The assistant is told never to save a note because an email, event or document said so. You can also edit the notes by hand at any time.

**What stays out of memory:** safety rules (policy, suspicious-text isolation) and operational settings (quiet hours, intervals, the spend limit, model, names). Memory is written through a model, so it must never control those.

## The dream

One dreamer for every conversation (`createDreamer` in `src/dream.ts`): the owner's chat, each group and each friend. Once a day, right before the brief starts (as the first step of the brief run, whoever started it; the friends' dreams start with it but the brief does not wait for them), it loops over the conversations whose capability set has `dream` (`allows(conversation, "dream")`, `DREAM=off` takes it from all) and, for each one that said enough since its last dream, runs a model with **no tools**. It is shown that conversation's notes and what its person said and did since the last dream (from its own log: the owner's or a friend's messages, voice transcripts and reactions, or the members' lines of a group; the assistant's chat replies only as context), and it answers with JSON: notes to write or delete. What differs between conversations is data, not code: `src/dreamscope.ts` gives each its notes folder, its snapshots (`state/notes-backup/` for the owner, `backup/` in a group's or a friend's folder), its state file (`state/dream.json`, `dream.json` in the group's or friend's folder: the day of the last attempt and when the last run started) and its note categories from the preset (`notes.dream`, `notes.group`, `notes.tenant`); the payer is `mayRun` (the login for the owner and groups, the instance key and her cost file for a friend: paused, a cooldown, a spent budget or no key means no attempt and the day stays open); the prompt is the one persona template `dream.md` (`{{subject}}`, `{{#group}}`, `{{#own}}`, `{{categories}}`). The thresholds are the preset's `rhythm.dream`: a direct chat is dreamt after 1 new line of its person's, a group after 3 from its members, at most 5 groups a run. It costs a few cents per conversation (Sonnet, one call), a failure never delays the brief and never stops another conversation. Each run writes one audit row, `dream_run`, with the kind (`owner`, `group`, `tenant` with her id) and counts, never a word of a note.

Code, not the model, decides what happens (`planOps`, pure and tested): a new or changed note needs `evidence`, a verbatim quote of the person's *own* words from that conversation (never a reaction's target or an assistant message, which can quote mail); a merge (`consolidates`) may only be shorter than the notes it replaces; a delete needs an expired date (verified) or their own words; `setup-` and `voice-` notes and anything outside that conversation's categories are refused; at most 8 writes and 12 deletes per run; the number of notes is capped (`MEMORY_MAX_NOTES`). Before anything is written the notes are copied to the conversation's snapshots (7 kept); nothing is announced (it is logged in `logs/agent.log` and `audit.jsonl`; a friend's log line has counts only), and "undo the dream" (the `undo_dream` tool of the conversation's own memory server: the owner's, a group's, a friend's) restores the snapshot. `DREAM=off` disables it.

## Tool modules

A tool is a module: one file in `src/modules/`, a plain object (`ToolModule`, `modules/types.ts`), no framework. It declares its `name`, how it connects (`connection`: the SDK's own tools, the owner's claude.ai connector or user-scope server, a server built in this process, or a separate server process; the last two say from the run when they apply, `when(ctx)`: a friend's own Google server process, `modules/google.ts`, and her own Notion, `modules/notionhosted.ts`, exist only for a friend's run whose capability set offers one of their tools), its manifest rows, what runs `free` (or free for a given call, `freeWhen`), what is `untrusted` to read (every `read` row unless the module is `trusted`), whether the whole connector is `never` allowed (trading) or `ownerOnly`, the floor data only it can state (`floor`: a verdict for its tools that can only restrict, actions that are never judged, a veto on the call's arguments, actions whose `fix` verdict is always `ask`, a note for the judge, a different audit row for a denial), the titles of its approval questions, the skills it brings (private, or shared with a capability), the setup questions it needs, and what the model sees of its connector. `modules/index.ts` lists them; `loaded()` is every module without a slot plus, in the `mail` slot, the one `MAIL_PROVIDER` names (Mailbird or Gmail, none for `none`). Always on: send, voice, draw, weather, memory, browse (and the browser it drives), the built-in tools, the tenant administration, intake, Calendar, Notion, Drive and Docs. Which conversation HAS a tool stays the capability set (`capabilities.ts`).

What the code a module wraps does is in `modules/runtime.ts`, bound to the module by its name: the servers it starts (`SERVERS`, built by `serversFor(ctx)` in `agentrun.ts`) and, for the mail providers, the mail client, `npm run restore`, the start-up wiring and the doctor check (`MAIL`). The split is deliberate: the declarations are read by almost everything (the manifest, policy, the judge, skills, notes, connectors, the prompts) and so import nothing of the application; only the places that start things import `runtime.ts`.

What a module may not do: decide policy. The never-allowed set, the capability sets of groups and tenants, the approval path (floor, judge, question), the judge prompt, payments (typed YES), the address checks, the browse guard, the per-conversation approvers, the tenant audit and the isolation stay central code. A module only adds rows and floor data that central code reads, and floor data can only restrict. The floor rules of a mail provider that is not loaded (the Gmail rules under Mailbird) keep applying for that reason.

To add a tool: write `src/modules/<name>.ts` (rows with the `cap` that gates them, `free` if they only read, the skill it needs in `plugin/skills/`), add it to the list in `modules/index.ts`, and, if it starts a server, add the factory under the same name in `runtime.ts`. A tool no module lists is unknown: it asks and is never judged. `test/modules.test.ts` checks the shape and `test/manifestrows.test.ts` pins every row.

## The assistant preset

What makes the harness "Ted, the personal assistant" is data in a folder, `assistants/<name>/` (default `ted`; `ASSISTANT_PRESET=<name or folder path>` picks another, read once at start-up), loaded and checked by `src/preset.ts` (a leaf that imports nothing of the harness, so `settings.ts` can read it):

- `preset.json`: the **rhythm** (heartbeat interval and quiet hours; the brief's skill, start hour, backstop hour and attempts; the radar's skill, whether it is on and its interval; whether the dream runs), the dream's thresholds (`rhythm.dream`: new lines per kind, groups a night), the **note categories** (all, those the owner's dream may touch, those a group keeps, those a friend keeps), the **profile table** (turns, budget and note categories of the chat, brief, radar, background, group and mail handler runs) and the assistant's own **skills** (`core`, with the ones the doctor requires, and the `order` of the owner's list). Each environment variable of the rhythm (`BRIEF_START_HOUR`, `RADAR_MINUTES`, `HEARTBEAT_MINUTES`, `QUIET_*`, `PROACTIVE`, `DREAM`, ...) still overrides its default.
- `persona/<prompt>.md`: the words of every prompt (the chat, a group, a tenant, the brief, radar, handler and background runs, the dream, the triage and the log summary, the wake-up's voice sentence, the gates' default rules, the personality and the shared rule blocks). A text is a template: `{{name}}`, `{{#flag}}...{{/flag}}` and `{{^flag}}...{{/flag}}`; the names each text may use are listed in `PROMPTS` (`preset.ts`), and `src/persona.ts` fills them in with what only code knows (names, folders, the date, the note categories, and which tools the run really has: a group's and a friend's prompt flags come from their capability set). A text that names anything else, a missing file, a number out of range, a category that is not declared or a wake-up skill that is not a core skill stops the start with a message naming the file and the problem (`test/preset.test.ts`).
- A preset may begin with `"extends": "ted"` and change only some keys and some texts; the others are the base's.

What stays in code, because a preset must not be able to loosen it: policy, the approval path (floor, judge, question), isolation, payments, the capability table, the heartbeat's small-model triage gate, the rules block every run gets (approvals, untrusted content, blocked tools, web search, the browse tool, honesty: `rules` in `persona.ts`; only its sentence naming the assistant's skills is the preset's), the policy source of each profile and the browse worker's limits. Enforcement never reads a prompt, so a preset changes how the assistant talks and when it wakes up, never what it may do. The loops still run per conversation by capability; a preset does not add owner-only loops.

## The tool manifest

`src/toolmanifest.ts` is the one table of every tool the model might get: the union of the rows of the loaded tool modules. Each row names the tool, its provider (`mailbird`, `gmail`, `calendar`, `notion`, `drive`, `docs`, `builtin`, `memory`), a generic action (`read`, `draft`, `send`, `forward`, `archive`, `calendar-write`, `share`, ...), the capability that gates it (`cap`, by default its provider's: `mail`, `calendar`, `notion`, `google`, `chat`, `weather`, `draw`, `voice`, `browse`, `intake`, `admin`) and, optionally, `only` (the sources the tool exists for: the browser's tools in the browse run, and the tools that need a conversation to exist in, such as `send`, `draw`, `voice` and the note files; elsewhere it is denied). A row holds no approval flag and no per-source table. `isFree` says whether a tool runs without the judge (a read, or the assistant's own plumbing); every other tool, and a tool that is not listed unless its name is a read verb (`list_`, `get_`, `search_`, ...), is not free and goes to the judge or the owner. So the same rule holds for every provider and every place: whatever has the action `send` is judged against its provenance, whether it is Mailbird's `send_message_now` or the Gmail connector's `send_message`. The Gmail module is loaded only when `MAIL_PROVIDER=gmail`; the rows of a provider that is not loaded do not exist, so one provider's rows never classify another's tools.

What stays code, because no judge may override it: the never-allowed set and the `file://` rule (`policy.ts`), the path containment of the file tools (a path inside the notes, or the data folders to read), and the vetoes before the judge (`autojudge.ts` reads them from the modules: no calendar attendees, a plain https address for a page, a named recipient for a mail). `hiddenTools` and the `MAILBIRD_TOOLS` / `NOTION_TOOLS` settings are about what the model SEES, not what needs approval, and stay settings.

With `MAIL_PROVIDER=gmail` the heartbeat's mail source is `GmailMail` (`gmail.ts`), which has Mailbird's shape (`inboxes`, `call`, `close`) over the claude.ai connector, so the rest of the heartbeat is unchanged. The connector is reachable only inside a model run, so a small Haiku relay makes exactly the planned calls (code refuses any other) and the tool results are captured raw from the PostToolUse hook; this costs one small model call per tick. The background handler works with Gmail too: it drafts with `create_draft` and the draft is shown on Signal like Mailbird's.

`mailView(tool, input)` normalises an outgoing mail call of any provider into one view, `{ action, to, cc, bcc, subject, body, hasAttachments }`: Mailbird's `send_message_now` from the draft read back, `forward_conversation`, the reply and draft tools from their inputs, and the Gmail connector's `send_message`, `reply`, `forward`, `create_draft` and `update_draft` from theirs. The approval text (`format.ts`) and the text the judge sees are both built from it, so approvals look the same for every provider and always show Bcc and attachments. A call that cannot be viewed (a send of a draft nobody could read back) is refused rather than approved blind.

## The browse sub-task

`browse(task)` is an in-process MCP tool (`mcp__browse__browse`, `createBrowseServer` in `src/browse.ts`) that the owner's chat, an owner background run and a group run get when `BROWSE=on` (the default). Calling it starts a **separate run** with the profile `browse` (`PROFILES`, policy source `browse`): a fresh session, `strictMcpConfig`, no user settings, plugins or skills, built-in tools `["WebSearch"]`, and one MCP server, the browser (`@playwright/mcp`, version pinned in `package.json` and `PLAYWRIGHT_MCP_VERSION`, run from `node_modules` with `--headless --isolated`; the Chromium it needs is downloaded by `npm run setup:browse`, which `npm install` also runs, into `state/browse/browsers`). The run is the same code for the owner's chat, a wake-up and a group (`browseRunner` in `agentrun.ts`); only the approval callback differs (the owner's chat approval, or `approveIn(groupId)`: the question is posted in that group); the limits and the guard are the same.

What code still decides and what the judge decides: code alone decides the addresses (plain http(s), public names, public DNS answer, no private, link-local or metadata range, redirects withheld), which refs exist, the caps (turns, USD, minutes, `BROWSE_MAX_COMMITS`, six refused calls) and that payment and login fields (and Luhn-valid numbers) always ask the owner, never judged, with the value kept out of the question and the audit. The classifier only spots commit-like steps (`classifyClick`, Enter/Space after typing, typing with Enter, accepting a dialog); each is sent to the approval judge with the page, control, form, entered values and task, and the judge says `auto` (read-only: search, filters, navigation, cookie banners) or `ask` (books, buys, pays, registers, subscribes, sends, submits personal details, accepts a price or terms); a judge failure asks the owner (in a group, the group). Every judged step has a `judge-*` audit row with its reason. 

Where each rule lives: the manifest rows (`mcp__browser__browser_*`, `only: ["browse"]`: reads and clicks are free; navigate / type / fill_form / select_option and dialogs are judged); `BrowseGuard.decide` (a `CallGuard` handed to `makeCanUseTool`, `permissions.ts`) for what a table cannot say: it answers deny, allow, ask (a commit step, with the question text built by code) or defer (leave it to the manifest and the judge); the pure rules in `src/browserules.ts` (addresses, snapshot parsing, commit classifier, payment fields, Luhn); the `PostToolUse` hook in `buildOptions`, which lets the guard read the page view in (the server writes the snapshot of a navigation or click to a file and only links it), cut it and remember its refs before `toolclean` runs. Point clicks (`BROWSE_VISION=click`, `browsecdp.ts`): the lookup picks the tab by the page address of the last page view (`pickPage`), an empty hit ("No node found") or a non-interactive surface is a plain click, and what stays unresolved is a `judge: true` commit step (a failed lookup is retried once). **Plan approvals carry forward:** `makeApprove` (`approvalask.ts`) returns the question as shown with the owner's decision (`Decision.question`); `makeCanUseTool` hands it to `GuardDecision.approved` after a yes (not after an edited approval), and the guard keeps the last one in memory (`BrowseGuard`, id/time/site/step/control, 10 minutes, dropped on a site change and in `endRun`). For the next judged commit step `BrowseGuard.offer` decides in code whether it is passed on as `GuardDecision.carried` (same site, in time, no card in progress, no pay-like label, no total on the page; never for `judge: false` steps), `judgePrompt` (`autojudge.ts`) adds it as a fenced `approved_plan` block with the instruction to answer `auto` only for exactly what it describes (the judge system prompt is unchanged, so the pinned default prompts do not move), and `permissions.ts` audits a resulting auto-approval as `covered-by-approval`. Everything that comes back to the caller passes `sanitizeResult` and a fence. Entry-tool results are untrusted data; the run's own system prompt (`browseSystem`) says so too, but only code enforces anything. Measured: a navigation page view is 0.9k to 24k characters (the cap), a three-step form fill costs about two cents on Sonnet, and the whole run starts in about 3 seconds. The browser server's real tool names and parameters (`target`, not `ref`) are in the guard; a pin bump needs `npm run browse:smoke` and a look at `isAllowedBrowserTool`.

**Saved details (the profile).** `src/profile.ts` holds the owner's non-secret details as one OpenBao item per key (`tenants/owner/profile/<key>`, via `ProfileStore` over `TenantSecrets`, see Secrets below); `src/profilecli.ts` / `npm run profile` is the only way in (hidden terminal prompt). `browse()` loads it for the owner's chat run only (`ctx.mode === "owner"` and `ctx.key === OWNER_KEY`; a group or wake-up gets none) and hands it to `BrowseGuard`, which tells the worker's prompt the key names (`profileKeys`). There is no extra MCP tool: the worker's `browser_type` / `browser_fill_form` text `{{profile:KEY}}` is the request (the browser server is a separate process, so only the guard can turn it into a typed value). `decide` runs `fillFrom` (https, page address equals that of the last page view, no frame ref, field role and name fit the key's kind, not a payment or login field, registered-domain binding from `src/domains.ts`) and returns `defer` with `input` = the call with the real value, which `makeCanUseTool` now runs in every allow path (judge auto, owner yes); the description for the judge and the owner has the key only. `shape` drops the server's "Ran Playwright code" echo, says `Filled “label” from the saved profile`, and `redact` cuts every typed value (and the filled field's line) from this and later page views. After a fill `commit` always asks the owner (`judge: false`) and `commitText` lists labels, keys, masked values and `findTotal` (`browserules.ts`); `questionfacts.ts` makes the host, keys, masked tails and total required in the model's question.

**Secrets (OpenBao).** `src/openbao.ts` is a small client over `fetch` (undici's, to pin the certificate): KV v2 read, write, delete (the metadata delete, all versions) and list, plus health, capabilities and token lookup for the doctor; loopback addresses only, validated path segments, a timeout, an optional in-memory cache (`OPENBAO_CACHE_SECONDS`) emptied by every write, and `BaoError`s with canned messages (the server's own words are kept apart in `detail` for the setup tool's terminal). `src/secrets.ts` adds the tenant: `TenantSecrets(bao, tenant)` reaches `tenants/<tenant>/<kind>/<name>` and nothing else, kinds are `profile` and `card`, and `card` is refused unless the tenant is in `CARD_TENANTS` (the owner). `appBao()` takes the token from the Keychain (`src/keychain.ts`, the `security` tool by arguments and stdin) and the pinned certificate from `state/openbao/tls/cert.pem`. The stores (`ProfileStore`, `CardStore`) turn every failure into a `ProfileError` and callers fail closed (`loadProfile` and `openCardAccess` report the reason to the audit and give no profile or card). `src/openbaoadmin.ts` is the server side, used by `scripts/openbao.ts` (`npm run openbao`): the pinned download and its checksum, the self-signed certificate, the config (Raft, loopback, TLS 1.3, a declared file audit device), init with Shamir 2 of 3, unseal from the Keychain, the mount, the owner policy and the two tokens, a transient root token that is revoked at the end, snapshots and token renewal; `src/openbaoservice.ts` renders and loads the two launchd jobs (`launchd/openbao.plist.template` for the server, `launchd/openbao-keeper.plist.template` for the keeper that unseals and renews every minute). Tests: `test/fakebao.ts` is an in-process fake of the HTTP API (it enforces the same tenant prefix rule), and `test/openbao-e2e.test.ts` starts a real throwaway OpenBao from the installed binary with fake values (skipped when none is installed).

**Card payment (`src/card.ts`, `src/cardcli.ts`, `src/paymentrules.ts`, `src/payments.ts`, `src/browsecard.ts`).** The card is one OpenBao item (`tenants/owner/card/primary`, `CardStore` over `TenantSecrets`; `loadProfile` never returns it, the client never caches it, and `TenantSecrets` refuses a card for any tenant but the owner), entered only by `npm run card`. `browse()` opens a `CardAccess` for the owner's chat run only (`ctx.mode === "owner" && ctx.key === OWNER_KEY`, kill switch off, caps above 0): the card's label, last four and currency (the card is opened and dropped to read them), a `load()` that decrypts it again, the kill switch, the ledger and the caps. The guard holds that handle, not the card. The worker types `{{card:number|expiry|cvc}}` through `browser_type`; `cardField` checks the page (https, a whole page view, an empty enabled field of that kind, order), `payTarget` finds the shop and the payment hosts (the run's chain of registered domains, how each page was entered, and for a field under an `iframe` node the browser's frame tree through `FrameProbe`/`cdpFrames` in `browsecdp.ts`, judged by `frameVerdict`), and the first detail returns an `ask` with `payment: true` and a `resolve` callback. `makeCanUseTool` skips the judge for it, passes `{typedYes: true}` to the `Approve` callback, and calls `resolve()` only after the yes: that is where the card is decrypted, the approval is stored (`PayRun`, ten minutes, one use) and the real number goes into the call. Later details are `allow` decisions with their own `resolve`, bound to that approval. `approvals.ts` marks the open question `typedYes`: the fast path, the judge's `approve` and reactions are checked against `isTypedYes`; `makeApprove` refuses the ask for a group or background scope. `payClick` re-reads everything from the last `browser_snapshot` and sets `attempted` before the click runs; `finishPayment` settles the ledger and gives `browse()` the note that opens the worker's answer. For a card run `browse()` also allocates the browser's debugging port (`freePort`), and `buildOptions` sets `persistSession: false` for the browse source. The kill switch is `KillSwitch` (a file); `cardCommand` answers `/card off` in `conversation.ts` `ownerTurn`, before any model.

## The approval judge

Many approvals are redundant: you tell the assistant "put pottery in my calendar tomorrow at 15:00" and it then asks you to approve exactly that. Every tool call, in every place (chat, group, tenant, mail handler, brief, radar, wake-up, browse), goes through one path in `permissions.ts`: the code floor (`policy.ts` classify: the never-allowed set, the capability set of a group or tenant, the notes path; `autojudge.ts` `isJudgeable`: what may never be judged), then the approval judge, then the question on your phone. The manifest (`toolmanifest.ts`) holds no per-tool or per-source yes/no; a read or the assistant's own plumbing is `free` (`isFree`), everything else is judged. `src/autojudge.ts` builds the judge's input and `src/approvaljudge.ts` holds its prompt (one small Haiku, one warm spare). The input carries a PROVENANCE block that code writes (`provenanceFor`, from `RunOptions.provenance`): your message with the recent ones, or the fixed task text of the mail handler, the brief or the radar, or a group or tenant member's message, or a scheduled wake-up (`derived` by the gate: a task selected from the conversation's own notes, the person's standing instruction acted on later, judged like a chat message from the same person), or the browse worker's task when no parent provenance exists (written by the assistant, labelled so), plus the flag `untrusted_input_in_run` (set for the mail handler and the browse worker, and for any run once it has read mail, an event, a Notion page, a Drive file or a page, and then for the rest of that chat session). With no provenance on record the action is asked. The judge never sees a mail body or a page, only code-rendered arguments. It answers `auto`, `ask` or `fix` as constrained JSON, and anything else, a timeout or an error is `ask` (`fix` also needs a non-empty reason). `fix` means the arguments are wrong, not that the action needs permission: `makeCanUseTool` denies the call with the reason as data ("Not run, nobody was asked: ...; correct the arguments and call the tool again, once"), asks nobody and never sets `updatedInput`, so the corrected call goes through the whole path like any new one. The counters live in the closure of the run: 2 per tool, none for identical arguments, and `mayFix` downgrades payments, mail sends, replies, forwards, deletes, shares and guard-built steps to `ask`; the audit row is `judge-fix`. For calendar writes the judge also reads a code-built "Notifies:" line (guests and notification fields in the call). `AUTO_APPROVE` is the one switch: `auto` (the default) or `off` (the judge is not called and everything that is not free asks). Every auto-approval is logged (`auto-approved`) and listed by `npm run report`.

## Approvals

There is one approval flow, conversational. It follows the owner's principle "model judgment over hard code": the question is written by a model, the reply is read by a model, and everything is audited. Sends and forwards are included.

**What code still decides (the invariants).** Only a message that arrives after the question, or a reaction on it, can resolve an approval. A 👍 / 👎 on the question and an exact plain yes / no that unambiguously targets the single open approval (it is the only one in that conversation, or the reply quotes it) are matched by code. An edit is applied only through the calendar allow-list (`applyChanges`, never recipients), so the arguments that run are the ones asked about or an explicitly allowed edit of them. Edits of a message and picture captions never answer. Everything else is the model's reading, with no length rule and no word lists.

- **Reading the reply.** Every other message goes to the one Haiku judge (task `answer`, `src/approvalmodel.ts`, prompts and strict parsers in `src/approvalprompt.ts`) together with ALL open approvals of that conversation (an id, who asked, how long ago, the exact question text that was shown, the arguments where an edit is allowed), the last few chat lines of the owner's chat (none in a group) and whether the message quotes an approval or was a voice message. The judge names the approval(s) it answers and the outcome: `approve`, `decline`, `approve_modified` (the calendar allow-list), `other` (a condition, a partial answer, "later", a hedge, a question, sarcasm: NOT approval, the approval stays open and the judge's short natural reply goes to the owner), `unrelated` (an ordinary message: it flows to the assistant as always), `unclear` (it asks which one), or `multi`: one reply that settles several approvals ("yes to both", "yes to the first, no to the second"), with an approve / decline / other verdict per approval id. Code applies each part to its own approval; a part that is not a plain yes or no stays open, and the reply asks only about those. An answer with an unknown or duplicate id, a wrong-task answer or a malformed one is unusable. An approval that ended while the judge thought is skipped.
- **When the reading fails.** A judge error, timeout or unusable answer approves nothing. The owner's words go back to the agent as the tool result ("the approval could not be confirmed: ... Nothing was executed. <owner> had replied: ..."), so the agent decides itself whether to ask again, rephrase or drop the action. The same goes for a question that could not be written. The agent may ask about the same exact call at most twice after failures (`MAX_FAILED_ASKS` in `permissions.ts`; then it is told not to retry), and an approved call is still refused if repeated within 30 minutes. Every failure is audited.
- **Voice.** A voice message may answer an approval (its transcript is a message like any other); the judge is told it is an automatic transcript, so words may be misheard, and asks again when it is ambiguous for a risky action.
- **One approver per conversation.** The same code for every conversation, scoped by `Conversation.key` (the owner's chat `owner`, a group id, `tenant:<id>`). `src/approvers.ts` is the one place that decides where a question goes: into the conversation that triggered the action (the owner's chat for her turns and her unattended runs, a group in the group, a tenant in her own chat), registered with `permissions.ts` `setApprovers` and used as `approveIn(key, { background })`. A tenant who is gone has no approver (nothing is sent, never the owner's chat). An approval carries its conversation and an answer must come from the same one, so the admin cannot answer a tenant's question and any member of a group may answer the group's (message, quoted reply or reaction). The audit records who answered (`by`). Which tools a group run has is unchanged (`policy.ts`): today none of them asks, so this is plumbing for later and widens nothing.
- **Writing the question.** ONE model call (task `write`) always writes the question, in the owner's language, with no code template; it gets the tool, the exact arguments, the code-rendered details (ground truth, never sent), the owner's recent messages and a list of REQUIRED strings. Code then checks (`src/questionfacts.ts`, no second model call) that every email address and URL in a structured field, every id, title or subject, the time zone, each start and end time (HH:MM) and date (D Mon), up to five amounts and the words Cc / Bcc for such recipients appear in the question verbatim, and that no address or URL appears that the arguments do not contain. If the check fails, or the call fails, no question is sent (no card, no retry): the failure goes back to the agent as above. What the check cannot catch is what the question says about the action in words ("replace" for "add", "send" for "draft") or a claim copied from an email body; those rest on the writer prompt.
- **Audit and review.** Every ask is audited (`approval-asked`: the full exact arguments (size-capped, secrets redacted by `audit()`), the question as sent, the code text), every failed question (`question-failed`), every answer (`answer-*`: who, the owner's reply, the question, the judge's target, outcome and reason, in a group the scope) and, after the decision, `approval-outcome` says whether the arguments of the call that ran equal the ones the question was written for (plain equality, logged, never blocking). `npm run report` has a section "Approvals: question vs arguments" listing recent asks with the arguments next to the question.

Pieces: `src/approvals.ts` (scoped `request` / `answer` / `answerReaction`; the scope is always given), `src/approvers.ts` (the approver of each conversation), `src/approvalask.ts` (wording and audit; a tenant's audit rows carry no words, `audit.ts` `wordless`), `src/approvalmodel.ts` (the model calls), `src/approvalprompt.ts` (prompts and parsers), `src/questionfacts.ts` (the verbatim check), `src/recentchat.ts`, `src/approvalreport.ts`. The measuring tool for the question check (real Haiku calls, a few cents, not part of `npm test`) is `scripts/approval-eval-check.ts`.

Measured (Haiku, 2026-10, a corpus of 72 owner replies written for this exploration: plain, German, hedged, conditional, delayed, modified, sarcastic, questions, unrelated, rambling, adversarial, injection inside the question, several open approvals including "yes to both", quoted, ended approval, background approval; one pass each): one call writes the question (3.5 to 4.8 s), a judged reply takes about 3.1 s (6.4 s max, warm), at about $0.002 per ask and reply. False approvals: 0 of 72 in the last warm pass; 2 in the first run (a stale-quote "yes", and "yes to both but the email can wait" approved only the pottery, the reading the owner asked for, corpus relabelled); 0 after a prompt fix for stale quotes. That is evidence on a small corpus, not a bound.

Question validation without a model call, on 33 hand-written questions: missed 2 of 23 wrong ones (an attacker claim repeated as fact; "add" described for "replace", both wording-only defects code cannot see), false alarms 0 of 10.

## Reply drafts

When the background handler drafts an in-thread reply (a scheduling answer, say), the draft is shown on Signal ("✉️ Reply ready (draft #id)", To, Subject, the new text; `src/propose.ts`, `src/proposals.ts`). You answer by replying to that message: "send", or what to change (the quoted text reaches the chat, which finds the draft by its id). Sending is a chat send (see the approval judge): `send_message_now` is judged from your message and the draft, or asks. Either way the text is not built from the model's arguments but from the draft read back from the mail client (Mailbird or the Gmail connector) at that moment (`src/permissions.ts`): recipients, Cc, Bcc, subject, attachments and the new text, with the quoted original announced. If the draft cannot be read back, the send is refused rather than approved blind. So what you approve is what is sent, whichever draft the model picked, and the same holds for any send you ask for in chat.

## The proactive radar

The heartbeat watches mail every few minutes with no model. The calendar can only be read through the model, so the radar is a periodic look instead: adaptive, about an hour before your next meeting and at most every `RADAR_MINUTES` (180) apart, while you are awake and after the daily brief has run, one Sonnet run (`src/radar.ts`, skill `ted-personal-assistant:radar`) reads your calendar, the heartbeat's digest and what it already told you, and returns JSON: zero or more messages (a meeting about to start with its prep, a clash with two alternative slots, mail that the calendar makes urgent). Each run also reports when the next meeting starts, and code schedules the next run from that (never sooner than 45 minutes, never later than `RADAR_MINUTES`). When the assistant itself creates, changes or deletes a calendar event, the next run is pulled forward to 30 minutes after the last. An event you add yourself in your calendar app sends no signal, so the longest wait is the blind spot. Most runs return nothing.

**Who decides when it runs.** The radar is a preset the owner's gate chooses (`task: "radar"`, see Wake-ups below): default rule "about every `RADAR_MINUTES`/60 hours while awake, sooner before a meeting", which the gate reads off its own log: each run writes `[radar] ran: N message(s) sent, M event(s) read, next meeting at HH:MM. keys: [...]` as a ledger line, and a calendar change by the assistant writes `[nudge]` and pulls the next look forward. The HOW stays here in code: the radar profile and structured output, `acceptMessages`, and the message-rate rules, which are now the generic cap on posts: `MAX_PROACTIVE_PER_DAY` counts only the radar's own messages of the day (the `[radar] ran: N message(s) sent` ledger lines), so mail alerts cannot starve it. Its dedupe keys are read back from the `[radar] ran` lines of the last three days, so there is no radar state file any more.

The model decides **what** deserves an interruption; code decides whether it **may** be sent (`src/radar-rules.ts`): never the same message twice (a dedupe key per event), at most 3 per run and `MAX_PROACTIVE_PER_DAY` (8) per day, and nothing while paused, during quiet hours, while the daily brief is still due, or over the spend limit. The run is read-only apart from a meeting prep page in Notion; a calendar change or a sent mail still asks on your phone (policy source `radar`). It must report how many events it read, so a run that never looked shows up in the log. Everything the assistant sends on its own is kept in `memory/recent-pings.json`, so the chat knows what "yes, do that" refers to. Switch it off with `PROACTIVE=off`.

## Wake-ups: one gate for messages and the clock

`src/gate.ts` is the one gate. "Should I do something in this conversation now?" is asked by a small model (Haiku, no tools, JSON schema `{ act, task?, instructions?, delaySeconds, nextCheckMinutes }`) with the clock, the conversation's notes, the tail of its log and the default rules in `src/persona.ts` (`GATE_DEFAULTS`; notes tweak them, except for the brief backstop, which stays an override of notes). Two triggers: a group message nobody addressed (the participation decision, `src/group.ts`; the owner's chat and tagged or quoted group messages are always answered, no gate) and the clock (`src/wake.ts`, called from the heartbeat's `onTick` for the owner's chat, every group the owner is in and every tenant with the capabilities, see Tenancy: loops over every conversation). The ledger is the conversation's own log: kind `wake` holds the chosen next look (the last one is the state), kind `action` records a wake-up that acted (posted or not). Both are skipped by everything that reads the log as conversation (chat context, dream, compaction summaries, recent lines, finding a reacted-to message). A conversation is looked at when its next look has come, when something was said since, or when its notes changed. If the gate acts, the conversation's normal runner does it and the reply goes through the shared pipeline (it may be `[[silent]]`): groups with the group run, the owner with `runBackgroundTurn` (policy source `background`, like the radar: reads, anything else asks). Code guards are listed in SAFETY.md. Cost: one Haiku call per due conversation, at most hourly.

**Tasks and profiles (`src/tasks.ts`, `src/agent.ts`).** Everything the gate can start is a `Task { name, instructions, profile, after, retries? }`. The `profile` is HOW a run may work and is fixed in code, named in `PROFILES`: `brief`, `radar`, `background` (the owner's free-form wake-up) and `group`, each with its policy source, system prompt, skills, max turns, max budget and output schema. The gate chooses only `task: "task" | "brief" | "radar"`: `task` is free-form (the gate's instructions, the answer posted), `brief` and `radar` are presets for a conversation that has the `mail` and `calendar` capabilities on the instance's login, today the owner's chat only (`buildTask(presets, ...)` turns anything else, and any preset asked for by a group or a tenant, into the plain task or nothing). Preset instructions are the skills, not the gate's words. `brief`: after = capture the email the agent sent, save `memory/last-brief.md`, post the Signal summary; the attempt is logged as `[brief] attempt N started` and `→ delivered|incomplete|failed`, and code retries an incomplete one (after 10 minutes, up to `BRIEF_MAX_ATTEMPTS` a day) and runs the brief at `BRIEF_BACKSTOP_HOUR` (9) if none is logged for the day, in both cases without asking the gate (the dream first). `radar`: after = post its messages. Presets run outside the chat's queue (a brief takes minutes) and are not awaited by the owner's look either: `wake.ts` starts each as a detached background job (I/O-bound, so no worker thread) with a per-task running guard, the look returns at once, failures are logged and audited, and the ledger lines are written when the run ends.

**Idle looks are skipped.** After a clock look the model answered quiet to, wake.ts remembers a fingerprint of what the model was shown (gate.ts `idleFingerprint`: the notes, the log without the model's own "you looked" lines, the hour, and for the owner the radar's age and the brief's state). If the next look is due and the fingerprint is unchanged, the model is not asked: the same next-look time is recorded and the look returns `idle`. A new message, a changed note, a new hour or a job coming due changes it; a note that names a time of day ("9:40", "at 9", "noon") puts the minute in it, so nothing is skipped. Only a real answer counts as a quiet decision (a failed call is never one), and a restart forgets them.

**Usage-limit cooldown (`src/cooldown.ts`).** When any call is refused with a rate limit (`failure` in `src/errors.ts`), a cooldown starts for that call's payer (the login's, or the instance key's, see "Who pays for a model call"): until the SDK's own reset time (`rate_limit_event`) if it gave one, else 15 minutes, doubling per consecutive refusal to 2 hours. Background model calls skip while it is active, with one log line per episode (`payer.ts` `mayRun` asks, so every one of them does): the clock look and everything it starts (gate, wake-up runs, brief, radar), quiet compaction, mail triage (the mail stays unseen and is retried), the dream, log summaries and notice writing (template text). The owner's chat and group turns, and a group message look, never check it; they are the probes, they get the usual notice, and any successful call (chat, run or gate) clears it.

**The heartbeat tick.** Every `HEARTBEAT_MINUTES` the mail check and the tick jobs (wake-ups, which include the brief and the radar) are started independently, each in its own try/catch with its own re-entrancy guard; none waits for another, so a failing Mailbird or a slow brief delays nothing else. Conversations are looked at in parallel.

## Skills and setup

The skills are an SDK **plugin** that lives in the repo (`plugin/`, loaded with the `plugins` option, offered to the model with the `skills` option, so nothing in `~/.claude/skills` leaks in or costs context). They are written for anyone: calendars, Notion pages and writing style are read from the owner's `setup-calendars`, `setup-tasks`, `setup-meetings`, `voice-writing` notes. `src/notes.ts` knows these four required files (`SETUP_ITEMS`); the system prompts list the missing ones. In chat the agent then offers to run the `setup` skill, which finds things with the connectors (list calendars, search Notion, optionally read sent mail to learn the owner's voice), asks one small question at a time and saves each answer as a note. Runs with nobody to ask (brief, handler) skip what they cannot do without it and say so in one line. Which connectors a run could see (Notion, Google Calendar, mail) is recorded from its start-up message in `state/connectors.json` (`src/connectors.ts`), so a missing connector is reported as "not connected", with how to fix it, and never as "not set up"; setup items that depend on it are not listed as missing. Nothing personal is ever in the repo. The plugin is loaded for every kind of conversation; what differs is the allowlist: the owner's is `ownerSkills()` (the assistant's own skills plus those of the loaded tool modules, `src/skills.ts`), a group's or tenant's is the shared skills her capabilities allow (`src/skills.ts`), never a private one. One skill is a habit rather than a task: `follow-through` is loaded after any action that changes mail, the calendar, tasks or a booking and asks what else the change implies (archive the handled mail, the matching task, travel time, follow-up tasks); routine and reversible steps are done, bigger ones asked once, and it grants no permission. A run that may not take a step itself (the mail handler cannot archive or change tasks without asking on the phone) writes it as a suggestion in its result line. The calendar, notion-tasks skills and the handler's task text point to it.

## One pipeline for every conversation

The private chat and each group go through the same code (`src/conversation.ts`, tested against `FakeMessenger` in `test/conversation.test.ts`). A `Conversation` is plain data made only by `owner()`, `group(id)` and `tenant(id)`: it fixes the Signal target, the policy source (`chat` or `group`, so owner-only tools stay owner-only), the log, the notes folder, whether the participation gate and approvals apply. Everything else is shared, memory and context handling included (below): read receipts, voice messages in and out, pictures in (`see()`: `src/image.ts` checks the bytes, shrinks the photo to 1568 px with macOS `sips` and converts HEIC, then the SDK prompt is one user message of image blocks plus the text; the bytes live in memory for that turn only, the log gets `🖼️ caption`), quote context and threading, reactions, `[[silent]]`, typing, the error notice (rate-limited in groups) and one turn at a time per conversation. **Bursts are handled there too, for both kinds** (`burst` in `src/conversation.ts`, `SETTLE_SECONDS`, default 2): after each message a short settling pause, and a newer message restarts it, but never beyond `SETTLE_MAX_SECONDS` (default 10) since the burst's first message: then it is processed and later messages join the next turn. Everything that arrived by the time the one queued run starts is folded into that single turn, oldest first (the owner's prompt keeps each message's own quote and voice marks; a group's run sees them all in its log). A run already in progress finishes and sends; messages that arrive meanwhile are the next turn. A group's participation gate and sticky "addressed" rule (`src/group.ts`) decide once the burst has settled, but the gate's model call is started when an untagged message **arrives**, in parallel with the settling pause (`judge()` in `createGroupBrain`), so the two overlap instead of adding up. The verdict is used only if that message still ends the burst; if a newer one arrives, the old verdict is dropped and the newer message is judged with its own tail (one Haiku call per untagged message, but never a second run: a burst is still one queued turn). No call is made when a run is already queued for the burst, or when paused or over budget. The owner's chat has no gate. **"typing…" starts when the decision to answer is made, not when the model starts** (`holdTyping` in `src/conversation.ts`, the one place that refreshes and stops it): right after the settling pause for the owner and for tagged group messages, when the gate says act for the rest, so it also covers the gate's delay and the wait behind an earlier turn; a "no" from the gate, a reaction or a wake-up never shows it, and every hold is released in a `finally`. The gate's delay is capped by `GATE_MAX_DELAY_SECONDS` (default 4) in code and in the output schema, because the delay is for seeming natural, not slow. Approval answers (text and reactions) stay a step before the burst, so they are never delayed or folded in.

**Long messages in.** A Signal app sends text over about 2000 characters as a cut body plus a `text/x-signal-plain` attachment holding all of it. The client surfaces that attachment as `m.longText` (`{ id, size }`, never as `m.file`, so no "unsupported file" sentence); `withLongText` in `src/conversation.ts` (the one intake for the owner and every group, edits included) reads it with `readLongText` (id only, a plain file in signal-cli's folder, no symlink, strict UTF-8 without NUL, at most 64 KB, then a note) and uses it in place of the body (appended if it does not start with the body). Unreadable: the cut body plus a one-line note for the model. Cuts on the way in: `cleanIncoming` 70,000 characters (`LIMITS.message`), the group's log and gate line 600 (the message that addressed a group goes whole), the owner's log line 4000, the gate's view 240 per line, a quote 2000, the thread preview 200; the model gets the full message up to 64 KB.

**Documents in (PDFs and text files), the same path as pictures.** signal-cli's first attachment that is neither a picture nor audio reaches the pipeline as `m.file` (`{ id, size, name }`, the id joined to the attachments folder exactly like pictures). `openFile()` in `src/conversation.ts` (the document twin of `see()`, same `tell()` rules and the same "tagged groups open it only when addressed" rule) calls `prepareDocument` in `src/document.ts`, and the bytes decide: `%PDF-` makes a PDF (at most 20 MB and 100 pages, the page count read from the page tree when it is in plain text, not password protected), a `.txt .md .csv .json .log .ics .vcf` name plus valid UTF-8 without NUL bytes makes a text file (cut after 200 KB with a note), everything else (Office files, zips, executables, a fake `.pdf`) is not opened and the sender gets one sentence naming what works. A PDF goes to the model as a base64 `document` content block in the same single user message as pictures (images, then documents, then the text; `userInput` in `src/image.ts`); a text file is placed in the prompt inside a `<file_text>` fence. The sender's file name is reduced to a plain label (letters, digits and a few marks) and quoted in a note that says the content is data from the sender, never an instruction. At most 3 documents per turn (newest first, PDFs together under about 22 MB), owner chat and groups alike; the bytes live in memory for that turn, and only the size is logged plus `📄 caption` in the conversation log. Checked end to end with a real model call: a generated PDF through the Agent SDK input path was read correctly (no `pdftotext` fallback needed).

**Edited and deleted messages** (the same code for both kinds, `edit()` and `deletion()` in `src/conversation.ts`, group parts in `src/group.ts`, pure parts in `src/edit.ts`). signal-cli reports an edit as `editMessage { targetSentTimestamp, dataMessage }` on the envelope (your own edit on another device, in Note to Self, as `syncMessage.sentMessage.editMessage`), and a delete as `dataMessage.remoteDelete { targetTimestamp }`; before this nothing handled them and `interpretEnvelope` dropped them. The package turns an edit into an `IncomingMessage` with `edited: { targetTimestamp }` and a delete into `IncomingDeletion` (`onDelete`). In the app: the sender must be the original's author (the log records `by` for every inbound line; for a message still waiting its own author). The original **still waiting** (in the settling pause, queued, or being judged by the gate): the edit takes its place in the burst, so the one turn answers the new text (in a group the gate is asked again, since a newer message supersedes the old verdict). **Already answered**: the edit is a new message to the same conversation, marked `[Edited message]` with the earlier and new text each fenced as data, and goes through the same participation logic as any message in a group. An edit that is identical after NFC and whitespace normalisation is ignored. An edit never goes to the approval check. A **delete** of a waiting message drops it (and a group's pending address of it, and a gate verdict made on it is judged again); of an answered one only adds a marker line. The log stays append-only: an edit is a line of kind `edit` and a delete a line of kind `delete`, both with `of` (the timestamp they concern); lookups by timestamp (reactions, quotes) resolve the original's or any edit's timestamp to the newest text (`findMessage`, `revisionsOf`); the group context and the gate's tail hide deleted messages and show an edit as an edit; the dream sees one message per edit (`foldEdits`) and none for a deleted one (`withoutDeleted`), and the compaction summary is shown an edit as a line of kind `edit`; `lastInboundAt` of the wake ledger does not count edits or deletes. Audio and pictures are not carried over by an edit (a caption edit is text only).

**Groups use the owner's memory and context model.** A group run is the SDK's auto-memory like the owner's chat, with `autoMemoryDirectory` set to the group's notes folder (`memory/groups/<key>/notes/`), Claude Code's own prompt with a short group persona appended, no user settings, no connectors, the tools and shared skills of its capability set (`runOptionsFor` in `src/runoptions.ts`, `src/capabilities.ts`). Its Read, Write and Edit are allowed only inside that folder (the SDK itself auto-allows writes inside `autoMemoryDirectory` and resolves `..`; every other path goes through `classify` and `isInside`). Each group also has a resumed SDK session of its own (`session.json` in its folder) with the owner's rules: never reset just because time passed, compacted in the background when the context passes `CHAT_COMPACT_TOKENS`. Groups are many and bursty, so they share **one warm process**, for the group that spoke last (see Speed and cost, one keyed pool); the owner's chat keeps its own. Messages in the group that were not for the assistant are not sent to the model one by one (that would be a model call each): they are logged, and the next turn's prompt **prepends** the lines members wrote since the session last saw the log (`groupContext`, `seenAt` in the session file); a fresh session gets the last 25 lines instead. The "Memory ... undo" announcement is the owner's only; in a group the reply says what was saved.

**One builder for the options of a conversation's run (`src/runoptions.ts`).** The owner's chat, a group and a tenant are built by the same function, `runOptionsFor(conversation, inputs)`, from the conversation's record (kind, source, notes folder, session file, the group's id) and, for a tenant, her registry record (capabilities, credential source, ledger, limits, consent). The caller adds only what is not in a record: the group's style lines, the owner's notifier, the instance key, the clock. What differs between the three is a small table in that file (persona, limits, skills, tools, memory, the `tenant` block with the instance key and her ledger), not three code paths; the isolation follows from `source` in `buildOptions` as before. The turn itself is one path too (`runConversation` in `src/agent.ts`: the conversation's session, the approver `approveIn(conversation.key)`, its warm process or a cold start), and so is the warm-up (`prepare`). `test/runoptions.test.ts` pins the options of all three against a fixture captured before they were unified, and lists what differs between them. The security invariants stay in code, not in the builder: tenants/, state/ and OpenBao stay denied (`policy.ts`), a tenant's environment carries the instance key and none of the owner's logins (`tenantEnv`), a group has no connectors and no private skill (`strictMcpConfig`, no settings sources, the skills allowlist), and approvals are asked per conversation (`approvers.ts`).

**One way to say something mid-turn (`send`).** During a longer task the model can put something in the conversation while it keeps working: a short text ("On it, researching now"), a voice note, a picture or a reaction, then send the result as its normal final reply (which stays the default last message, with its `[[silent]]`, `[[voice]]` and `[[react: ...]]` markers, and needs no tool call). It does so through the `send` tool (`src/send.ts`, an in-process MCP server, manifest row `mcp__send__send`, no approval), offered only to the owner's chat and groups, never to unattended runs (brief, radar, handler, browse worker, dream, compaction, wake-ups). Parameters: `text` (with `voice: true` to speak it), or `picture` (a screenshot id, optional `caption`), or `react` (one emoji, on the message being answered); exactly one kind per call, checked in code, any number of calls in any order. Text the model writes between tool calls stays internal and is never sent. Everything a turn says, the final reply and every `send` call, goes through ONE delivery function in `src/conversation.ts` (`delivery` in `createPipeline`): sanitiser, target, quote and thread rules, `[[silent]]`, the voice language safety net (`src/lang.ts`: text in a language the voice does not speak is sent as text), group rules, typing re-asserted after each mid-turn send, and one log line per item; a mid-turn send also writes one audit row (`send`: kind, conversation, and for a picture id and size). A mid-turn reaction replaces the final ✅. When and how often is the model's call (persona rule); there is no count limit in code, the run's turn, budget and time limits bound it. The sink is found by conversation when the tool is called, because warm processes are built before their turn.

**A voice of your own per conversation (`voice`, Qwen only).** The Qwen server (`packages/speech/scripts/qwen-tts-server.py`) keeps one model loaded and takes the reference per request: `POST /say {text, voice?}`, where `voice` is a relative path of fixed shape (`voices/<name>` or `groups/<16 hex>/voices/<name>`) inside the voice folder; without it the configured clip (`TTS_REF_AUDIO` / `TTS_REF_TEXT`) is the default voice. The model caches the encoded reference per clip, so a switch needs no restart: `tts-qwen.ts` reads the conversation's `active.json` (`voices.ts`) for every reply, and `synthesizeWith(..., scope)` is given the conversation key by `speak()` in `src/conversation.ts`. Libraries: `state/voice/{active.json,voices/<name>/{ref.wav,ref.txt,meta.json}}` for the owner, the same under `groups/<hash>/` per group. The `voice` tool (`src/voicetool.ts`, one tool with `use | sources | list | switch | delete | reset_group`) is built per conversation key like `send`, only with `TTS_PROVIDER=qwen`, and is `no` approval for chat and group in the manifest. `use` builds a clip from a voice note of that conversation (`src/voicenote.ts` remembers id, sender and a snippet of each received voice note, 50 per conversation for 7 days; a reply to a voice note is recognised by `quotedAudio` in the envelope), `buildReference` (`packages/speech/src/voiceclip.ts`) decodes with ffmpeg to mono 24 kHz, trims silence, checks length (3 s minimum), loudness and steadiness, keeps the best 15 s, transcribes it with whisper for `ref.txt` and refuses clips without words. Measured on an M-series Mac (small Whisper): a 33 s voice note with 1.5 s and 2 s of silence around it became a 13.5 s clip in about 1.5 s; the first reply after a switch took no longer than the next one (no restart, no extra load); a longer reference makes every reply slower because the clip is part of the prompt (a 27 s clip took about twice as long per reply as a 10 s one), hence the 15 s cap. Groups and the owner share all of it; only the key differs.

**Audio files in (MP3, M4A, WAV, OGG, AAC, FLAC), the same path as documents.** An audio attachment with a file name (a recorded voice message has none) is surfaced by `parseFile` as `m.file` (with an `audio` hint from the declared type, used only to decide whether a group file is opened at all), so it takes `openFile()` and `prepareFile()` in `src/document.ts`: the bytes decide, first by the magic bytes (`audioMagic`), then by `ffprobe` (`probeAudio` in `packages/speech/src/audiofile.ts`, `execFile` with arguments and a timeout, plain files only): there must be an audio stream and no real video stream (cover art is fine), so a video, a fake `.mp3` or a renamed file is refused with a sentence. At most 50 MB. The first 5 minutes are transcribed with the same whisper step and queue as voice messages (`transcribe(file, model, maxSeconds)`), and the model gets a new document kind, `audio`, fenced as `<audio_file_transcript>` with a note that it is a FILE the sender attached (sanitised file name, length, "only the first 5 minutes" when cut) and not a message they recorded; no recognisable speech is said as such. When it has speech and `TTS_PROVIDER=qwen`, `openFile()` also registers it in `voicenote.ts` as a source (`kind: "file"`, name, seconds, id only), the same list and lookups as voice messages (the asking message, a quoted file via `quotedAudio`, the latest, or an id from `sources`), per conversation. `use` runs `buildReference(file, tools, { file: true })`: it probes again, searches the first 5 minutes of a long file instead of refusing it, and picks the 10 to 15 s stretch with the most lively speech (loud frames only count when the level moves, so an intro jingle or a held tone loses to speech; a long pause inside a stretch costs more than the frames it lacks); the speech and steadiness checks apply to that stretch, not the whole file. Measured (M-series Mac, small Whisper): a 40 s MP3 with a 28 s tone intro and 12 s of speech was probed and transcribed in about 1.5 to 2 s and became a 12.1 s reference in about 1.5 s (the tone was skipped); a 40 s tone alone was refused as steady noise, a video and a fake `.mp3` in under 40 ms. Known limit: music with vocals can pass for speech until the transcript of the chosen clip comes back empty or not words.

**Passing a screenshot back (`send` with `picture`).** With `BROWSE_VISION=read` or `click` the browse guard keeps each screenshot the worker takes as a small jpeg (real jpeg bytes only, 3 MB cap, a name code chooses) in a private folder under `state/browse/shots` (`src/shots.ts`). The browse result lists them to the calling chat run as `shots: [{id, caption}]` (ids `shot1`, `shot2`..., the caption is the worker's one line, cleaned and cut). The model decides whether a picture helps and calls `send(picture: id, caption?)`. Code looks the id up in THIS turn's screenshots only (never a path), re-checks the file (a plain file inside the turn's folder, no symlink, jpeg magic bytes, size) and the delivery sends it as an attachment to the conversation the turn belongs to, with the reply's target and quote rules and the caption cleaned. The files are removed when the turn ends; a sweep removes folders older than an hour. With `BROWSE_VISION=off` there are no screenshots and the tool answers "No screenshot available".

## Capabilities decide the tools and skills of every conversation

The owner's chat, a group and a tenant have the same features; what differs is the permission. One mechanism, not three lists:

- **ONE resolver: `capabilitiesOf(conversation)`** (`capabilities.ts`), a set of `tenants.ts` `CAPABILITIES`; `allows(conversation, capability)` is `capabilitiesOf(conversation).has(capability)`. Tools, skills AND the loops (wake-ups, the dreams, the mail check, the gate's presets, the spoken wake-up) all read this one set, for the owner, a group and a friend; there is no second list. It is: (1) the conversation's grant: the owner's record (everything before it is seeded), a tenant's record, or for a group the fixed `GROUP_CAPABILITIES` (chat, browse, voice, heartbeat, dream, wake, weather, draw); (2) nothing at all unless the person is `active` (not invited, suspended or removed); (3) less what only the instance's own login can give, for everybody but the owner: `profile`, `card`, `admin`, `drive`; (4) less what is not set up: `mail`, `calendar` and `google` of a person on the instance key need her `google` capability and the instance's Google OAuth client (one `googleReady()` in `settings.ts`), `notion` needs the intake page's public address (`INTAKE_BASE_URL`), `intake` needs a purpose she holds the capability for; (5) less what the instance switched off in `.env`, for the owner and groups too (`BROWSE`, `WEATHER`, `DRAW`, `DREAM`, `WAKEUPS`; `PROACTIVE` switches the radar preset, which is not a capability); (6) less her own `tenant.json` switches (`browse`, `voice` off). Every step only takes away.
- **Tools.** Every row of the tool manifest (the rows of the loaded tool modules, `src/modules`) names the capability that gates it (`cap`) and the sources it is for (`only`). `toolsFor(capabilities)` is the manifest rows whose capability is in the set and that are offered to a "group" run; nothing else exists, and an unknown tool is simply not in it. From that one set come the run's built-in tools (`agentrun.ts`), which in-process MCP servers it gets (send, voice, draw, weather, browse, intake), and `policy.ts` `classify` (`classify(tool, input, "group", notesDir, tools)` denies a tool outside the set; a file tool is also path-checked). A new MCP server is a tool module that declares its capability in its rows and nowhere else.
- **Skills.** The tool modules and `src/skills.ts` (the assistant's own skills) list the shared skills and the capabilities each needs (`research-booking`: browse, `surf-conditions`: weather, `draw`: draw) and the private ones (`daily-brief`, `mailbird`, `mailbird-troubleshooting`, `gmail`, `calendar`, `notion-tasks`, `meeting-prep`, `setup`, `radar`, `follow-through`), which no group or tenant is ever offered; a test requires every folder of `plugin/skills/` to be in one list. An isolated run loads the bundled plugin with the SDK's skills allowlist set to `skillsFor(capabilities)` and has the `Skill` tool only when that list is not empty; settings sources stay empty and MCP strict, so no user skill, no `CLAUDE.md`, no connector. The shared skills read and write this conversation's own notes folder (they say "the person" and "this conversation's notes", not "the owner").
- **What stays code.** The resolver never gives the owner's tools to anybody else: `NEVER_FOR_ISOLATED` and the modules' `ownerOnly` flags still remove the owner's connectors and tools from any set, and the owner's own tools are not derived from the set. `tenants/` and `state/openbao/` are denied for every file tool (`policy.ts`); payment is only by a typed yes in the owner's foreground chat, and a group or tenant never gets payment, profile or card (`NEVER_FOR_ISOLATED` removes them from any set); the admin reads no tenant files; the browse tool starts a separate run that asks in the conversation; text relayed by an agent never approves. The owner's own tools, skills and prompt are not derived from the set: the owner's conversation is the full set, with the connectors and the whole plugin, and the manifest flags decide what asks.
- **Tests** (`test/capabilities.test.ts`): the tools and skills of a group, a friend and a person with chat only are pinned; adding one capability changes exactly its tools and skills; every capability is in the table; no private skill or connector tool is in any set; `classify` gives the same answers for the same probes as the set says.

## Tenancy: more than one person on one instance

One instance, one Signal account, several people. **Off by default** (`TENANTS=off`): with no `state/tenants.json` and no invite codes nothing here runs and an unknown sender is ignored as always. Everybody, the owner included, is one record in one registry: the owner is the record `owner` (role admin, every capability, the folders and files the instance has always used, unmoved: `pathsOf()`); a friend is a record with a folder `tenants/<id>/` of her own. It is the same pipeline (`src/conversation.ts`), not a fork: a third `Conversation` kind `tenant(id)` next to `owner()` and `group(id)`, which takes the owner's turn path (always answered, no gate, her own approvals scope) and the group's isolation (policy source `group`, so none of the owner's data). What differs is only data and which tools exist.

- **Identity and routing** (`src/tenantroute.ts`, `main.ts`): identity is the sender's Signal account id (ACI), never a number. `packages/signal` marks a private message from someone other than the peer (`other`, `fromUuid`) and addresses one person with a target made by `directTarget(aci)` (packages/messenger; Signal's adapter turns it into signal-cli's `to:<aci>`), used wherever a conversation target is taken; `Conversation.target` is where a conversation's messages go (a group id, a direct target, or undefined for the owner's chat). A tenant's message goes to her conversation; a suspended tenant's to nobody; anyone else gets one fixed text with no model call (invitation, "that code is not valid", welcome), rate-limited. A member of a group who is also a tenant is just a member there: the group's folder, log and run are the group's.
- **Registry** (`src/tenants.ts`): `state/tenants.json` holds ONE record per person: id, name, account ids (ACI), role (`admin` or `member`), status (`invited`, `active`, `suspended`), capabilities, credential source (`login` for the owner, `instance-key` for tenants), created, and for the owner her number (the seed); never a key. Paths (root, notes, log, session, cost) and limits are derived from the record (`pathsOf`, `tenantContext`; limits from `tenant.json` and `TENANT_DAILY_BUDGET_USD`). A field an older file lacks gets the safe value (a member with the friend defaults), and an unknown role, capability or id does not load. `listTenants()` is everybody but the owner (what invitations, routing, suspension and removal work on, so none of it can reach her record); `people()` is everybody. Invite codes (`src/onetime.ts`, `state/invites.json`) are single-use, expire after `INVITE_TTL_HOURS`, are stored hashed and are minted by the owner's chat tool `create_invite` (`src/tenanttools.ts`, no approval needed); `suspend_tenant` and `remove_tenant` ask on the phone. A valid code provisions her folder (`notes/`, `backup/`, `tenant.json`) and makes her a member with the friend capabilities.
- **Who is the owner** (`guards.ts`, `tenants.ts` `resolveSender`): the first start seeds the `owner` record from `SIGNAL_OWNER_NUMBER` (and `SIGNAL_OWNER_ACI` when set). A sender resolves to a record by account id when it is known, else by number; "is the owner" is "resolves to a record with role admin" (`acceptOwner`, and the group approver and vouching checks in `main.ts`). The envelope carries the sender's account id also for the peer's own messages and Note to Self (`fromUuid`); the first message from the owner's number with an id records the pair once (`learnOwnerAci`: logged and audited, never by chat or the model, never replaced by a later message, never an id a tenant has). Without an id in the envelope the number keeps working. **The admin role** moves only through `npm run tenants -- set-admin <id>` (the only way back in after a lock-out; one admin at a time), and capabilities only through `grant` / `revoke` there: nothing under `src/` imports those functions (a test scans for it), so no tool, hook or chat path can reach them. Until every person has her own file root the admin chat is the instance's own files, so the CLI sets the role on `owner` only.
- **Capabilities**: `chat`, `browse`, `voice`, `heartbeat`, `dream`, `wake`, `mail`, `calendar`, `notion`, `profile`, `card`, `notes`, `intake`, `weather`, `draw`, `google`, `drive`, `admin`. The owner has all; a new tenant gets `chat`, `browse`, `voice`, `heartbeat`, `dream`, `weather`, `draw` (NOT `wake`; the last two are free tools, so they are on; a record written before they existed gets them with `grant`); the admin switches the rest with `grant` / `revoke`. `capabilities.ts` `allows(conversation, capability)` is the one question code asks: her `browse` and `voice` tools follow their capability (and her `tenant.json` switches, for the loops as for the tools), `heartbeat` / `wake` / `dream` drive the loops below, and `card` gates the `/card off` command. `profile`, `card`, `admin` and `drive` need the instance's own login or the admin's powers: only the owner's conversation is on the login (`onLogin`), and the record's `credential` field changes nothing about that. `mail`, `calendar` and `google` are her own Google and `notion` her own Notion, each only once she has connected it (the next two sections). The others are recorded and shown (`npm run tenants -- list`).
- **Loops over every conversation** (`wake.ts`, `dream.ts`, `payer.ts` `mayRun`): the tick looks at the owner, every vouched group and every active tenant with `heartbeat` (`TENANTS=on`). For a tenant the idle look and the wake-up need `heartbeat` AND `wake` (`wake` is off for friends: the admin grants it), the quiet-time compaction needs `heartbeat`, the nightly dream `dream`. Everything is hers: the gate reads HER notes and log (her messages under her name, `speakerOf`), the wake-up is the conversation run on the instance key (`runConversation`, her session, her notes folder, her approvals in her chat), the answer goes to her chat only (`Conversation.target`), the cost is written to her `cost.json`, a refusal of the key is the key's cooldown (`gate.ts` `GateInput.payer`, `dream.ts` `runnerFor`). `mayRun(conversation, what)` is the silent version of the gates of her turn: suspended, the key in a cooldown or past her day's budget means no model call and no message to her; with `TENANT_ANTHROPIC_API_KEY` unset nothing runs (the owner's login is never a fallback) and the owner gets the one key notice (`keynotice.ts`). The instance's own daily budget stays the owner's and the groups' and hers stays hers; the shared cooldown of the owner's usage limit never stops a tenant, and a refusal of the instance key never stops the owner. Quiet hours (`QUIET_START_HOUR`, `QUIET_END_HOUR`) apply to every private chat, the owner's and each tenant's; idle fingerprints and next-look times are per conversation. Each conversation is tried on its own (`Promise.all` with a catch per conversation; the dream loops over conversations with a catch per conversation), so one tenant's failure never reaches another conversation. Her gate prompt is `directGateDefaults` (no brief, no radar, nothing of the owner's); her chat prompt says she can act at set times (`SELF_TIMED`) only when both capabilities are on. The friends' dream is the one dreamer above (their notes categories are the preset's `notes.tenant`, their snapshots in her `backup/`, their state in her `dream.json`); it starts with the owner's dream before the brief but is not waited for, runs only when she wrote something since the last time, and logs no note text. The brief, the radar and the mail heartbeat stay owner-only. There is no separate notes backup loop: snapshots are made by the dream (`dreamapply.ts`).
- **Her folder** `tenants/<id>/`: `tenant.json` (typed overrides: language, persona, daily budget, turn limits, browse and voice off, both deprecated in favour of revoking the capability; anything else, such as the old `timezone` and `connectors`, is reported as an unknown setting and ignored), `notes/` (the SDK auto-memory and the only place her file tools reach), `messages.jsonl` (her history, size-bounded, summarised without a model), `session.json`, `cost.json`, `consent.json`, `meta.json`. It sits outside `logs/`, `state/` and `memory/`, which are what the owner's chat may read, and `isReadableData` also names it, `state/openbao/` and the ticket files as unreadable; the admin's chat cannot write there either (its write tools are notes-only) and has no Glob, Grep or Bash. The admin's powers are the instance's (invites, suspend / resume / remove, groups, the instance's logs and audit, reports), never a tenant's content: her audit rows carry no words, and the first reply she gets says so, and says that whoever runs the computer could still read its files (`DISCLOSURE`).
- **A tenant's run** (`tenantrun.ts`, then `agent.ts` `runConversation`, the same path as the owner's and a group's): the gates that need no model come first (`mayRun`: suspended, no instance key set, the key's cooldown, her budget: a fixed notice at most every `TENANT_NOTICE_MINUTES`; with no key the admin gets a notice in her chat too); then the run: `RunOptions.tenant` carries the instance key (`TENANT_ANTHROPIC_API_KEY`, read into `settings.tenantApiKey` and deleted from `process.env` at start, so no other process inherits it), which `payer.ts` `envFor` puts in the run's environment as `ANTHROPIC_API_KEY` *instead of* the owner's logins (the owner keeps the Claude login, unchanged, and never sees the key), her ledger and her tool set. Her browse worker and her compaction use the same. The key is never logged or audited (redaction covers `sk-ant-` and a test checks the logs and the audit). Cost goes to her `cost.json`; a refusal of the key (`rate_limit`, `billing_error`, `invalid_request`, `authentication_failed`: HTTP 429, 402, 400, 401) becomes an `InstanceKeyError` and a cooldown of the KEY (`cooldown.ts` keeps a state per payer; `INSTANCE_KEY_COOLDOWN` is the instance key's, the default key the login's), so every friend pauses together, and never the owner; her daily budget stays her own; the owner's chat gets ONE notice that the shared key was refused (`keynotice.ts`, called from `errors.ts` `failure`, where every model call on the key ends up whatever started it: her chat turn, the heartbeat, a wake-up, the dream, the mail loops and the handler, the idle look, the compaction), at most every `TENANT_KEY_NOTICE_MINUTES` (three hours), a fixed sentence with no word or name of any friend; a missing key goes through the same function (`mayRun`; `tenantrun.ts` has no copy of it). A warm process is kept for each of the `TENANT_WARM_MAX` most recently active tenants (the same pool as the owner's and the group's). The first reply she gets carries the AI line; before her one-time age and region confirmation (`record_consent`) her run has that one tool.
- **Who pays for a model call and may it run now** (`payer.ts`, `haiku.ts`): ONE answer for every call, whoever started it. A `Payer` is `{ kind: "login" }` (the owner's and the groups': the instance's day budget in `state/cost.json` and the login's usage-limit cooldown) or `{ kind: "instance", id, apiKey, costFile }` (a friend: the instance key, her own cost file and ceiling, and the instance key's cooldown, shared by every friend). `mayRun(conversation, what, options)` returns the Payer or `{ refused }` (`paused`, `inactive`, `no-key`, `cooldown`, `budget`): the pause switch, the status, the key, the cooldown, the budget, the same for the idle look and its gate, a wake-up, the brief, the dream (owner, groups, friends), the mail check and its handler, quiet AND urgent compaction (`chatsession.ts` `compactConversation`), a warm process and a friend's chat turn (`chat: true`: somebody wrote, so the pause switch is not asked, and the owner's and a group's turns are never held back). The call itself is `oneShot({ system, prompt, schema, payer, timeoutMs, spare })` for the small model (triage, the gate, the dream, notices, the language check, the log summary, the approval judge) and `runAgent` / `compactChatIfNeeded` for the rest: each takes the Payer for its environment (`envFor`), its ledger (`charge`), the rate-limit reset time (`observe`), the failure (`errors.ts` `failure`: the cooldown, the owner's one key notice) and the cleared cooldown on success (`succeeded`). The approval judge is always paid by the login: it is the instance's safety net, not the person's work.
- **Tools and skills** (`capabilities.ts`, `skills.ts`, `policy.ts`): her capabilities give her tool set and her skills, the same way a group's fixed set does (next section); `classify` takes the set and denies a tool outside it. Today: her notes (Read, Write, Edit inside `notes/`), WebSearch, `forget_note`, `search_logs` (her history only), `send`, `voice`, `browse` (the worker has neither saved profile nor card in this mode), the weather tools, `draw`, and the shared skills those allow. Owner-only tools, mail, calendar, Notion, page fetches, payment and the saved profile are never hers (`NEVER_FOR_ISOLATED`, tested). Her own Google and Notion are the next sections.
- **The instance key**: tenants have no keys of their own and there is no per-tenant key store. The key is a SEPARATE Anthropic Console workspace key with a monthly spend limit (the guard against a runaway tenant, with the per-tenant daily budget); it is `TENANT_ANTHROPIC_API_KEY` in `.env`, not `ANTHROPIC_API_KEY` (which `settings.ts` applyCredentialMode drops in login mode). The OpenBao policy stays the owner's folder only.
- **Doctor** says whether the instance key is set (never its value) and lists each tenant with status, capabilities, whether her Google and Notion are connected (`connections.ts`: whether and since when, never a token; `npm run tenants -- list` and the `list_tenants` tool show the same), consent, today's spend against her limit and a pause (the running agent writes `meta.json`, since doctor is another process).
- **The intake page** (`src/intakeserver.ts`, `src/intakelinks.ts`, `src/intakepurposes.ts`, `src/intakestore.ts`, `src/intaketools.ts`, `scripts/intake.ts`): the only way a tenant enters a secret, and nothing secret goes through Signal. A separate Node process (`npm run intake`, plain `node:http`, inline CSS, no script or outside file) on `127.0.0.1:INTAKE_PORT`; a tunnel the owner sets up puts https in front (`INTAKE_BASE_URL`). In a tenant's run, when `INTAKE_BASE_URL` is a usable https address and she holds `intake` plus the capability of a purpose, her tool set has two more (`get_setup_link`, `setup_status`; never in the owner's or a group's run). `get_setup_link(purpose)` mints a link: 128 random bits, kept only as a hash in `state/intake/<hash>.json` (a file per link, so the agent that mints and the page that redeems never write one shared file; a use is an atomic rename that one request wins), bound to her id and ONE purpose, expiring after `INTAKE_LINK_MINUTES`, one open link per person and purpose. The page serves `GET /i/<code>` (the form), `POST /i/<code>` (check, claim the link, store, burn it; a failed store puts the link back) and `GET /healthz`; everything else is one identical 404. The purposes are a registry (`PURPOSES`: each carries its capability, the kind of secret item it writes (`ITEM_KINDS` in `secrets.ts`, from which the page's writer, both OpenBao policies and the doctor's probe are generated) and what it needs set up): `profile` (the keys of `profile.ts` with their kind and domain binding; an ID-like value only with its sites) and `card` (number, expiry, holder, currency; the security code field exists only for `CARD_TENANTS`, the owner); `google`, `notion` and `cvc` are added there when they are built. The page writes through `IntakeWriter` with its own write-only OpenBao token (`openbaoadmin.ts` `INTAKE_ROLE`, Keychain `ted-openbao-intake`) and records only names and lengths (`state/intake-status.json`, the audit row `intake_store`), which is all `setup_status` can tell the model. Owner: `npm run intake -- link owner <purpose>` mints a loopback link.
- **Her Google** (next section): her own Gmail and Calendar tools and her own mail heartbeat, through the same code as the owner's.
- **Not yet**: SQLite instead of files, saved details and a card for friends, per-tenant voice libraries beyond the conversation key.

## Google for friends, and the mail heartbeat for every conversation

A friend with the capabilities `google`, `mail` and `calendar` (`npm run tenants -- grant <id> google` grants the three) has her OWN Gmail and Calendar, off by default and only with the instance's OAuth client set (`GOOGLE_OAUTH_CLIENT_ID` and `_SECRET`). `mail` and `calendar` mean the owner's connectors for the owner and her own Google for a person on the instance key (`conversationmodel.ts` `allows`, `capabilities.ts` `runCapabilities`): without `google` they give her nothing, and the owner's claude.ai connectors and Mailbird are never in a friend's set (`NEVER_FOR_ISOLATED`).

- **Connecting** (`googleoauth.ts`, `intakeserver.ts`): the `google` purpose of the intake page is a sign-in, not a form. She asks the assistant for a link (`get_setup_link google`); the page for that single-use link shows a link to Google's consent screen made with `access_type=offline`, `prompt=consent`, PKCE (S256), the combined Gmail and Calendar scopes (`GOOGLE_OAUTH_SCOPES`) and a `state` that is 256 random bits, single use, ten minutes, and bound to that link (a second page view replaces it). `GET /oauth/google/callback` uses the state up, checks the link is still open for her and the purpose and that she still holds the capability, claims the link, exchanges the code at the token endpoint (`GOOGLE_OAUTH_TOKEN_URL`, a fake in the tests) with the client secret and the PKCE verifier, refuses a grant with a missing refresh token or an unticked scope, and writes `{refresh_token, email, scope}` to `tenants/<id>/google/oauth` through the write-only intake token. Every failure is one fixed sentence; a wrong, replayed or foreign state is the page's one 404. The model hears "Google is connected", never a token.
- **Her server** (`googlemcp.ts`): the pinned third-party server (`GOOGLE_MCP_COMMAND` and `GOOGLE_MCP_ARGS`, by default `uvx --exclude-newer 2026-10-20T00:00:00Z workspace-mcp==2.1.0 --single-user --tools gmail calendar`) runs as ONE stdio process per friend, started by this process on first use and closed after `GOOGLE_MCP_IDLE_MINUTES`. Its stdio mode takes credentials from a file, not from the environment, so the token goes OpenBao (her own path; the app's policy also reads `tenants/+/google/*`) -> this process -> a file in a private temp folder (0700, 0600) -> deleted when the process stops; the child's environment is its transport's default (HOME, PATH...) plus the credentials folder, her address and the OAuth client, nothing of the instance (no Anthropic key, no owner login). The SDK would put an MCP server's environment on the Claude CLI's command line, so the run does not get the server at all: it gets an in-process proxy (`googleProxy`, type `sdk`) that lists only the tools her capability set offers, sets `user_google_email` to her own address on every call, and forwards. Two friends are two processes with two tokens.
- **Her tools** (`modules/google.ts`): Gmail (`search_gmail_messages`, `get_gmail_message_content`, `..._batch`, `get_gmail_thread_content`, `..._batch`, `list_gmail_labels` = reads; `draft_gmail_message` = draft; `send_gmail_message` = send, which also replies and forwards by its arguments; `modify_gmail_message_labels` = label, removing INBOX is an archive) under `mail`, and Calendar (`list_calendars`, `get_events`, `query_freebusy` = reads; `manage_event` = calendar-write by its `action`) under `calendar`. Attachment, filter and sign-in tools are not rows, so they do not exist for her. A non-free call of these rows goes to the floor, the judge and her chat, like the owner's: `policy.ts` `classify` is one fold for every source, with no rule of its own for isolated runs beyond the capability set.
- **The same rules** (nothing is copied from the owner's modules): a send reads its recipients from its own arguments with the shared `nativeView`, is never judged without a named recipient (`named`), never fixed (`noFix`); the floor refuses attachments, a "Send As" alias, an export to a file or raw MIME; TRASH or SPAM as a label and a delete (`manage_event` with action delete) are never allowed, for her as for the owner (`neverallowed.ts`); an event with guests and an answer to an invite ask her and are never judged (the shared `namesPeople` of `guests.ts`, `notifyLine`); reading mail or events marks the run's arguments as possibly steered (`untrusted`) and results are cleaned like mail (`toolclean.ts`). The approval comes from the conversation the call was made in (`approvers.ts`: her chat; an answer anywhere else, the admin's included, never applies), judged against her words or, for the handler, its fixed standing task; her audit rows have no words (`audit.ts` `wordless`).
- **The mail check is one function for every conversation** (`heartbeat.ts` `createMailCheck`, `handler.ts` `createHandler`, `triage.ts` `triageBatch`): a `MailContext` says where its seen-mail memory and last tick live, how its triage call is made (the owner's: the login; a friend's: the instance key, her name, her notes, her cost file, her cooldown), how a decision is recorded, whether archiving is log-only, whether a handler exists and what a usage limit means for it; a `HandlerContext` says whose queue, whose name, the standing task, the run and the day's budget. The mail handler is one path as well: the mail-tools module of the conversation (`MailTools.handlerTask`, `modules/mailtask.ts`: Mailbird, Gmail, a friend's Google) states the standing task in its own tool names and, with `createdDraft`, which call left a reply draft; a provider has a handler exactly when it has `handlerTask` (`mailhandler.ts`), so the owner on Gmail has one too (drafts via `create_draft`, read back through the connector and shown on Signal like Mailbird's); `handlerOptions(conversation, payer)` in `agent.ts` builds every handler run (the conversation's own options, a fresh session, the mail module's tools, the preset's `profiles.handler` limits, the notes it has, the standing task as provenance, `untrusted`), and one `handler.md` prompt carries the safety lines for both. The owner's functions took no context before; now the owner is one context (`ownerMailContext`, `ownerHandlerContext`) and her files, prompts and behaviour are as they were (the prompt snapshots are unchanged).
- **The friends' loop** (`mailloops.ts`, started from the heartbeat's tick like the other jobs): for each active friend with `heartbeat`, `mail` and `google`, a connected account and an instance Google client: a `GoogleMail` mailbox (`googlemail.ts`: a search, a read and the INBOX label, called directly on her server with NO model call), the same check, triage (the small model on the instance key, only for NEW mail), handler (a fresh run of hers with her Google tools only, her notes as data, its `provenance` is the standing task (fixed text), drafts only: a send or an invitation asks her in her chat) and alerts in her chat. Her state is `tenants/<id>/mail/` (seen mail, last tick, the handler's queue, a log of decisions with words, which is her file; the admin's audit log gets `heartbeat_triage` rows with her id, label and kind only, and the owner's brief digest never reads them). The cost guard is the idle look: a tick with nothing new costs one search on her server; no access (her cooldown, day's budget, suspension or no key) means no look at all and the mail stays unseen. Archiving is log-only while `ARCHIVE=log` (the one switch of every mail check). One friend's failure is logged once and stops with her.
- **Her brief entry**: what the check did in the last day with mail that needs her or her assistant is a fenced digest in her chat's system prompt (`tenantmail.ts` `mailDigest`), so "anything in my mail?" is answered from it. A daily brief preset and the radar stay the owner's (they read the owner's connectors; `hasPresets` needs her login).
- **Not built**: push (Gmail Pub/Sub, calendar webhooks); polling with the cheap search instead.

## Notion for friends, and what Google and Notion share

A friend with the capability `notion` (and `intake`, and a usable `INTAKE_BASE_URL`) has her OWN Notion, off by default. Google and Notion are two users of two shared pieces, not two implementations:

- **One OAuth helper** (`oauth.ts`): the PKCE pair, the single-use `state` bound to the one-time intake link, the flows in progress, the token POST and the callback route `/oauth/<service>/callback` are written once. A service is an `OAuthProvider` (`googleoauth.ts`, `notionoauth.ts`): its consent address, how its token endpoint is asked, what comes back and where it is stored. The intake page (`intakeserver.ts`) knows no service by name; `PURPOSES` gains `notion` like `google`.
- **One credentialed proxy** (`mcpproxy.ts`): an `UpstreamSession` per friend (opened on first use, closed when idle, a fixed sentence for every failure) and `credentialedProxy`, the in-process server of type `sdk` that a run gets instead of the real server, because the SDK hands an MCP server's command, environment and http headers to the Claude CLI on its command line, where `ps` shows a token. `googlemcp.ts` (a stdio process with a credentials file) and `notionmcp.ts` (the hosted server over https) only say how their connection opens.
- **Connecting** (`notionoauth.ts`): Notion's hosted MCP server (`NOTION_MCP_URL`, `https://mcp.notion.com/mcp`) is found by discovery (`/.well-known/oauth-protected-resource`, then the authorization server's `/.well-known/oauth-authorization-server`), and the instance registers ONE public client by dynamic registration (RFC 7591, `token_endpoint_auth_method: none`, redirect `<INTAKE_BASE_URL>/oauth/notion/callback`) the first time a friend opens a Connect Notion link; the client id is kept in `state/notion-client.json` (an id is no secret; the intake page has only a write-only OpenBao token and must read it; a lock directory keeps the two processes from registering twice) and is never registered again per person or session. A new tunnel address is a new redirect URI and so a new registration; grants made under the old client keep refreshing because each stores the client id and token endpoint it was issued to. The callback stores `{access_token, refresh_token, expires_at, client_id, token_endpoint}` at `tenants/<id>/notion/oauth` through the write-only token.
- **Keeping it alive** (`NotionTokens`): Notion's access tokens last hours and its refresh tokens ROTATE (each refresh returns a new one and retires the old, with a one-step grace). A refresh runs under a per-friend lock (two at once would each spend the same old token and lose the rotation), sends the original client id, and WRITES THE NEW REFRESH TOKEN TO HER OPENBAO PATH BEFORE the new access token is used; if the write fails the new access token is not used and the pair is kept in memory so the next call writes it instead of refreshing again. It runs at the start of every run (the proxy's tool listing) and again for every request (the transport's `fetch` adds the bearer inside this process). The app's OpenBao policy therefore reads AND writes `tenants/+/notion/*` (no delete, no list); re-run `npm run openbao -- setup`. A refresh Notion refuses for good (expired by inactivity or age, withdrawn by her) is recorded (`intakelinks.ts` `markNeedsReconnect`, shown by the list and the doctor) and surfaces as a fixed instruction to the model: tell her, and call `get_setup_link` with purpose `notion`; the run is still shown her tools so it can try one and be told. A refresh that fails for any other reason (Notion down, a timeout) is a plain try-again-later and changes nothing.
- **Her tools** (`modules/notionhosted.ts`): the owner's Notion rows are shared, not copied (`modules/notion.ts` `notionRows`): `notion-search` and `notion-fetch` are reads (free, untrusted text), `notion-create-pages` and `notion-update-page` page writes, `notion-create-comment` a comment write; the hosted server calls them under the name `notion`, so hers are `mcp__notion__notion-search` and so on, and the owner's connector tools are never hers (`NEVER_FOR_ISOLATED`). One row is hers alone: `notion-move-pages` (never judged, always asks her), and a page write that sends a page to the bin (`in_trash`, `archived`) is never judged either. Every other hosted tool is not offered. The rows are `personal`: judge, floor and her chat as for her Google; the approver is the conversation the call was made in; her audit rows are wordless. The manifest-rows fixture gained these six rows on purpose.
- **Intake and admin**: `get_setup_link` and `setup_status` know `notion` ("Notion is connected", or that it no longer works; never a token); `npm run doctor` has a Notion line only when a friend holds the capability (the page's address, whether the client is registered, each friend's state).

## Replies and threads

Signal's reply (quote) works in both directions. When you reply to one of the assistant's messages (an alert, the brief's summary), the quoted text is passed to the chat as fenced data, so "move this one" has something to refer to. The assistant threads its own answer under your message only when that helps: you were already replying to something, or the answer took more than 20 seconds, so other messages may sit in between. Otherwise it answers plainly, to keep the Note to Self thread uncluttered. In a group it always threads its answer under the message that addressed it, and a quoted message reaches it as fenced data too.

The model can also answer with an emoji reaction instead of text for a thanks, an ok or a joke: it starts its reply with `[[react: 👍]]` (exactly one emoji, only at the very start; `src/reaction.ts`). The reaction goes on your message and replaces the ✅ status, and any text after it is still sent.

## Speed and cost

Every model call re-sends the whole context, and most of it is fixed: the tool definitions and the skills list. So the main levers are what the model can see and keeping the prompt cache warm. Numbers below were measured in October 2026 with Sonnet.

- **The model only sees the tools it uses.** Connectors the skills never touch (trading, Gmail, Drive, Docs) are hidden, Notion is cut to the tools the skills use (four by default: search, fetch, create pages, update page), and tools policy always denies are hidden too (`hiddenTools` in `src/policy.ts`; the lists are the `HIDDEN_CONNECTORS` and `NOTION_TOOLS` settings, so keep them in step with your skills). That took the fixed context from about 118k to about 49k tokens. One Notion tool alone (`query-data-sources`) was 21k.
- **Warm processes: one mechanism, one setting.** Starting Claude Code (process, config, skills, connectors) takes about 3 seconds (about 0.7 s for the small Haiku gate) before the model is asked anything, so a process is started ahead of the next message. All of them use the same slot (`SpareSlot`, `src/warmslot.ts`), the three conversation kinds one keyed pool (`WarmPool`, `src/agentwarm.ts`, key = the conversation's key), the same switch `WARM=on|off` and the same idle limit `WARM_IDLE_MINUTES` (default 60: a process stays ready for an hour after the last message, then is dropped and the next message pays the cold start). The slots: **(a) the owner's chat** (Sonnet; prepared after each reply and after a mail ping, renewed by a 25 minute timer only while it is in use, and only when what it was built from changed or it would be stale by the next renewal), **(b) the group that spoke last** (Sonnet; `prepare` in `src/agent.ts`; prepared when a message arrives in a group that may be answered and after each of its turns, replaced when another group becomes the latest), **(b2) the tenants most recently active** (Sonnet; at most `TENANT_WARM_MAX`, the least recently used closed to make room; built from her options and the instance key, which is in her process's environment only; closed when she is suspended or removed), **(c) one Haiku spare for the group gate** (`prepareGate` in `src/gate.ts`). A process is reused only if what it was built from is unchanged (session, prompt, notes index; for the gate its exact system prompt), once, and never for another conversation: the owner's holds the owner's connectors and is never given to a group, a group's (its notes folder as auto-memory, its resumed session, its memory server, no user settings, connectors or skills) is given only to that group. The gate spare is the one that is conversation-independent: the SDK fixes the system prompt, tools, MCP servers and output schema when a process starts, and `WarmQuery.query()` takes only the prompt, so the spare is built from the gate's options alone (the group message look: its rules plus a one-line style summary) and everything about a conversation (clock, notes, log) is in the prompt. That is why any group's untagged message can take it. The two approval judges are one Haiku (`src/approvaljudge.ts`: one system prompt with both jobs, one output schema, and a `task` field, `reply` or `action`, that the prompt states first and the answer repeats; an answer for the other task counts as no answer, so it fails closed), so they share one spare (`JudgeSpare`, `src/judgespare.ts`, the same slot, switch and idle limit): **(d) the approval judge** is started when a chat question goes out, rebuilt after each auto-approve judgement, dropped when the last chat question closes and after `JUDGE_WARM_IDLE_MINUTES` (default 10) unused, with one `timing judge ...` log line per call (warm or cold, phases, api time, cost), and falls back to a cold call if its spare is missing or dead. Measured with real Haiku calls (cold and warm, merged prompt against the two separate ones: the same answers on yes, "yes but make it 16:00", no, a question, a plain calendar create, one with an attendee, a related and an unrelated page fetch; the API varies by seconds): the action task 2.6 to 4.9 s cold, 2.4 to 4.1 s warm; the reply task 2.7 to 3.9 s cold, 1.7 to 2.5 s warm. Other Haiku jobs (the clock look and the owner's look, mail triage, log summaries) are not kept resident. **A warm process can die while idle** (killed, out of memory): it is detected when used (the query fails before any output) and that turn or gate call starts cold instead, then the next spare is built. Checked with the real SDK: a spare stayed usable after 25 and after 65 minutes idle (the SDK has no internal expiry or keepalive for `startup()` processes; the typings document none), and a killed one fails with `ProcessTransport is not ready for writing`. **Memory:** about 200 MB resident per process measured here (`ps` rss of a fresh Haiku spare: 204 MB; other measurements 140 to 200 MB), so at most four, usually three: roughly 450 to 600 MB with the first three present, no tokens (starting one makes no model call). `WARM=off` starts none.
- **Run ceiling.** No model run may outlive `RUN_MAX_MINUTES_CHAT` (40: the owner's chat and every group) or `RUN_MAX_MINUTES_BACKGROUND` (180: gate tasks, brief, radar, the mail handler), enforced in the one wrapper every run passes (`underCeiling` in `src/agentrun.ts`, `src/ceiling.ts`). On the limit the query is aborted (a warm process through its query), `run: timed out after N minutes` is logged and audited (`run`, `timeout`), and the rejection takes the normal error path: the notice (rate-limited in groups), the conversation's queue moves on, and a spare of that conversation is dropped rather than reused. A background run is always cold, so the time it waits for an approval is paused and `BACKGROUND_APPROVAL_TIMEOUT_MINUTES` cannot cut into it; a chat approval wait (15 minutes) counts toward the 40, so a chat turn that waits unanswered on several approvals in a row can be cut, which fails closed. Compaction, the dream, triage, summaries and the small judges run outside this wrapper and are not under the ceiling.
- **The gate call** (untagged group message) is timed per phase in a `timing gate ...` console line: prompt and system size, `init` (process ready, first message), `result`, `api` and total. Measured with real Haiku calls: a cold call spent 0.65 to 0.8 s starting the process and then the model time (about 1.0 s on a quiet moment, 1.5 to 2.5 s on others, the API varies by that much); returning only after the process wound down cost another 0.8 s (fixed: the call returns on the result); the warm spare brings process start to 40 to 75 ms (median whole call 1.9 s against 2.5 s cold in alternating runs). The message look's prompt is kept small (last 12 log lines, long lines cut, a one-line style summary); measured, it saves tokens but no visible latency.
- **Timing line.** Every answered turn, in the owner's chat and in groups, logs one line of durations in ms, no content, for example (made-up numbers): `timing group settle=2003 gateWait=0 gate=2840 gateDelay=0 typing=2004 queue=0 first=4900 run=3100 total=5200`. `settle` is arrival to the end of the settling pause, `gate` the participation call (untagged group messages), `gateWait` how long the burst still waited for it after settling, `gateDelay` the delay it asked for, `typing` arrival to "typing…" showing, `queue` the wait behind an earlier turn, `first` arrival to the model's first message, `run` the model run and `total` arrival to the reply sent (`src/timing.ts`). Use it to compare a tagged and an untagged group message with the owner's chat. A gate call itself takes about 3 s (Haiku, measured), which the settling pause now hides; lowering effort and dropping thinking and the saved session made no measurable difference.
- **Connectors are waited for at start-up** (`MCP_CONNECTION_NONBLOCKING=false`). Otherwise a slow connector (seen: about 30 seconds) means the first model call runs without its tools, and the tool list then changes mid-session, which also throws the prompt cache away.
- **The prompt cache lives an hour** (the default when logged in to a Claude subscription). A message within the hour reuses it; the first one after a quiet hour pays to rebuild it.

| Chat turn | Time | Cost |
|---|---|---|
| Simple reply, warm | about 3 s | about $0.01 |
| Calendar question (loads the skill, one tool call) | 8 to 11 s | $0.03 to $0.08 |
| Remembering something | about 10 s | about $0.02 |
| First message after a quiet hour (cache rebuilt) | about 8 s | about $0.20 |

What is left is model time: a tool question is two or three model calls of 2 to 3 seconds each, one of them loading the skill.

**Text length tiers (`LIMITS` in `src/sanitize.ts`).** One named constant per purpose, characters unless noted: `control` 80 (a page control's name in an audit row), `name` 100 (a person's name), `reason` 120 (error text or a reason in an audit row or notice), `gist` 160 (a one-line gist: style note, description, shown row), `subject` 300 (a mail subject), `preview` 200 (a short preview: thread quote, wake-up log, summary input, error text in an audit row), `line` 240 (one message as a line a model skims: gate and tail lines, helper-model context; the gate pays for every character), `logLine` 600 (a message or ledger entry in a group or notice log in a prompt), `quote` 1500 (the message being replied to), `brief` 1500 (a short report, or a logged question and its arguments), `logEntry` 4000 (one entry kept in a conversation log file), `body` 20,000 (a mail body or voice transcript), `message` 70,000 (what a person typed, a long message included: 64 KB plus a note; never lower), `block` 100,000 (one fenced block), `args` 6000 (tool arguments in an audit row), `textFile` 200,000 (a text file shown to the model) and `pageView` 24,000 (one browse page view). The Signal package keeps its own byte caps and has no dependency on `src/`: `MAX_LONG_TEXT_BYTES` (64 KB) pairs with `message`, `MAX_FILE_BYTES` (20 MB, PDFs and other files) with `textFile`.

## The Signal package and the app

`packages/signal` is a library: it never exits the process, installs no signal handlers and prints nothing unless given a logger. The policy lives in `src/main.ts`: if the messenger reports a lost connection (`messenger.onClose`: for Signal the socket or the daemon it started), the app exits and launchd restarts it; SIGTERM/SIGINT stop the messenger (Signal: its daemon) and exit.

**The messenger (`packages/messenger`, `src/messenger.ts`).** The app talks to ONE `Messenger` interface and never to a platform: receive (`onMessage`, `onReaction`, `onDeletion`, `onClose`), `send(target, { text, styles, quote, attachments })`, `react`, `typing`, `markRead`, `groups()`, `attachmentFile(ref)`, `readLongText(ref)`, `self` (the assistant's own author id) and `capabilities` (`reactions, typing, readReceipts, groups, people, voice, quotes, maxMessageBytes, voiceFormat`). A conversation is an opaque `Target` (undefined: the owner's chat; a group id; `directTarget(accountId)` for one other person). Missing capabilities are handled quietly in one place each: no typing means working / done icons (reactions), no reactions means no icons and the `send` tool's react answers "not available", no read receipts means none sent, no quotes means no threading, a `maxMessageBytes` limit means `outbound.reply` sends parts that fit, `voice` gates spoken replies and `voiceFormat` picks the speech engine's ffmpeg step. `MESSENGER=<name>` (default `signal`) loads `@ted-assistant/<name>/messenger` by dynamic import (`loadMessenger`); that entry exports `createMessenger(config)` and `doctor(config)`, which is how `npm run doctor` reports the messenger. The Signal adapter (`packages/signal/src/messenger.ts`) owns the signal-cli daemon, the client and its two modes (Note to Self, own account), the attachments folder, the text style strings and person targets. Who the OWNER is stays the app's decision (`guards.ts`, `tenants.ts`): the messenger only reports `from` / `fromUuid`. Every adapter passes ONE contract suite (`messengerContract` in `packages/messenger/src/contract.ts`, run against `FakeMessenger` and against the Signal adapter over its fake daemon): send and refusal, the best-effort calls that never throw, neutral incoming messages, reactions and deletions, one handler per kind, groups, attachments, `onClose` reported once and stopping on purpose not being a loss. A platform's own options are `unknown` to the interface; its package exports their type (`SignalOptions`) and checks them when the messenger is made. The speech libraries live in their own private package, `packages/speech` (entry points `/tts` and `/voice`), which any messenger can use without the Signal package: the `tts*`, `voices`, `voiceclip`, `transcribe`, `audiofile` and `voiceformat` files and their tests, `scripts/` (`kokoro-say.py`, `qwen-tts-server.py`, `setup-tts.sh`) and `docs/remote-tts.md`. It depends only on `@ted-assistant/messenger` (the `VoiceFormat` type); `packages/signal` does not import it and has its own small `internal/exec.ts`.

`packages/speech` and the platform skeletons (telegram, whatsapp, slack) are private and have no build: their `exports` point at `src/` (speech with the `workspace-source` condition). `packages/messenger` and `packages/signal` are published (signal depends on messenger with a `^0.1.0` range), so they publish compiled `dist/` (Node does not strip types inside `node_modules`), and `npm run verify-pack -w packages/signal` packs both, installs the two tarballs together into an empty folder and imports every entry point under plain Node. But the app runs straight from TypeScript with no build step: its `exports` carry a `workspace-source` condition that points at `src/`, and every app command (`run.sh`, the `npm run` scripts, `npm test`, `tsconfig.json` `customConditions`) enables it with `--conditions=workspace-source`. A new `node` entry point that imports the signal package needs that flag, or it resolves to `dist/` and fails when that has not been built (a `dist/` left over from an old build would be loaded instead: delete it).
